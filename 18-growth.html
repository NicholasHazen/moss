Let environmental input change supply

An empty patch receives three new biomass units, and a grazer asks for a two-unit meal. At the end of the tick, the grazer might have two reserve units or none. We can produce both results using the same growth and meal functions: all we have to change is their order.

Trace when new supply becomes available

You'll implement renew, which adds only the biomass that fits and reports the actual addition. We'll give that helper a tick-based daylight cycle, then run it before and after a meal in two explicit Bevy schedules. Holding the grazer and patch fixed lets us attribute a missed meal to phase order.

Follow both runs through the same four-tick day. By the end, you should be able to account for environmental additions, explain why the first meals differ, and show how equal final stores can conceal different paths. That is the distinction a helper test alone can't establish: correct operations still need a deliberate order when they share state.

This isolated Bevy ECS 0.18.1 model uses a four-tick day and one-for-one food conversion as teaching rules. You'll implement bounded renewal and test it in two schedules. The reference doesn't install growth or feeding in live Moss or change NOW.md.

Give one consumer a renewing supply

The previous lesson made starting conditions explicit before comparing individuals. We'll use that discipline here by holding the consumer fixed. One grazer reaches one patch on every tick, so the difference we observe can't come from crowding, target choice, or another animal winning a contest.

The patch begins empty, can hold four biomass units, and requests three new units on each lit tick. The grazer begins at zero reserve, can hold twenty, and requests a two-unit meal each tick. There is no travel, maintenance, or death. A meal still obeys the familiar supply and capacity bounds, converting each accepted biomass unit into one reserve unit.

We store the single patch and grazer as resources to keep the scheduling question visible. This is a convenient shape for one pair, rather than a layout for a whole population. A many-actor world would use entities and queries, with stable identities and the contention handling from the meal lesson.

Renewal introduces an accounting difference worth naming now. A meal moves existing units between stores; growth adds units from the environment. Daylight represents that external input here. There are no soil nutrients or decomposition in the model, so the addition doesn't establish a recycling loop.

Locate daylight in executed time

Growth needs a repeatable answer to whether this tick is lit, so we'll derive daylight from executed simulation time. Our default day lasts four executed ticks. Ticks one and two are lit, three and four are dark, and five begins the next lit phase. To calculate the position in that cycle, convert the one-based tick to a zero-based value with tick - 1, then take the remainder modulo cycle_ticks. Positions below lit_ticks are lit.

The constructor makes the remainder operation meaningful by rejecting a zero-length cycle. It also rejects a lit duration longer than the whole cycle. A day with no lit ticks is still valid, as is a day that is entirely lit. Zero darkness or zero light describes a scenario; zero cycle length would break the calculation.

The schedule begins by incrementing its tick with checked_add. That gives growth the one-based tick it needs before evaluating daylight. Counter overflow stops the run before growth or eating instead of wrapping to an earlier day. The initial zero means no tick has executed, and is_lit rejects it as an executed-tick input. After a successful schedule run returns, the counter identifies the completed result we're inspecting.

Neither growth nor daylight reads frame counts or elapsed milliseconds. Repeated inspection therefore can't bring another dawn. Faster playback can request more complete ticks, while pausing requests none. Keeping that pacing outside the rule lets us compare the same four-tick day regardless of how long we take to watch it.

Add only the supply the patch can hold

Before comparing schedules, we need renewal to give an honest answer at capacity. If a four-unit patch already contains three, a request for three more can add only one. The helper should both add one and return one, so the report records accepted supply rather than the larger request.

Calculate remaining space before adding. Adding the whole request and clamping afterward can overflow first, especially near u32::MAX. Patch::new establishes that biomass doesn't exceed capacity, so capacity minus biomass gives valid room. Limiting the addition to that room preserves the same relationship after mutation.

The patch fields are private, with the usual Rust module boundary: code in the defining module and its descendants can still access them. Such code must maintain the invariant too. The constructor and renewal helper give us a clear path through which to establish and preserve it.

Darkness and a full patch both return an actual addition of zero, but they explain that number differently. Showing the daylight phase alongside current biomass and capacity lets a reader tell which condition applied. The supplied Flow resource records only the latest tick's addition and meal, and each system overwrites its field even when the outcome is zero. Otherwise, yesterday's successful growth could appear to continue through darkness.

Let the meal use what exists at its turn

With bounded renewal in place, we can isolate the scheduling choice without changing either action's arithmetic. Both schedules begin by selecting the next tick. One then runs growth followed by eating; the other runs eating followed by growth. We use .chain() to express those dependencies. Selecting a single-threaded executor would limit execution mode, but it wouldn't tell Bevy which biological order we intended.

Start with the empty patch on lit tick one. Growth first adds three units, after which the grazer takes two. Eating first finds nothing, so that meal contributes zero even though growth adds three later in the same tick. Now start from a full patch instead: eating can make room that a later growth phase uses. The table shows both effects.

So ordering can change both access to food and the amount of external supply accepted. The same functions can be individually correct in either schedule. Choosing between their combined outcomes requires a model decision about when new material becomes available.

Continue the empty-patch comparison through tick three, the first dark tick. Carry each patch forward from its own previous result. Does the schedule that missed its first meal catch up as soon as daylight ends?

Hint 1: preserve each run's first result

Growth before meal leaves one biomass after tick one. Meal before growth leaves three. Tick two begins with those different balances.

Hint 2: distinguish stored food from new supply

Darkness prevents a new addition, but it doesn't prevent a meal from using biomass already present. Find what each schedule retained after tick two.

Prediction answer

Growth before meal reaches biomass two and reserve four on tick two, then biomass zero and reserve six on tick three. Meal before growth reaches biomass four and reserve two, then biomass two and reserve four. The two runs first agree at the end of tick four, with biomass zero and reserve six. Their equal final state hides the earlier delay.

Implement renewal and run both schedules

Your edit is renew. It returns zero in darkness; during light, it adds what fits and returns the actual addition. The surrounding systems and two schedules are provided, so the same small arithmetic helper will be checked both directly and as part of a real Bevy execution.

use bevy_ecs::{prelude::*, schedule::ExecutorKind};

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum InvalidSetup {
    OverCapacity,
    InvalidDay,
}

#[derive(Resource, Clone, Copy, Debug, PartialEq, Eq)]
struct Patch {
    biomass_units: u32,
    capacity_units: u32,
}

impl Patch {
    fn new(biomass_units: u32, capacity_units: u32) -> Result<Self, InvalidSetup> {
        if biomass_units > capacity_units {
            return Err(InvalidSetup::OverCapacity);
        }
        Ok(Self {
            biomass_units,
            capacity_units,
        })
    }
}

#[derive(Resource, Clone, Copy, Debug, PartialEq, Eq)]
struct Daylight {
    cycle_ticks: u64,
    lit_ticks: u64,
}

impl Daylight {
    fn new(cycle_ticks: u64, lit_ticks: u64) -> Result<Self, InvalidSetup> {
        if cycle_ticks == 0 || lit_ticks > cycle_ticks {
            return Err(InvalidSetup::InvalidDay);
        }
        Ok(Self {
            cycle_ticks,
            lit_ticks,
        })
    }

    fn is_lit(self, tick: u64) -> bool {
        let zero_based = tick.checked_sub(1).expect("executed ticks begin at one");
        zero_based % self.cycle_ticks < self.lit_ticks
    }
}

#[derive(Resource, Default)]
struct Tick(u64);

#[derive(Resource)]
struct Rules {
    growth_units_per_lit_tick: u32,
    meal_units_per_tick: u32,
}

#[derive(Resource, Default)]
struct Grazer {
    reserve_units: u32,
}

const RESERVE_CAPACITY_UNITS: u32 = 20;

#[derive(Resource, Default)]
struct Flow {
    added_units: u32,
    eaten_units: u32,
}

fn begin_tick(mut tick: ResMut<Tick>) {
    tick.0 = tick.0.checked_add(1).expect("tick counter exhausted");
}

fn grow(
    tick: Res<Tick>,
    daylight: Res<Daylight>,
    rules: Res<Rules>,
    mut patch: ResMut<Patch>,
    mut flow: ResMut<Flow>,
) {
    flow.added_units = renew(
        &mut patch,
        daylight.is_lit(tick.0),
        rules.growth_units_per_lit_tick,
    );
}

fn meal(
    rules: Res<Rules>,
    mut patch: ResMut<Patch>,
    mut grazer: ResMut<Grazer>,
    mut flow: ResMut<Flow>,
) {
    let space = RESERVE_CAPACITY_UNITS - grazer.reserve_units;
    let eaten = rules
        .meal_units_per_tick
        .min(patch.biomass_units)
        .min(space);
    patch.biomass_units -= eaten;
    grazer.reserve_units += eaten;
    flow.eaten_units = eaten;
}

#[derive(Clone, Copy, Debug)]
enum Order {
    GrowthBeforeMeal,
    GrowthAfterMeal,
}

fn tick_schedule(order: Order) -> Schedule {
    let mut schedule = Schedule::default();
    schedule.set_executor_kind(ExecutorKind::SingleThreaded);
    match order {
        Order::GrowthBeforeMeal => {
            schedule.add_systems((begin_tick, grow, meal).chain());
        }
        Order::GrowthAfterMeal => {
            schedule.add_systems((begin_tick, meal, grow).chain());
        }
    }
    schedule
}

fn fixture(biomass: u32, capacity: u32, growth: u32, bite: u32) -> World {
    let mut world = World::new();
    world.insert_resource(Patch::new(biomass, capacity).unwrap());
    world.insert_resource(Daylight::new(4, 2).unwrap());
    world.insert_resource(Rules {
        growth_units_per_lit_tick: growth,
        meal_units_per_tick: bite,
    });
    world.init_resource::<Tick>();
    world.init_resource::<Grazer>();
    world.init_resource::<Flow>();
    world
}

#[derive(Debug, PartialEq, Eq)]
struct Reading {
    tick: u64,
    biomass: u32,
    reserve: u32,
    added: u32,
    eaten: u32,
}

fn inspect(world: &World) -> Reading {
    Reading {
        tick: world.resource::<Tick>().0,
        biomass: world.resource::<Patch>().biomass_units,
        reserve: world.resource::<Grazer>().reserve_units,
        added: world.resource::<Flow>().added_units,
        eaten: world.resource::<Flow>().eaten_units,
    }
}

fn main() {
    for order in [Order::GrowthBeforeMeal, Order::GrowthAfterMeal] {
        let mut world = fixture(0, 4, 3, 2);
        let mut schedule = tick_schedule(order);
        println!("{order:?}");
        for _ in 0..4 {
            schedule.run(&mut world);
            println!("{:?}", inspect(&world));
        }
    }
}

    if !lit {

    added

Explain the path as well as the endpoint

In this lossless conversion, biomass plus reserve increases only by actual environmental addition. Eating changes where the units are stored without changing their sum. The accounting test widens both stores to u64 before adding them, so the sum of two valid u32 fields can be represented. Reasoning for the one-lit-tick comparison

Only tick one adds supply, so each run receives three units over the four ticks. Growth first lets the grazer eat two on tick one and the remaining one on tick two. Meal first delays those meals to ticks two and three. Both finish with zero biomass and three reserve units, while the early availability still differs. This prediction follows the declared arithmetic; run the variant to compare its trace with that reasoning.

The Bevy 0.18.1 schedule configuration source explains chained dependencies, and its executor documentation describes single-threaded execution. They tell us how to express an order. The empty patch and missed meal tell us why choosing that order matters.

Equal endpoints can hide a missed meal

Our opening grazer received no reserve because its turn came before the new supply. Renewal respected the patch's capacity in both schedules, but the order decided when the grazer could use the addition. By tick four, the equal final stores concealed that earlier delay. Reporting actual flows and intermediate states lets us explain both the accounting and the experience along the way.

In terminal transitions and retained history, an earlier phase will change whether an animal may take its next action at all. We'll make that eligibility change explicit and preserve an account of it after the animal is removed.
