Ecosystem depth · 40 minutes

Compare individuals fairly

One run ends with 111 reserve units and another with 222. The second looks more successful until we count its animals: it has twice as many.

Build populations whose differences you can explain

To interpret those totals, we need to know what each animal started with and which cost it actually paid. You'll implement populate, validating an authored roster before spawning it and resolving each optional maintenance override into an individual component. Then we'll follow the same stable IDs through a pair of runs while changing the population size.

The resulting reports should let you separate three questions: what a default supplies, what an individual stores, and what a larger aggregate means. You'll check that an invalid roster leaves the world unchanged and that doubling this maintenance-only population changes the total without improving either original animal's outcome.

This isolated Bevy lab uses authored maintenance costs to study comparisons. Its profiles are teaching inputs rather than measurements of real species. It doesn't change Moss's fixture or the active assignment in NOW.md.

Start with two individuals you can recognize

Begin with two hares, IDs 10 and 20. Each starts with 60 reserve units and receives three maintenance executions. ID 10 costs two units per tick; ID 20 costs one. There is no feeding, movement, or interaction, so we can first ask a narrow question: what difference does the configured upkeep make under otherwise equal conditions?

After three executions, ID 10 should have 54 units and ID 20 should have 57. Their three-unit difference follows from paying different rates three times. The upkeep system doesn't read the IDs, so identity doesn't cause the difference. IDs let us connect each outcome to its profile without assuming that ECS query order matches authoring order. As in target resolution, an identity gives us something stable to follow through changing collections.

Now keep those two animals and add IDs 30 and 40 with the same pair of cost profiles. All four share the same declared area of 64 cells. Count per area rises from 2/64 to 4/64, but we have also doubled the starting reserve from 120 to 240. These facts belong beside the final totals if we want the comparison to mean anything.

The unchanged individual results are expected here. Area is experiment metadata; no system reads it to calculate space, contact, or competition. Doubling this roster changes the count and totals without giving the original animals another interaction. A finite feeding system could make added neighbors consequential, but maintenance alone can't demonstrate that effect.

Choose when a cost becomes the animal's own

To make the cost comparison repeatable, we need to decide when a default becomes an individual's stored value. Each authored Profile contains a species and an optional maintenance override. The species resource supplies defaults of Hare 2 and Fox 4. When we populate the world, we'll resolve the override once and store the result in the individual's Maintenance component. The running upkeep system then reads that component.

This gives two hares a straightforward way to differ. ID 10 uses None, meaning “use the species default,” while ID 20 uses Some(1). An explicit Some(0) is also valid in this experiment: it requests zero cost. Treating zero as though it meant absence would silently discard an authored value and replace it with the default.

Resolving at spawn time has a consequence we should test. Changing the default afterward won't rewrite components that already exist. One test changes the Hare default to 99 and checks that the original pair still pays two and one. This differs from the earlier query lab, where maintenance read the shared rates resource on each execution. Either design can be useful; here we want each profile to remain a stable experimental input.

The fallback comes from the standard Option API. Its method provides a value when the override is absent. The larger choice—when to apply that fallback and where to store the result—belongs to our model. Reading the resolved component makes it possible to explain an individual's cost without consulting a resource that may have changed later.

Validate the whole roster before spawning it

To compare individuals across runs, we need unambiguous IDs. This lab reserves zero as invalid and rejects duplicates, including an incoming ID that already belongs to an entity in the world. The identities are stable within this run; retained reports from several runs would also need a run identifier.

There's a subtle failure case when importing several profiles at once. Suppose the world already contains ID 10, and a new batch offers valid ID 30 followed by duplicate ID 10. If we spawn while validating, the function could return an error after leaving ID 30 behind. The caller would have a rejected batch and a changed starting population.

We'll avoid that partial result with two passes. First, populate collects existing IDs in a BTreeSet and validates every incoming profile against it. Inserting an ID reports whether it was new, so the same operation catches collisions with the world and repetitions inside the batch. Only after the complete pass succeeds does spawning begin.

The resulting guarantee is specific: validation errors leave the population unchanged. We aren't adding rollback for allocation failure or arbitrary panics, and the supplied fixture ensures that the defaults resource exists. A focused guarantee is easier to use and test than a broad transaction promise the implementation can't fulfill.

The function borrows the profile slice, but the world doesn't keep that borrow. The world keeps copied identity, species, and reserve values together with the resolved maintenance rate; it doesn't retain the profile slice or its optional override. Reporting makes another owned projection and sorts it by stable ID. Reversing spawn order may change ECS handles while leaving that report equal. Bevy 0.18.1's World API describes the immediate spawn operation used during this setup.

Build the population boundary

Your population constructor has two promises to keep: resolve valid profiles consistently and leave a rejected batch unapplied. Before editing, trace both the ordinary and rejected batches. For the ordinary pair, resolve each cost and calculate the two reserves after three executions. For the rejected extension, decide exactly when the duplicate ID should stop the function and whether any spawning should have occurred.

Hint 1: finish validation first

Collect existing SimId values, then reject incoming zero IDs or IDs that the set can't insert as new. Keep world.spawn out of this first pass.

Hint 2: copy the resolved cost into each animal

After validation, obtain the defaults. For each profile, use its override or matching species default and spawn the ID, species, reserve, and maintenance component together.

Prediction answer

The pair finishes at 54 and 57, while the doubled roster totals 222. The extension with ID 30 followed by existing ID 10 returns DuplicateId(10) and leaves only the original pair. A partially accepted extension would change the experiment before it began.

use bevy_ecs::{prelude::*, schedule::ExecutorKind};
use std::collections::BTreeSet;

#[derive(Component, Clone, Copy, Debug, PartialEq, Eq)]
struct SimId(u32);

#[derive(Component, Clone, Copy, Debug, PartialEq, Eq)]
enum Species {
    Hare,
    Fox,
}

#[derive(Component)]
struct Reserve(u32);

#[derive(Component)]
struct Maintenance(u32);

#[derive(Resource, Clone, Copy)]
struct Defaults {
    hare: u32,
    fox: u32,
}

impl Defaults {
    fn rate(self, species: Species) -> u32 {
        match species {
            Species::Hare => self.hare,
            Species::Fox => self.fox,
        }
    }
}

#[derive(Resource)]
struct AreaCells(u32);

#[derive(Clone, Copy)]
struct Profile {
    id: u32,
    species: Species,
    initial_reserve_units: u32,
    maintenance_override: Option<u32>,
}

const PAIR: [Profile; 2] = [
    Profile {
        id: 10,
        species: Species::Hare,
        initial_reserve_units: 60,
        maintenance_override: None,
    },
    Profile {
        id: 20,
        species: Species::Hare,
        initial_reserve_units: 60,
        maintenance_override: Some(1),
    },
];

const DENSER: [Profile; 4] = [
    PAIR[0],
    PAIR[1],
    Profile { id: 30, ..PAIR[0] },
    Profile { id: 40, ..PAIR[1] },
];

enum AuthorError {
    ZeroId,
    DuplicateId(u32),
}

fn populate(world: &mut World, profiles: &[Profile]) -> Result<(), AuthorError> {

}

fn empty_world() -> World {
    let mut world = World::new();
    world.insert_resource(Defaults { hare: 2, fox: 4 });
    world.insert_resource(AreaCells(64));
    world
}

fn fixture(profiles: &[Profile]) -> World {
    let mut world = empty_world();
    populate(&mut world, profiles).expect("authored fixture IDs are valid");
    world
}

fn upkeep(mut creatures: Query<(&Maintenance, &mut Reserve)>) {
    for (rate, mut reserve) in &mut creatures {
        reserve.0 = reserve.0.saturating_sub(rate.0);
    }
}

fn execute(world: &mut World, ticks: u32) {
    let mut schedule = Schedule::default();
    schedule.set_executor_kind(ExecutorKind::SingleThreaded);
    schedule.add_systems(upkeep);
    for _ in 0..ticks {
        schedule.run(world);
    }
}

#[derive(Debug, PartialEq, Eq)]
struct Reading {
    id: u32,
    species: Species,
    reserve_units: u32,
    units_per_tick: u32,
}

fn readings(world: &mut World) -> Vec<Reading> {
    let mut query = world.query::<(&SimId, &Species, &Reserve, &Maintenance)>();
    let mut rows: Vec<_> = query
        .iter(world)
        .map(|(id, species, reserve, rate)| Reading {
            id: id.0,
            species: *species,
            reserve_units: reserve.0,
            units_per_tick: rate.0,
        })
        .collect();
    rows.sort_by_key(|row| row.id);
    rows
}

fn total_units(rows: &[Reading]) -> u64 {
    rows.iter().map(|row| u64::from(row.reserve_units)).sum()
}

fn main() {
    let defaults = *empty_world().resource::<Defaults>();
    println!(
        "defaults: Hare={}/tick Fox={}/tick",
        defaults.rate(Species::Hare),
        defaults.rate(Species::Fox)
    );
    for (label, profiles) in [("pair", PAIR.as_slice()), ("denser", DENSER.as_slice())] {
        let mut world = fixture(profiles);
        execute(&mut world, 3);
        let rows = readings(&mut world);
        println!(
            "{label}: count={} cells={} reserve_total={}",
            rows.len(),
            world.resource::<AreaCells>().0,
            total_units(&rows)
        );
        for row in rows {
            println!(
                "  #{}: reserve={} cost={}/tick",
                row.id, row.reserve_units, row.units_per_tick
            );
        }
    }
}

#[derive(Debug, PartialEq, Eq)]
enum AuthorError {
    ZeroId,
    DuplicateId(u32),
}

fn populate(world: &mut World, profiles: &[Profile]) -> Result<(), AuthorError> {
    let mut ids: BTreeSet<u32> = world.query::<&SimId>().iter(world).map(|id| id.0).collect();
    for profile in profiles {
        if profile.id == 0 {
            return Err(AuthorError::ZeroId);
        }
        if !ids.insert(profile.id) {
            return Err(AuthorError::DuplicateId(profile.id));
        }
    }
    let defaults = *world.resource::<Defaults>();
    for profile in profiles {
        let rate = profile
            .maintenance_override
            .unwrap_or(defaults.rate(profile.species));
        world.spawn((
            SimId(profile.id),
            profile.species,
            Reserve(profile.initial_reserve_units),
            Maintenance(rate),
        ));
    }
    Ok(())
}

fn empty_world() -> World {
    let mut world = World::new();
    world.insert_resource(Defaults { hare: 2, fox: 4 });
    world.insert_resource(AreaCells(64));
    world
}
