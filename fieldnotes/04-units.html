Give the number a unit

Fern has four reserve units left. A forecast says that the next three ticks will cost six. If reserve stops at zero, how much will she actually pay? We'll build a report that can keep all three facts together: six requested, four paid, and zero remaining. Along the way, we'll use Rust types and arithmetic operations to make those meanings harder to mix up.

This is an isolated forecast built from copied inputs. You'll implement one function in units.rs; it won't change a live reserve or add a rule to Moss. The illustrative rate belongs to this calculation, and the active movement exercise remains in NOW.md.

Account for the missing two units

In the query lesson, different species rates gave us different reserves after three executions. Here we'll examine the arithmetic for a rate of two units per tick. Three ticks multiplied by two units per tick requests six reserve units. If we start with 60, there is enough to pay all six and finish at 54.

Starting with four changes the payment, but it doesn't change the requested cost. Under a rule that floors reserve at zero, only four units can be removed. Calling that a six-unit payment would invent expenditure; reporting only “zero remaining” would lose the explanation of the shortage. Our forecast therefore needs separate fields for the requested charge, actual payment, and remaining reserve.

Before choosing Rust operations, put a few cases beside one another. The zero-duration case helps check that we're measuring simulated time rather than the number of times someone asks for a forecast:

Three forecasts under the same maintenance rule
InputsRequested, actually paid, remaining
60 units; 3 ticks; 2 units per tick6 units requested; 6 paid; 54 remaining.
4 units; 3 ticks; 2 units per tick6 units requested; 4 paid; 0 remaining.
4 units; 0 ticks; 2 units per tick0 units requested; 0 paid; 4 remaining.

All three rows assume a constant rate, no replenishment, and a nonnegative reserve. Those assumptions are part of the forecast. If Fern eats during the interval or her upkeep changes, this calculation no longer predicts the whole outcome. A reader needs to know what a report includes before deciding whether its answer explains the world.

Help the caller keep quantities apart

The inputs contain three numbers with different jobs: a reserve, a duration, and a rate. If all three parameters were plain u32, Rust would accept them in the wrong positions. Good names help when reading the function, but distinct types can also catch the mistake where the function is called.

We'll use three tuple structs: Units(u32), Ticks(u32), and UnitsPerTick(u32). Each stores one integer, yet each is a different type. Their unnamed field is accessed as .0. Inside forecast, we'll read those fields to do the arithmetic, then wrap each result in the type that describes its unit.

This is enough structure for the calculation we need. We aren't defining multiplication for every possible unit combination. Instead, one function states the dimensional relationship: ticks multiplied by units per tick produces units. Keeping that decision in one place makes it easier to inspect than several call sites each assembling the same formula.

All three wrappers derive Copy because they contain small integer values that we want to duplicate freely. Passing them by value leaves the caller's inputs available. This also makes the forecast's relationship to the world clear: it receives copies and returns an owned report. It has no mutable reference through which it could deduct anything from Fern's live reserve.

Once you've read the complete signature below, compare its correct call with forecast(Units(60), UnitsPerTick(3), Ticks(2)). The two final arguments have the wrong types, even though both contain integers. That intentional compiler experiment should be corrected by putting a Ticks value in the duration position and a UnitsPerTick value in the rate position. The Rust Book's tuple-struct section explains why these wrappers remain distinct.

Decide what each arithmetic limit means

We know how to handle a reserve smaller than the requested charge: the remainder should stop at zero. Rust's saturating_sub expresses that rule. After calculating the bounded remainder, we can recover the payment as starting reserve minus remaining reserve. That subtraction is safe because the remainder cannot exceed the starting amount.

There is another limit that needs a different response. Our requested total is stored in a u32, whose largest value is 4,294,967,295. If ticks multiplied by rate exceeds that value, no exact total fits in the report. Saturating the product would print a plausible number that is smaller than the real request. Wrapping would make the discrepancy even harder to recognize.

We'll therefore use checked_mul for the requested total. It returns Some(total) when the product fits and None when it doesn't. Our function will return None in the latter case too, telling the caller that it couldn't produce the promised exact forecast. The explicit match in the answer keeps both paths visible.

These methods aren't interchangeable choices about how cautious to be. The zero floor is an intentional rule for reserve; an unrepresentable product prevents us from completing the calculation accurately. The references for checked multiplication and saturating subtraction define the operations. Our reporting contract explains why we use each one here.

A successful report may legitimately contain zeros. With zero ticks, for example, requested and paid are both zero while reserve stays unchanged. Returning an all-zero report on overflow would confuse that successful calculation with a failure to calculate. The next lesson will develop this distinction between a value being zero and a value being unavailable.

Build the forecast

Before editing, follow the four-unit example through the two operations: first calculate the requested amount, then calculate what can actually be paid. Compare it with a request for u32::MAX ticks at two units per tick. The extreme input is useful because it forces the overflow policy to become observable.

Hint 1: preserve the exact request

Multiply ticks by the rate with checked_mul. A successful product becomes the requested field. An unsuccessful product should return None before constructing a report.

Hint 2: derive payment from the remainder

Subtract the request from the starting reserve with saturation. The actual payment is the start minus that bounded remainder, so it can never exceed the amount available.

Prediction answer

Four starting units, three ticks, and a rate of two produce requested 6, paid 4, remaining 0. The maximum tick count multiplied by two can't fit in the requested field, so that forecast returns None.

Complete worked answer: units.rs
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Units(u32);

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Ticks(u32);

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct UnitsPerTick(u32);

#[derive(Debug, PartialEq, Eq)]
struct Forecast {
    requested: Units,
    paid: Units,
    remaining: Units,
}

fn forecast(start: Units, ticks: Ticks, rate: UnitsPerTick) -> Option<Forecast> {
    let requested = match ticks.0.checked_mul(rate.0) {
        Some(units) => units,
        None => return None,
    };
    let remaining = start.0.saturating_sub(requested);
    Some(Forecast {
        requested: Units(requested),
        paid: Units(start.0 - remaining),
        remaining: Units(remaining),
    })
}

fn main() {
    let report = forecast(Units(4), Ticks(3), UnitsPerTick(2))
        .expect("the example's product fits in u32");
    println!("requested={} paid={} remaining={}",
        report.requested.0, report.paid.0, report.remaining.0);
}

Use the failures to locate a mistaken assumption

Each test challenges a different part of our account. If the ordinary three-tick case fails, look for a rate used as though it were already a total. If the shortage case reports six paid, check whether the payment was copied directly from the request. The zero-duration and zero-rate assertions catch an accidental minimum charge that the model never specified.

The two numerical-limit tests are especially useful together. One rejects a product beyond the range; the other accepts the exact maximum. A guard that simply rejects “very large” values could satisfy the first while breaking the second. Testing both sides gives the boundary a precise meaning that we can reuse when validating dimensions and other bounded inputs.

Passing these tests establishes the forecast under its stated assumptions. Moss's installed maintenance system doesn't call this helper, so the tests don't establish a new connection to the live schedule. If we later put the report in a chart, we would also need to check which ticks the chart requests and whether its labels describe projected or observed expenditure.

Read the report as a forecast

Return to Fern's four units. The report can now explain the two-unit shortfall without creating negative reserve or recording a payment she couldn't make. Yet calling the function has left her live reserve alone: the inputs were copies, and the returned account describes what would happen under our assumptions.

Recall: why isn't an unavailable forecast an empty forecast?

An empty forecast would still claim that the calculation succeeded and produced its fields. None says the exact requested amount couldn't be represented. Substituting zeros would erase that distinction and give the inspector a result it had no basis to display.

That care with missing evidence will matter beyond arithmetic. In the next lesson, we'll ask whether an absent target identity, an empty patch, and a patch missing from a reading should produce the same inspector message.
