A living world. An inspectable program.

Return with a different question

Suppose an observation is empty. You know several ways that could happen: the entity might lack a required component, its commands might still be pending, or the history might not cover the time you're asking about. Recognizing the result isn't enough to choose between those explanations. These six returns change the fixtures from earlier lessons and ask you to decide what evidence would settle the question.

Optional mixed practice. Try cases one through three after the ECS core, then four through six after the first cumulative fieldwork. Each is available whenever you want it; there are no grades or unlocks. The examples use isolated course worlds and leave live Moss and NOW.md unchanged.

If you're listening, pause at the prediction before opening its hint or full answer; generated narration skips those disclosures and their code. The first three cases build small reporting worlds, while four and five use your actual fieldwork library. Case six uses the existing target lab, so it doesn't introduce another implementation of the same selection rule.

Choose the evidence before the fix

The aim of these returns is to diagnose a changed situation with ideas you already know. Each case starts with an observation or prediction, offers a hint when you need one, and develops a complete explanation you can check. Work through one case at a time: identify what is uncertain, choose an observation that separates the possible causes, and then compare it with the answer. Five of the worked checks can join your continuing project, so the reasoning remains available when that world changes.

1. Which rows changed, and which reading stayed old?

Start with a reporting world containing the three rows below. Each execution of its decrement system requests Query<(&Identity, &mut Reserve), With<Active>> and removes one unit from every matching row. Before running the schedule, an observer saves an owned vector of identity and reserve pairs. Its reporting query does not require Active, so the writer and observer may include different rows.

Initial reporting fixture
RowIdentityReserveActive marker
A117Present
B127Absent
CAbsent7Present

Run the decrement schedule twice, asking for extra reports between the runs. Predict each current reserve, the vector saved before execution, and a fresh vector afterward. In your explanation, account for why a row can be unchanged yet still appear in the report, and why another row can be absent from the report altogether. Finally, decide what owning the vector gives the caller: ownership of the components, or ownership of the values copied from them?

Hint: separate the two membership rules

The writer needs identity, reserve, and the active marker. The observer needs identity and reserve. Work out those two memberships before doing the subtraction, and remember that neither query supplies a component the entity lacks.

Full reasoning and expected result

Only A matches the writer, so the current reserves are five, seven, and seven. B still appears in the report because the observer doesn't require the marker; C appears in neither report because it lacks identity. The original vector stays [(11, 7), (12, 7)], while the fresh vector is [(11, 5), (12, 7)]. The saved vector owns copied numbers, so subsequent component changes cannot update it, and reading extra reports does not execute the decrement schedule.

If membership was uncertain, return to predicting query membership. If you expected the saved values to change, revisit a saved reading's ownership and the owned report. The final numbers are evidence for both ideas, but each difficulty needs a different explanation.

2. The observer saw 91. What would you inspect next?

In this fixture, a selected sample contains two units out of seven, while an unselected sample contains four out of five. A projection system floors the selected percentage and writes it into a display resource. The display starts at 91, and another system copies its value into a trace. After one schedule run, that trace contains 91—the old value you hoped the projection would replace.

Two installation mistakes could explain this result: the projection wasn't installed, or it ran after the observer. Choose one additional reading that would distinguish those explanations in this fixture. Predict both the final display and trace for each mistake, then for a repaired schedule. There's also a helper-only percentage test available; explain whether passing it would settle which system actually ran.

Hint: look for a write that happened too late

The earlier observation can be identical in both cases even if the final world differs. Ask whether either mistaken schedule still executes the projection after recording the trace.

Full reasoning and expected result

Read the final display. Without the projection installed, it remains 91 and the trace is [91]. With the order reversed, the projection eventually writes 28, but the earlier trace remains [91]. Correct order produces display 28 and trace [28]. The unselected sample would produce 80, giving the fixture another distinguishable outcome if the wrong membership were used.

This reasoning assumes the supplied projection works when called; it doesn't imply that all stale displays have only two causes. The worked test executes all three schedules so it can distinguish their behavior, while a percentage helper test alone cannot establish installation or order. Return to required ordering edges or writing discriminating evidence according to which part of that diagnosis you want to revisit.

3. A handle, a visible component, and a retained observation

Now the thing waiting to become visible is an entity rather than a calculated percentage. An empty world queues RowId(41) and immediately saves its entity handle. Observer A runs next, followed by an explicit ApplyDeferred, then observer B. Both observers save copied IDs. For this experiment, automatic intermediate application is disabled, while final application at the end of the schedule remains enabled.

Predict A's vector, B's vector, and whether the saved handle resolves to RowId when the schedule returns. Then remove only the explicit intermediate application point and predict all three again. If the final world contains the row in both runs, decide whether that final state could tell you what A saw earlier. Keep the application settings beside your prediction; changing them would change the experiment.

Hint: keep the experimental settings with the prediction

With automatic insertion disabled, declaring an order does not supply an intermediate application point. In the altered schedule, final application still happens, but only after both observers have finished.

Full reasoning and expected result

With the intermediate point present, A saves [], B saves [41], and the handle resolves to 41 after the schedule. Without that point, both saved vectors are empty, although the final handle still resolves to 41. Applying the command later changes what a future query can fetch; it doesn't rewrite observations the earlier systems already copied.

The reserved handle was therefore not proof of component visibility. These results depend on the stated experimental settings, rather than a general claim that chains never flush commands. Revisit explicit application points and identity versus an entity handle if the difference between reservation and observation was hard to place.

4. Can the accounting balance while the animal dies too early?

Return to the actual fieldwork library with a smaller fixture. One grazer begins with two reserve units and capacity six. It requests five upkeep units, then a meal of three from its authored contact. The patch begins with one biomass unit, has capacity four, and requests growth of four on tick one, which is lit. The installed order is upkeep, growth, meals, then starvation—the same rescue opportunity you established in fieldwork.

Predict the actual upkeep payment, accepted growth, meal transfer, ending stores, and life state. Then move starvation before meals in your imagined trace and work out the ending again. Would the total-store conservation equation necessarily expose that ordering mistake? Pause to write both outcomes, including the individual stores, before using the hint.

Hint: a requested amount is not automatically an actual flow

The reserve floor limits the payment, and the patch's remaining capacity limits growth. A meal transfers units between stores. Starvation changes which actions are still available; it doesn't create or remove patch biomass.

Full reasoning and expected result

Upkeep pays two and leaves the grazer at zero. Growth accepts three, filling the patch to four, then the meal transfers three. The grazer finishes alive at three and the patch holds one. The ledger records added three, upkeep two, eaten three, and no starvation. Ending stores of four plus payment of two equal starting stores of three plus accepted growth of three.

A starvation-first schedule can instead leave a dead grazer at zero beside four units in the patch. The same conservation equation still balances because total stores are still four. Individual reserve and life assertions are what establish that the intended rescue opportunity occurred. The worked test calls CourseWorld::step, exercising your installed systems rather than recreating their arithmetic. Revisit accepted growth, actual transfer, or the connected tick to recover the part of the trace you need.

5. Zero deaths over which interval?

An owned course report has an empty event vector, but also says its complete coverage starts strictly after tick four and extends through tick seven. Its current grazer is dead at zero reserve. Predict what starvations_between returns for four through seven, five through seven, and seven through eight. The intervals differ by only a boundary, so identify what each includes before interpreting the empty vector.

The executable fixture reaches this state with no patches, four initial reserve units, upkeep of one per tick, and history capacity zero. It executes seven ticks. Trace when the animal dies and what happens to records produced then. How can a journal that retains no events still establish zero new deaths for a later interval?

Hint: retained contents and collected coverage answer different questions

Events were lost through tick four. Ticks five, six, and seven were executed without another terminal transition, while tick eight has not yet been collected. The report can use those facts even when it can't supply the earlier event records.

Full reasoning and expected result

The answers are None, Some(0), and None. Four upkeep records and one starvation were evicted, making five lost events. The last loss happened in tick four; later empty ticks advanced the collected boundary without producing another death. Thus coverage excludes the death tick but includes the completed interval from five through seven.

Dead state describes a present condition, not the missing interval's event count. The test's known starting state lets us explain how this particular history arose, but an empty report alone cannot recover it. Return to unknown versus zero and coverage boundaries if those answers were difficult to distinguish. Replacing an absent answer with zero would hide exactly the uncertainty this report preserves.

6. The chosen patch is already empty

For this case, return to the isolated target lab; the shared-meadow checkpoint itself uses fixed contacts. At observation time, an actor at zero, zero sees ID 17 at one, zero and ID 12 at zero, one. Both patches have two biomass units and lie within radius two. The selection policy compares Manhattan distance first, then stable ID when distances tie.

Predict which patch it chooses. Before acting, the actor reaches that patch, but another completed meal empties it. The saved reading still says two units, and ID 17 remains visible with food. Decide what this action's resolver may do, then change the fixture again: what if the chosen patch has disappeared entirely? In each case, distinguish evidence that the earlier choice was reasonable from permission to take a meal now.

Hint: distinguish choosing again from validating this action

The tie rule chooses one identity. The resolver revalidates that identity against current state; a failure does not silently invoke another selection policy or establish contact with a different patch.

Full reasoning and expected result

ID 12 wins the equal-distance tie. Its currently empty state rejects the bite without reserve gain, even though the saved observation remains two. Removing ID 12 instead produces a missing-target rejection. Neither outcome authorizes a fallback meal at ID 17, and food remaining at the selected patch would still require current contact before transfer.

Those answers follow the target lab's declared rules; the lab does not by itself prove that movement or another consumer actually ran. Its existing tests supply the executable evidence for selection and revalidation, so the file below doesn't duplicate the selector. Return to the tie rule, action-time revalidation, and rejection without partial mutation to connect a failed choice with the state it must leave unchanged.

Complete worked file: tests/returns.rs

//! Worked checks for “Return with a different question.”
//! Save this whole file as work/fieldwork/tests/returns.rs, preserving any
//! investigation.rs already there. This is an integration test, not a rustc lab.
//! From the Moss repository root:
//! cargo +1.93.1 test --offline --locked --manifest-path work/fieldwork/Cargo.toml --test returns
//! python3 learning/scripts/fieldwork.py check --project work/fieldwork
//!
//! Cases 1–3 use separate, nonbiological Bevy worlds. Cases 4–5 execute the
//! actual persistent course library. Case 6 returns to the existing target lab.

mod membership {
    use bevy_ecs::{prelude::*, schedule::ExecutorKind};

    #[derive(Component)]
    struct Identity(u32);
    #[derive(Component)]
    struct Reserve(u32);
    #[derive(Component)]
    struct Active;

    fn decrement(mut rows: Query<(&Identity, &mut Reserve), With<Active>>) {
        for (_, mut reserve) in &mut rows {
            reserve.0 = reserve.0.checked_sub(1).expect("fixture has enough units");
        }
    }

    fn report(world: &mut World) -> Vec<(u32, u32)> {
        let mut query = world.query::<(&Identity, &Reserve)>();
        let mut rows: Vec<_> = query
            .iter(world)
            .map(|(id, reserve)| (id.0, reserve.0))
            .collect();
        rows.sort_by_key(|(id, _)| *id);
        rows
    }

    #[test]
    fn case_1_required_components_and_owned_readings_answer_different_questions() {
        let mut world = World::new();
        let a = world.spawn((Identity(11), Reserve(7), Active)).id();
        let b = world.spawn((Identity(12), Reserve(7))).id();
        let unnamed = world.spawn((Reserve(7), Active)).id();
        let saved = report(&mut world);
        let mut schedule = Schedule::default();
        schedule.set_executor_kind(ExecutorKind::SingleThreaded);
        schedule.add_systems(decrement);
        for _ in 0..2 {
            let _ = report(&mut world); // Reading does not run the schedule.
            schedule.run(&mut world);
            let _ = report(&mut world);
        }
        assert_eq!(world.get::<Reserve>(a).unwrap().0, 5);
        assert_eq!(world.get::<Reserve>(b).unwrap().0, 7);
        assert_eq!(world.get::<Reserve>(unnamed).unwrap().0, 7);
        assert_eq!(saved, vec![(11, 7), (12, 7)]);
        assert_eq!(report(&mut world), vec![(11, 5), (12, 7)]);
    }
}

mod projection {
    use bevy_ecs::{prelude::*, schedule::ExecutorKind};

    #[derive(Component)]
    struct Chosen;
    #[derive(Component)]
    struct Sample {
        used: u32,
        capacity: u32,
    }
    #[derive(Resource)]
    struct Display(Option<u32>);
    #[derive(Resource, Default)]
    struct Trace(Vec<Option<u32>>);

    fn project(rows: Query<&Sample, With<Chosen>>, mut display: ResMut<Display>) {
        display.0 = rows.single().ok().and_then(|sample| {
            (sample.capacity != 0).then(|| {
                (u64::from(sample.used.min(sample.capacity)) * 100 / u64::from(sample.capacity))
                    as u32
            })
        });
    }

    fn observe(display: Res<Display>, mut trace: ResMut<Trace>) {
        trace.0.push(display.0);
    }

    enum Order {
        Missing,
        Reversed,
        Correct,
    }

    fn run(order: Order) -> (Option<u32>, Vec<Option<u32>>) {
        let mut world = World::new();
        world.spawn((
            Sample {
                used: 2,
                capacity: 7,
            },
            Chosen,
        ));
        world.spawn(Sample {
            used: 4,
            capacity: 5,
        });
        world.insert_resource(Display(Some(91)));
        world.init_resource::<Trace>();
        let mut schedule = Schedule::default();
        schedule.set_executor_kind(ExecutorKind::SingleThreaded);
        match order {
            Order::Missing => {
                schedule.add_systems(observe);
            }
            Order::Reversed => {
                schedule.add_systems((observe, project).chain());
            }
            Order::Correct => {
                schedule.add_systems((project, observe).chain());
            }
        }
        schedule.run(&mut world);
        (
            world.resource::<Display>().0,
            world.resource::<Trace>().0.clone(),
        )
    }

    #[test]
    fn case_2_final_display_separates_missing_installation_from_wrong_order() {
        assert_eq!(run(Order::Missing), (Some(91), vec![Some(91)]));
        assert_eq!(run(Order::Reversed), (Some(28), vec![Some(91)]));
        assert_eq!(run(Order::Correct), (Some(28), vec![Some(28)]));
    }
}

mod deferred {
    use bevy_ecs::{
        prelude::*,
        schedule::{ExecutorKind, ScheduleBuildSettings},
    };

    #[derive(Component)]
    struct RowId(u32);
    #[derive(Resource, Default)]
    struct Reserved(Vec<Entity>);
    #[derive(Resource, Default)]
    struct Seen {
        before: Vec<u32>,
        after: Vec<u32>,
    }

    fn enqueue(mut commands: Commands, mut reserved: ResMut<Reserved>) {
        reserved.0.push(commands.spawn(RowId(41)).id());
    }

    fn before(rows: Query<&RowId>, mut seen: ResMut<Seen>) {
        seen.before = rows.iter().map(|row| row.0).collect();
        seen.before.sort();
    }

    fn after(rows: Query<&RowId>, mut seen: ResMut<Seen>) {
        seen.after = rows.iter().map(|row| row.0).collect();
        seen.after.sort();
    }

    fn run(intermediate_application: bool) -> (Vec<u32>, Vec<u32>, u32) {
        let mut world = World::new();
        world.init_resource::<Reserved>();
        world.init_resource::<Seen>();
        let mut schedule = Schedule::default();
        schedule.set_executor_kind(ExecutorKind::SingleThreaded);
        schedule.set_build_settings(ScheduleBuildSettings {
            auto_insert_apply_deferred: false,
            ..Default::default()
        });
        schedule.set_apply_final_deferred(true);
        if intermediate_application {
            schedule.add_systems((enqueue, before, ApplyDeferred, after).chain());
        } else {
            schedule.add_systems((enqueue, before, after).chain());
        }
        schedule.run(&mut world);
        let saved = world.resource::<Seen>();
        let handle = world.resource::<Reserved>().0[0];
        (
            saved.before.clone(),
            saved.after.clone(),
            world.get::<RowId>(handle).unwrap().0,
        )
    }

    #[test]
    fn case_3_final_existence_does_not_rewrite_an_earlier_observation() {
        assert_eq!(run(true), (vec![], vec![41], 41));
        assert_eq!(run(false), (vec![], vec![], 41));
    }
}

use moss_course_ecosystem::{
    CourseWorld, Daylight, GrazerSeed, Life, PatchSeed, Scenario, SimId, TickLedger,
};

#[test]
fn case_4_actual_course_tick_caps_growth_and_rescues_after_actual_upkeep() {
    let mut world = CourseWorld::new(Scenario {
        daylight: Daylight::new(4, 2).unwrap(),
        grazers: vec![GrazerSeed {
            id: SimId(8),
            reserve_units: 2,
            capacity_units: 6,
            maintenance_units_per_tick: 5,
            meal_units_per_tick: 3,
            feeding_site: Some(SimId(80)),
        }],
        patches: vec![PatchSeed {
            id: SimId(80),
            biomass_units: 1,
            capacity_units: 4,
            growth_units_per_lit_tick: 4,
        }],
        history_limit: 32,
    })
    .unwrap();
    let before = world.snapshot();
    assert_eq!(before.tick, 0);
    world.step();
    let after = world.snapshot();
    assert_eq!(after.tick, 1);
    assert_eq!(
        (after.grazers[0].reserve_units, after.grazers[0].life),
        (3, Life::Alive)
    );
    assert_eq!(after.patches[0].biomass_units, 1);
    assert_eq!(
        after.ledger,
        TickLedger {
            added_units: 3,
            maintenance_units: 2,
            eaten_units: 3,
            starvations: 0,
        }
    );
    let before_stores =
        u64::from(before.grazers[0].reserve_units) + u64::from(before.patches[0].biomass_units);
    let after_stores =
        u64::from(after.grazers[0].reserve_units) + u64::from(after.patches[0].biomass_units);
    assert_eq!(
        after_stores + after.ledger.maintenance_units,
        before_stores + after.ledger.added_units
    );
    assert_eq!(after.history.starvations_between(1, 1), Some(0));
}

#[test]
fn case_5_evicted_death_and_collected_empty_ticks_have_different_evidence() {
    let mut world = CourseWorld::new(Scenario {
        daylight: Daylight::new(4, 0).unwrap(),
        grazers: vec![GrazerSeed {
            id: SimId(9),
            reserve_units: 4,
            capacity_units: 4,
            maintenance_units_per_tick: 1,
            meal_units_per_tick: 0,
            feeding_site: None,
        }],
        patches: vec![],
        history_limit: 0,
    })
    .unwrap();
    for _ in 0..7 {
        world.step();
    }
    let state = world.snapshot();
    assert_eq!(state.grazers[0].life, Life::Dead);
    assert_eq!(state.grazers[0].reserve_units, 0);
    assert!(state.history.events.is_empty());
    assert_eq!(state.history.evicted_events, 5);
    assert_eq!(
        (
            state.history.complete_after_tick,
            state.history.collected_through_tick
        ),
        (4, 7)
    );
    assert_eq!(state.history.starvations_between(4, 7), None);
    assert_eq!(state.history.starvations_between(5, 7), Some(0));
    assert_eq!(state.history.starvations_between(7, 8), None);
}
