A patch in sight is not a meal

Two grazers spot a patch with two units of food and head towards it. They both arrive, but only the first gets a meal. When you inspect the second grazer, its local observation still says the patch holds two units. That looks like a contradiction until you ask when the observation was made. The grazer saw real food before either animal moved; another grazer ate it before its turn to feed. We'll build that sequence into the population world, keeping enough evidence to explain how a sensible choice can end in an empty meal.

Third cumulative course arc, checkpoint A. This guide extends your saved population project. Its daylight, finite meals, birth, maturity, inherited upkeep, and starvation continue under the same authored course rules. The new work stays separate from the live movement exercise in NOW.md; fatigue, rest, and hunting follow in later checkpoints.

Continue the world whose costs you can explain

In the population project, a feeding-site ID was enough to connect a grazer to a patch. Once animals can move, that connection needs an explanation: the grazer has to discover the patch and reach it. We can add those steps while keeping the existing rules for paying upkeep, transferring food, and funding a child. Choose what a cell means before drawing it

For the smallest journey, put a grazer at cell zero and its food at cell two. We need to know where the grazer is now, how far it can see, and how far it can afford to move. We'll also need to remember where it saw the food, because the observation and the eventual meal happen at different points in the tick. Sketch those values before choosing their types. Some will be components that systems update, some will describe the starting world, and some will be copied into a report so you can inspect what happened.

The simulation uses Cell { x, y } rather than screen coordinates, so a browser can draw the same world at any size. Each coordinate is an unsigned integer starting at zero, and GridBounds gives the positive width and height it must stay below. For these grid journeys, distance is the horizontal separation plus the vertical separation, usually called Manhattan distance. Be careful when calculating it: subtracting a larger unsigned coordinate from a smaller one doesn't produce their separation. Take each absolute difference, widen it, and then add, so cells near the integer limit still have a valid distance.

Representation hint

A private Position component can wrap the cell shared by grazers and patches. A grazer also needs Motion, which names its sensing radius, maximum cells per tick, and travel units per cell. The reference keeps that motion together with copied local readings, a selected target, and tick markers in MobileActor. A patch has a place in the world without carrying all of a traveller's state.

Complete configuration answer

The configuration module supplies GrazerPlacement, PatchPlacement, SpatialConfig, and MobileScenario::new(scenario, population, space). Each authored entity needs exactly one placement within the bounds. Grazers may share a cell, while distinct patch cells make a contact identify one patch location. Require a positive travel cost so affordability has a meaningful divisor, but allow zero speed for a stationary grazer and zero sensing radius for a same-cell view. Apply the motion checks to the newborn template too, since future children will use it.

There is one old input that would undermine this design. A seed with a feeding-site ID already has permission to use that patch under the fixed-contact rules, even if you now place the grazer across the map. Mobile seeds therefore start with feeding_site: None, and validation rejects a conflicting seed by ID. Calling CourseWorld::new_mobile selects this spatial contract. The first-arc and fixed-contact population constructors keep their original meaning, so giving an animal a position doesn't silently change what an older lesson does.

Keep reset failures atomic

Validate the complete mobile specification before installing any part of it. If reset_with_mobile finds an out-of-bounds placement, both the current world and the configuration used by a later reset() must remain unchanged. A successful reset starts the selected mode under a new run ID with targets and observations cleared. The existing reset_with and reset_with_population operations still select first-arc and fixed-contact population mode respectively.

Write the whole observation system

A position lets us answer where an animal is, but it doesn't say what the animal knows. The browser's inspector can show every patch; giving that table to the choice system would let a grazer pursue food outside its sensing range. Instead, we'll give each grazer a small record of what it could see from its own cell. Implement that record-building phase as observe in src/mobile/perception.rs, with a complete system signature and body.

The phase runs after upkeep and patch growth, while every grazer is still at its position from the previous tick. For each living grazer whose first action is due, read its position and sensing radius, then copy the patches within that Manhattan distance into its local readings. Include an empty patch if it's visible: seeing that a patch is empty is still useful information, even though the next phase won't choose it as food. Sorting those copies by stable patch ID keeps the resulting report reproducible when entity installation order changes.

The copy is the important Rust step here. Each PatchObservation owns a patch ID, a cell, and a biomass value; it holds no reference into the patch query. When observe finishes, its query access can end, and later systems are free to move animals or change patch biomass. The choice system will still have a readable account of the earlier moment. That account can become stale, which is exactly what we need to represent in the two-grazer example. Trying to keep a borrow of the live patch instead would blur the difference between what was seen and what exists now.

For this small world, the observation system can scan every patch and copy only the local ones. The selector receives that filtered vector, with no global inspector table or unrestricted world reference. A spatial index could make the scan cheaper later; it would still need to preserve this boundary between finding nearby entities and deciding what an animal is allowed to know.

Once the grazer moves, a single coordinate in the report is no longer enough to explain its view. In the first tick of our short journey, it looks from cell zero, travels to cell one, and still intends to reach the patch at cell two. MobileGrazerReading.observed_cell preserves the first of those positions, its current cell gives the second, and PatchTarget.observed_cell will hold the third. Keep the observation tick as well. An absent observation means the grazer hasn't collected one; an observation with an empty vector means it looked and saw no patch.

You now have enough information to write the system: it reads the clock and the two kinds of entity, then replaces each eligible grazer's copied view. Observation hint 1: list reads and writes

The clock supplies the tick. Patches supply their identities, positions and biomass; grazers supply their positions and life/first-action state. The only component you need to mutate is MobileActor, where you replace the local readings and record the observation's origin and tick. Nothing in this phase spends reserve or moves an entity.

Observation hint 2: a query shape

Complete observation and choice answer

The complete perception module includes both systems with their imports, eligibility checks, stable ordering, target-change accounting, and journal writes. Begin your comparison with the system signature: it needs to update the actor's stored view, but it can do that while borrowing the actor's position through a shared reference.

It's tempting to request mutable access to everything associated with the grazer, but that would ask Bevy for more access than observation needs. Consider changing only the grazer's position fetch to &mut Position while the patch query still uses &Position. The two queries then claim incompatible access if they can match the same entity. Although we think of grazers and patches as different kinds of inhabitant, requiring Grazer in one query and Patch in the other doesn't prove an entity cannot have both components.

Choose an opportunity without reserving it

With a local view in place, choosing food becomes a smaller problem: which of these observations should the grazer follow? Write your rule in words before translating it into query code. In this checkpoint, the grazer continues towards its previous target while that patch appears in the current tick's view with positive biomass. If the target no longer qualifies, it chooses the nearest visible nonempty patch, using stable ID to break an equal-distance tie. When no candidate remains, it clears the target and stays put. The model doesn't give it a global fallback or a random search step.

The chosen PatchTarget needs an ID, an observed cell, and an observed tick. The ID lets a later action look up the same patch, while the cell gives movement its destination. The tick tells us whether this choice came from the view just collected. Without that last check, a remembered target could keep guiding the grazer after it had left sensing range. A grazer can refresh its observation of the same patch on successive ticks without recording a change of target ID.

Choice reasoning: when a nearer patch appears

Suppose the grazer is already heading towards a visible, nonempty patch when a nearer one grows fresh food. Under this continuation policy, it keeps its existing target; “nearest” governs the moment it needs a new choice. If the old patch empties or disappears from the current view, it compares the remaining candidates by distance and ID. Keeping retention and replacement explicit prevents query iteration order from accidentally deciding the policy.

At this point the grazer has committed only to a destination. Choosing a patch hasn't locked any biomass or added any food to its reserve, so another grazer can make the same choice. This is the distinction behind action-time revalidation: an intention gives an action something to attempt, and the action must still discover whether it can succeed. Before we can attempt the meal, though, we need to get there.

Pay for the route that actually happens

Our grazer at cell zero knows about food at cell two, but knowing the destination doesn't pay for the journey. Movement follows the target's observed cell, taking horizontal steps before vertical ones. It may reject an ID that no longer identifies a patch, but it must keep using the destination the grazer actually observed. Patches are stationary here, so the distinction won't change this route; it will matter when an opportunity can move between observation and action.

Suppose a grazer could travel three cells this tick, has five reserve units left after upkeep, and pays two units per cell. It can complete two cells for four units, leaving one in reserve. A possible meal at the destination can't fund the third step, because that meal hasn't happened yet. Integer division of reserve by the positive per-cell cost gives the number of whole steps it can afford.

Affordability is only one limit. The grazer must also stop when it reaches its destination or uses its maximum cells for the tick, so the accepted distance is the smallest of those three bounds. Calculate that distance, the resulting cell, and the actual cost before mutating the entity. If there is no target, its speed is zero, it has already arrived, or it can't afford the first cell, the accepted journey costs nothing.

Implement those bounds in src/mobile/movement.rs, then record the cells actually travelled and the units actually paid. The complete movement module shows both the arithmetic and the ECS adapter. Compare how it calculates a result before committing that result to position, reserve, and accounting.

Travel answer: stop at arrival rather than spending the full allowance

If the destination is one cell away, an allowance of four still permits only one useful step. Once you've bounded the total distance, take as much of it as needed along x and use the remainder along y; neither coordinate should pass its destination. Check the ledger and history arithmetic before committing the resulting position and reserve, so an accounting failure can't leave a partially recorded journey.

The movement system also needs to recognize an opportunity it has already processed. last_travel_tick records that evaluation even when the accepted distance was zero, so a second invocation can't take another turn in the same tick. When you're investigating actual movement, use the Travelled events instead: those record journeys with a nonzero distance.

It pays one unit of upkeep each tick, can see three cells, and can travel one cell for one unit. Its meal request is two. Patch 100 at (2,0) holds three units and doesn't grow. Arrive, then check the meal against the current world

Reaching the destination gives feeding a new fact to check: the grazer and its selected patch now occupy the same cell. Derive contact from those current positions and the selected patch ID. A patch can appear in the inspector or lie within sensing range while still being several cells away, so neither observation establishes contact. The meal phase then checks the contact again alongside current biomass, reserve room, and demand before using the existing immediate transfer between the two stores.

This brings us back to the two grazers at the beginning. They can both observe two food units and both pay to reach the patch, because neither action reserves a meal. Feeding resolves grazer one first by stable ID, immediately transferring those units out of the patch. When grazer two's turn arrives, its copied view still contains two, but the current patch contains zero. It gets no meal. Follow the diagram from top to bottom and notice that nothing edits the old observation to make it agree with the later world; those two records describe different moments.

The unsuccessful grazer gets another observation and choice on the next executed tick. It doesn't respond to the failed meal by choosing again inside the feeding system, which would give it an extra decision after seeing the first grazer's outcome.

Write a test that makes the stale claim real

Let's turn that sequence into an investigation in tests/mobile_investigation.rs, alongside your existing tests. Give both grazers a starting cell of (0,0), reserve four, upkeep one, speed one, travel cost one, sensing radius one, and meal request two. Put patch 100 at (1,0) with two units. Then add patch 101 at (2,0) with five units, and give neither patch any growth. That second patch matters: you can see it in the global inspector, but the grazers can't see it from their starting cell. It lets the test distinguish a legitimate later choice from a hidden same-tick fallback.

Predict the first two ticks before opening the complete test. On tick one, each grazer pays upkeep and travel, reaching patch 100 with two reserve units. ID one eats its two units and finishes at four; ID two remains at two. Patch 101 must still hold five, because neither grazer observed it when making that tick's choice.

On tick two, both grazer positions have changed, so their next observations can include patch 101. They can now choose it, travel there, and take two units each. The patch falls from five units to one, while the grazers again finish at reserves four and two. This time the repeated ending balances conceal a change of destination. Your assertions need to identify where the meals came from as well as how much each grazer ate.

Investigation hint 1: inspect observation and state separately

After tick one, both copied local readings should still show patch 100 with biomass two, even though the authoritative patch has reached zero. Neither reading should include patch 101. Asserting all three facts establishes that the grazers chose from their earlier local views, rather than secretly consulting the inspector's current global information.

Investigation hint 2: challenge same-tick fallback

A total for eaten units won't tell you which patch supplied them. Assert target ID, cell, reserve, and both patch stores so a meal from the wrong patch can't hide behind the right total. Then assert the legitimate choice of patch 101 on tick two: the rule forbids using unseen food during the first action, rather than forbidding that patch forever.

Complete learner test: tests/mobile_investigation.rs

This is a full integration-test file for your continuing project. It uses the public world and its installed schedule; it does not implement a second choice or feeding algorithm. The mobile-stage command below runs this file with your earlier tests.

use moss_course_ecosystem::{
    Cell, CourseWorld, Daylight, FounderTrait, GrazerPlacement, GrazerSeed,
    GridBounds, MobileScenario, Motion, PatchPlacement, PatchSeed,
    PopulationConfig, Scenario, SimId, SpatialConfig, UpkeepTrait,
};

#[test]
fn stale_local_claim_cannot_take_a_second_meal_or_skip_to_unseen_food() {
    let motion = Motion {
        sensing_radius: 1,
        max_cells_per_tick: 1,
        travel_units_per_cell: 1,
    };
    let scenario = Scenario {
        daylight: Daylight::new(1, 0).unwrap(),
        grazers: [1, 2].into_iter().map(|id| GrazerSeed {
            id: SimId(id), reserve_units: 4, capacity_units: 8,
            maintenance_units_per_tick: 1, meal_units_per_tick: 2,
            feeding_site: None,
        }).collect(),
        patches: [(100, 2), (101, 5)].into_iter().map(|(id, units)| PatchSeed {
            id: SimId(id), biomass_units: units, capacity_units: 8,
            growth_units_per_lit_tick: 0,
        }).collect(),
        history_limit: 128,
    };
    let mut population = PopulationConfig::new([1, 2].into_iter().map(|id| FounderTrait {
        id: SimId(id), upkeep: UpkeepTrait::new(1).unwrap(),
    }).collect());
    population.max_living = 2;
    let space = SpatialConfig {
        bounds: GridBounds { width_cells: 3, height_cells: 1 },
        grazers: [1, 2].into_iter().map(|id| GrazerPlacement {
            id: SimId(id), cell: Cell { x: 0, y: 0 }, motion,
        }).collect(),
        patches: vec![
            PatchPlacement { id: SimId(100), cell: Cell { x: 1, y: 0 } },
            PatchPlacement { id: SimId(101), cell: Cell { x: 2, y: 0 } },
        ],
        newborn_motion: motion,
    };
    let mut world = CourseWorld::new_mobile(MobileScenario::new(scenario, population, space)).unwrap();
    world.step();
    let first = world.mobile_snapshot().unwrap();
    assert_eq!(first.tick, 1);
    assert_eq!(first.base.grazers.iter().map(|g| g.reserve_units).collect::<Vec<_>>(), vec![4, 2]);
    assert_eq!(first.base.patches.iter().map(|p| p.biomass_units).collect::<Vec<_>>(), vec![0, 5]);
    assert_eq!((first.ledger.travel_cells, first.ledger.travel_units), (2, 2));
    assert_eq!(first.base.ledger.eaten_units, 2);
    for grazer in &first.grazers {
        assert_eq!(grazer.cell, Cell { x: 1, y: 0 });
        let target = grazer.target.unwrap();
        assert_eq!((target.patch, target.observed_tick), (SimId(100), 1));
        assert_eq!(grazer.visible_patches.len(), 1);
        assert_eq!(grazer.visible_patches[0].patch, SimId(100));
        assert_eq!(grazer.visible_patches[0].biomass_units, 2);
    }
    world.step();
    let second = world.mobile_snapshot().unwrap();
    assert_eq!(second.tick, 2);
    assert_eq!(second.base.grazers.iter().map(|g| g.reserve_units).collect::<Vec<_>>(), vec![4, 2]);
    assert_eq!(second.base.patches.iter().map(|p| p.biomass_units).collect::<Vec<_>>(), vec![0, 1]);
    assert_eq!(second.base.ledger.eaten_units, 4);
    assert_eq!(second.population.totals.births, 0);
    for grazer in &second.grazers {
        assert_eq!(grazer.cell, Cell { x: 2, y: 0 });
        let target = grazer.target.unwrap();
        assert_eq!((target.patch, target.observed_tick), (SimId(101), 2));
    }
}

Give the newborn a place in the same world

Founders aren't the only grazers that will inhabit this world. As soon as the existing population rule produces a child, observation and movement will expect that child to have a position too. Extend the birth transaction to require both parents at an actual shared patch cell after their actions. The patch can be empty and still provide that meeting place. Once the transaction has found it, check the child's placement and the history's eviction-counter arithmetic alongside the payment, ID, deadlines, and origin that birth already prepares. A full journal can evict its oldest event; it does not by itself make a birth invalid.

Queue the child's position together with its other components, using the configured newborn motion. It keeps its inherited upkeep and becomes eligible to act at birth tick plus one, but starts without a target, local readings, or a prior travel tick. Copying a parent's target would claim the child had already made an observation. Adding its position in a later phase would create a different problem: other systems could see a newborn before it had the components their mobile queries require. Installing the complete bundle gives the child a place immediately while still preserving its first-action delay.

Newborn answer and test boundary

The full reproduction module shows the additional preflight and the complete queued bundle. After the birth flush, you should be able to find the placed child in public mobile readings. A deliberately late invocation of observation, travel, or meals in the same tick must still leave that child inactive. Check events and flows as well as its ending reserve, because an illegal expense and an illegal gain could cancel in the balance.

Install the phases and account for the journey

The systems now describe a journey, but their order determines which version of the world each one sees. Start the tick and clear its ledgers, then mature eligible children, pay upkeep, and grow patches. Observe all actors before any of them chooses or travels. After travel, derive contact and resolve meals, then starvation and births. Apply the queued children, clean up dead rows, apply those removals, and only then mark the histories complete. Follow that order in the complete schedule, explaining what each phase needs from the one before it.

In particular, keep observation out of the movement loop. If you observe one grazer, move it, and then observe the next, the two grazers no longer make their decisions from the same moment. Separating those phases is what makes the copied readings a coherent account of the world before travel.

Travel also changes the explanation for missing energy. The units paid for movement leave the measured stores, just as upkeep and birth costs do. To check a tick, add ending grazer reserves and patch biomass to actual upkeep, actual travel payment, and dissipated birth cost; that should equal starting stores plus accepted growth. Meals and birth contributions move units between stores, so they don't add another loss. Use MobileSnapshot for this accounting: it includes the base and population reports along with the travel costs that the older snapshot cannot show.

To explain how a particular journey led to a meal, you need more than a correct total. Target changes, accepted travel, and newborn placements go into a third bounded journal. Their events have to cover the same interval as the resource events you're comparing, and a birth may bring the population journal into the explanation too. Use the intersection of those coverage intervals. The current target tells you what a grazer intends now; it can't recover the route from an event that has been evicted. Lifetime travel totals remain useful even when that detailed explanation is no longer available.
