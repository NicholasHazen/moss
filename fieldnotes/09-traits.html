A trait is a promise you can use

Two readings both say “Fern,” but one has ID 2 and the other has ID 10. Another pair both refer to ID 10, yet their reserves differ because they were collected at different moments. Before asking Rust whether those values are equal, we have to decide what we're comparing.

Isolated identity and reporting lab. This continues canonical reports and reuses a private representation with a public constructor. Complete one small generic helper. The ID type is a teaching type, not a replacement for Moss's existing IDs or a new live identity allocator.

Order identities without taking their readings

Our practical destination is a helper that turns IDs 10, 2, 10 into 2, 10 while leaving the caller's readings available. To choose its trait bounds sensibly, we'll first distinguish equality of identities from equality of whole observations, then connect copying and ordering to the operations the helper performs. Compiler experiments with the owned nickname will show why a capability suitable for the ID need not suit the reading around it.

Make the identity contract smaller than the reading

The report in the preceding lesson used integers as IDs. An integer can also describe an energy amount or a tick count, so a function accepting a plain number doesn't tell us which meaning belongs there. Wrapping one u64 in StableId gives identity a distinct type. Its module keeps the field private and provides a constructor that rejects zero, making that rule part of how callers obtain a valid ID.

Zero is rejected because this lab explicitly chose that rule, not because an identity type or a derive automatically requires it. The constructor returns a Result, and the private field directs ordinary external callers through that constructor. The live simulation has its own ID rules; this small type lets us study the relationship between validation and traits without replacing that allocator.

A Reading holds more than an identity: it contains the ID, an owned nickname, and an optional reserve. Derived equality compares all of those fields. If a later observation records a different reserve, it should differ from the earlier reading even when both describe the same individual. Comparing only their ID fields asks the narrower question of whether they name that same individual.

That distinction resolves the opening pairs. Two Fern nicknames don't turn IDs 2 and 10 into the same ID, while equal IDs don't make two different observations equal. We can retain an application's stable identity long after collecting a reading. Discovering whether that identity still resolves to a living entity requires another operation against the current world.

Read each derive as a capability

To make those comparisons available, a type needs the appropriate trait implementations. PartialEq supplies == and !=; Eq adds the full equality contract, including the promise that a value equals itself. An integer-backed ID can meet that promise. A floating-point value illustrates why Rust distinguishes the traits: NaN does not equal itself, so a familiar-looking numeric value doesn't necessarily support the same equality contract.

Our report also needs a predictable order. PartialOrd permits comparisons that may find no ordering for a pair, while Ord promises a total order. Deriving these traits compares a struct's fields in declaration order. StableId has one integer field, so its derived order puts 2 before 10, as the report expects. Sorting formatted strings would put “10” before “2” instead; that would order their written representation rather than their numeric identities.

When one of those assertions fails, we want the diagnostic to show the values involved. Debug makes programmer-facing formatting such as {:?} available, and deriving it saves us from writing that inspection code by hand. Its output is helpful in a test failure, but an exported file would need its own defined schema rather than depending on derived debug text staying unchanged.

The ID list also needs values it can keep after the input borrow ends. Clone provides an explicit duplication operation, while Copy allows implicit copying where an assignment would otherwise move ownership. A Copy type must also implement Clone. Our one-integer identity can derive both, letting a caller copy the ID without transferring ownership of the reading that contains it. These traits describe ownership behavior; they don't promise that every operation involving the type is free.

The Ord reference, PartialEq reference, and Debug reference are useful when checking one of these contracts. Read the required relationship first, then the derive behavior. The macro saves repetitive implementations; it does not remove their meaning.

Borrow the readings and copy the identities

Now put those capabilities to work. A report helper can borrow a slice of readings and extract their small IDs into a new vector, leaving all the owned nicknames in place. Each output element is a copied StableId, so the list can outlive the borrowed slice. We get an independent list of identities without cloning all the text or moving the readings away from their owner.

Suppose the extracted list is 10, 2, 10 and the caller wants each ID once, in numeric order. Sorting and removing repeated values don't require any knowledge of creatures, so we'll write ordered_unique<T: Ord + Copy>. The caller chooses a concrete T; the bounds promise that its values can be copied and totally ordered. That is enough for the same helper to process stable IDs or a short list of signed integers.

The bounds are also the agreement under which Rust checks the generic function body. It can use copying and ordering because every accepted caller must provide those capabilities. If a call fails with an unsatisfied-bound diagnostic, consider the operation you intended before adding more derives. A function that only needs a list of IDs may be asking too much if you hand it complete readings instead.

To preserve the caller's original order, start by copying the borrowed slice into a vector with to_vec(). Sort that owned vector, then call dedup() to remove consecutive equal values. The order of those operations matters: on 10, 2, 10, deduplication alone doesn't bring the two tens together. Sorting first turns the sequence into 2, 10, 10, from which deduplication can produce 2, 10.

Complete one helper and keep the inputs usable

Try that implementation in a fresh practice file. Only ordered_unique is unfinished, so the initial check should compile and then reach its todo!. The result must leave the caller's source slice unchanged. It should also handle an empty slice naturally by returning an empty vector, without inventing a special identity to fill the space.

Hint 1: own a result before changing its order

The input is borrowed. Build a vector using values.to_vec() and bind it mutably. Sorting that owned vector changes the result you will return, while leaving the caller's sequence untouched.

Hint 2: equal values need to meet before deduplication

Call sort() before dedup(). Return the vector. The trait bounds let the compiler verify those operations for every type accepted by this helper.

mod identity {
    #[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord)]
    pub struct StableId(u64);

    #[derive(Debug, PartialEq, Eq)]
    pub struct InvalidId;

    impl StableId {
        pub fn new(value: u64) -> Result<Self, InvalidId> {
            if value == 0 { Err(InvalidId) } else { Ok(Self(value)) }
        }
        pub fn value(self) -> u64 { self.0 }
    }
}

pub use identity::{InvalidId, StableId};

struct Reading { id: StableId, name: String, reserve: Option<u32> }

fn ids_of(readings: &[Reading]) -> Vec<StableId> {
    let ids: Vec<_> = readings.iter().map(|reading| reading.id).collect();
    ordered_unique(&ids)
}

fn main() {
    let fern = Reading {
        id: StableId::new(10).unwrap(), name: "Fern".into(), reserve: Some(57),
    };
    let mut renamed = fern.clone();
    renamed.name.push_str(" the hare");
    println!("same ID: {}", fern.id == renamed.id);
    println!("same reading: {}", fern == renamed);
    let ids = ordered_unique(&[fern.id, StableId::new(2).unwrap(), fern.id]);
    println!("IDs: {:?}", ids.iter().map(|id| id.value()).collect::<Vec<_>>());
    assert_eq!(ids_of(&[fern, renamed]).len(), 1);
}

struct Reading { id: StableId, name: String, reserve: Option<u32> }

fn ordered_unique<T: Ord + Copy>(values: &[T]) -> Vec<T> {
    let mut result = values.to_vec();
    result.sort();
    result.dedup();
    result
}

Owned text changes the copying decision

The complete Reading makes a different ownership choice from its ID. It derives Clone but omits Copy because its String owns text storage. Cloning the reading clones that string too. The test then appends to one clone and checks that the original still says “Fern,” demonstrating the independence this particular reporting type needs.

That independence comes from the fields' clone implementations, so don't generalize it into a promise that every clone duplicates all underlying data. Later, a shared-ownership type can clone a handle while keeping the data shared. Here, deriving clone field by field for a struct containing String gives the new reading its own text, which is the behavior the test observes.

You can see the difference by adding Copy to the derive on Reading as an intentional compiler experiment. The expected E0204 error identifies a field that can't meet the copying contract. Remove the derive afterwards and connect the error back to the owned string: implicitly copying its owner would not be the operation that String provides. The repair is to keep the intended ownership behavior, not to hide the field behind an arbitrary pointer.

For a second diagnostic, pass a slice of Reading to ordered_unique. The helper asks for copying and ordering that a reading doesn't offer. Adding every suggested derive would choose a new meaning for whole observations, including an order based on field sequence. If your question is which individuals appear in the report, extracting and ordering IDs expresses it more accurately.

The Copy and Clone references explain these distinctions. A diagnostic's suggested operation is useful evidence, but the correct repair depends on whether the caller needs ownership, a borrow, a copyable identity, or an independent snapshot.

A derive supplies integration, not a world rule

Traits connect ordinary Rust types to Bevy too. The earlier ECS lesson used #[derive(Component)] and #[derive(Resource)] to supply implementations Bevy requires for those roles. Naming a struct Energy doesn't register it as a component; deriving Component supplies that capability. Neither the name nor the derive, however, schedules an upkeep system.

For upkeep to affect an entity, the relevant components still have to be installed and the system still has to run. Validation must separately protect the energy range and identity rules, and lifecycle code must separately define what the outcomes mean. A Component implementation lets these pieces integrate with Bevy without deciding their behavior for them.

The same distinction applies to our derived ID order. It makes the report reproducible, but it doesn't establish that the lowest ID should win a competition for food. If a later ecological rule uses that order, we'll need to choose and explain it as a rule of the model. A capability that's convenient for display shouldn't silently decide who eats.

Recall answer: which equality belongs in each assertion?

Compare IDs to ask whether two readings refer to the same named individual. Compare complete readings to ask whether their recorded fields match. Compare owned text after editing one clone to test independence. None of these assertions proves that the corresponding creature currently exists in the live world.

Choose capabilities for the question you are asking

Check the opening puzzle again: two equal IDs can belong to unequal readings, and two equal nicknames can belong to different IDs. Your helper should now put ID 2 before ID 10, collapse repeated IDs, handle empty input, and leave the borrowed readings available to their owner. In conflicting component access in Bevy, we'll carry that distinction between retained identity values and borrowed data into an actual system.
