Everyday Rust · 30 minutes

Put the boundary in the code

The inspector prints “Fern: 60 units.” You want to move the reserve implementation into another file without changing that report or every caller that asks for it. Rust's modules let you separate the implementation from the names a caller uses, but the file move is only part of the work: we also need to decide which details the inspector may depend on.

Isolated Rust lab and read-only source navigation. This lesson continues validated construction with Result. You'll complete a reporting function in a separate practice file containing two inline modules, then trace an existing public type through Moss. The live modules, biological rules, dependencies, and assignment remain unchanged.

Protect the measurement while exposing the report

We'll trace a public name through Moss, then recreate that boundary with a measurement module and an inspector in one practice file. Your reporting function will borrow through the public interface and return text it owns. A deliberate privacy error will help locate the boundary: the finished report should distinguish a measured zero from an unknown reserve without gaining access that could bypass construction rules.

Follow the public name into the project

Start with a caller's view of the real project. Open crates/moss-sim/src/lib.rs and find pub use energy::{Energy, MovementRules, SpeciesEnergyRules};, then find mod energy;. The second declaration makes the implementation module part of the crate. The first offers selected names from that module at the crate root, so a caller can write moss_sim::Energy without including the implementation module's name in its path. That gives us a public route we can keep stable when the implementation moves.

Follow the declaration into crates/moss-sim/src/energy.rs to see who implements the type. Then open crates/moss-web/src/browser/snapshot.rs and find the browser consumer's import. You don't need to understand the whole energy module yet. Trace the name from public entry point to implementation and back to a caller; that route shows where an internal change could stop without spreading into presentation code.

Before moving any files, it helps to distinguish the three levels you've just crossed. A package is described by a Cargo.toml and can contain compilation units called crates, such as a library and a binary. Modules organize items inside a crate. Moss's workspace contains simulation and browser packages, while this lab needs only one binary crate with two inline modules. Splitting that binary's code into modules doesn't require another manifest or another application process.

The separation between Moss's packages serves a larger purpose than navigation. The simulation owns authoritative state and uses ECS without requiring a renderer; the browser depends on that simulation and presents what it reports. A native test can therefore exercise the simulation library without opening a window. Moving a file inside one crate leaves that dependency direction alone, which is why source organization and application architecture are different decisions.

Give two responsibilities one public reading

We'll make the same boundary small enough to inspect in one file. A measurement module owns a validated Energy value, and an inspector module turns an optional borrowed measurement into owned text. The caller sees the re-exported Energy and report names. To produce Fern's line, the inspector only needs the public units() accessor; it doesn't need access to the representation that construction protects.

For this lab, an energy value may contain zero through 100 units. That gives the constructor a boundary we can test: Energy::new(101) returns an error, while zero and 100 are valid. You already established that distinction in the preceding lesson. Putting the type in a module should protect the same distinction, so a caller can't bypass validation by writing an arbitrary number into a field.

The inspector also has to describe a measurement that wasn't collected. Its input is Option<&Energy>, so it can receive either a shared reference to a valid measurement or no measurement at all. A reference to a zero reserve should produce “0 units”; the absent case should produce “unknown reserve.” The inspector can make that presentation choice without knowing why collection failed.

Follow the ownership through the call: the caller first constructs a valid reserve, then lets the inspector borrow it through the public interface. The inspector returns a string that owns the finished description. Once the call ends, the caller can change or discard the nickname without affecting the already prepared text. The module boundary changes how the function finds the type, but it doesn't change those borrowing and ownership relationships.

Complete the reporting function

Now use that interface from inspector::report. Prepare the starter in a new directory and replace only that function's body; the preparation command refuses to overwrite an earlier attempt. Its initial todo! deliberately fails at runtime, so the first check should reach the unfinished function. If it fails on syntax or dependencies instead, resolve that setup problem before using the output to reason about reporting.

python3 learning/scripts/labs.py prepare modules --dest work/modules-practice
python3 learning/scripts/labs.py check modules --file work/modules-practice/modules.rs

Before you edit, predict the two lines in main: one call receives a valid reserve and the other receives none. Then look at the return type and explain why changing the caller's nickname afterwards cannot alter the result. The function now lives across a module boundary, but the ownership question is the same one you've already practiced.

Hint 1: use the same two cases as the input type

Match the optional reference. The Some branch has an &Energy; call its public units() method. The None branch has no reserve number to print, so preserve that absence in the wording.

Hint 2: return text with its own storage

format! constructs a String. Use the supplied name in both branches and place the available units only in the measured branch. You do not need to clone the reserve, expose its field, or take ownership of the caller's nickname.

Complete starter file: modules.rs 
mod measurement {
    #[derive(Clone, Copy, Debug, PartialEq, Eq)]
    pub struct Energy { units: u32 }

    #[derive(Debug, PartialEq, Eq)]
    pub struct InvalidReserve;

    fn check_limit(units: u32) -> Result<(), InvalidReserve> {
        if units <= 100 { Ok(()) } else { Err(InvalidReserve) }
    }

    impl Energy {
        pub fn new(units: u32) -> Result<Self, InvalidReserve> {
            check_limit(units)?;
            Ok(Self { units })
        }
        pub fn units(&self) -> u32 { self.units }
    }
}

Use a privacy error to locate a responsibility

A working report shows that the public interface gives the inspector enough access. Now we'll check which implementation details that interface keeps private. The inspector can name Energy because the type is public, yet it still can't reach the private units field directly. Rust lets a module expose a type while controlling how callers construct and inspect its values. That is useful here: making the field public to silence an access error would also let callers create the out-of-range value the constructor was meant to reject.

Try the following intentional compile-error line inside the isolated program's main, then remove it. The expected diagnostic is E0603: the helper function is private. You are deliberately attempting to call an implementation detail from its parent module, not discovering a runtime failure in reserve validation.

let _ = measurement::check_limit(60);

Call Energy::new(60) instead. It validates the input and constructs the value in one operation, so a successful call gives you an energy value that meets the module's rule. Calling the hidden helper on its own would only validate a number; the caller could ignore that result and would still need another way to construct the value. Keeping those steps together gives the public method a clear responsibility.

Private items are usable within their defining module and its descendants. Broader visibility can be deliberately limited with pub(super) for the parent scope or pub(crate) for the crate. Those tools serve real internal consumers; they are not a ladder every function must climb. Start with the caller that needs access, then choose the narrowest suitable scope. The Rust Reference's privacy rules supply the precise cases.

Imports name existing items

Inside the inspector, use crate::Energy; makes the root's re-exported name available without repeating its full path. It names the type that already exists; no energy value is copied and no second library is loaded at runtime. Here crate starts at the current crate root, while super would start at the parent module. These paths locate a definition. A borrow such as &Energy separately describes access to one of its values.

Suppose you later rename measurement. If the crate root still re-exports Energy and preserves its behavior, the inspector and caller tests can keep using the same public path. This is the useful promise behind the re-export: callers depend on selected entry points, giving you room to reorganize implementation files without asking every consumer to follow along.

The lab's tests live in the same crate, so they check its chosen names and behavior rather than the exact external API of the real Moss library. Moss also has separate integration tests that import its library as consumers. For this standalone exercise, the intentional privacy error is the additional compiler check that the helper stays hidden.

Change file placement without inventing another architecture

So far the module bodies have stayed inline to make the practice file complete when copied. When navigation would benefit from separate files, replace the inline mod measurement { ... } body with mod measurement; and put that body in src/measurement.rs in a normal Cargo binary. You can do the same for the inspector. Each module is still declared once, so remove the inline definition when you move its contents.

This file move leaves the module paths and public calls intact. A use declaration cannot replace mod, because an import names an item that must already be part of the module tree. The Book's file-separation example is a useful reference when the compiler cannot find a newly moved module.

For one final check, imagine moving report into another private implementation module while keeping its root re-export. The reporting, absence, construction, and ownership assertions should all remain the same: their inputs and results don't depend on an implementation folder. If a caller changes purely because you renamed that folder, trace whether it was reaching through the public boundary into an internal path.

Recall answer: a path and a borrow answer different questions

crate::Energy identifies the type through the crate's public route. &Energy describes shared access to an instance. Re-exporting the type does not change the borrow, and owning the returned string does not make the private reserve field accessible.

Keep the public promise when the implementation moves

Fern's report still says 60 units after the function crosses a module boundary, and its returned text still owns what it needs. Once your reporting check passes, return to the real Energy type and trace the same route from crate root to implementation to browser consumer. In the collection lesson, we'll turn this one owned description into a population report that stays understandable even when its inputs arrive in a different order.
