The ECS contract · 35 minutes

Prove that the borrows cannot meet

A source sample contains 60 and its preview contains zero. Copying 60 into the preview should be a small job, yet Bevy can reject the system before its loop runs. Both entities use the same component type, and the system's two query signatures may claim incompatible access to it. We'll make the intended separation explicit, then write a refresh that copies from the right source without overwriting that source.

Isolated Bevy ECS 0.18.1 lab. These samples are presentation data in a separate test world. They are not creature reserves, movement, or live biological state. You will complete one preview-refresh body after understanding its access contract. The single live assignment remains in NOW.md.

Read access before the body

In the preceding traits lesson, a Component derive supplied the capability Bevy needs to store a value. It didn't decide which systems could access that value together. For this refresh, we need to read some Sample components and write others, so Bevy has to understand the access declared by the whole system parameter list.

With ordinary Rust values, a mutable borrow gives exclusive access while it is in use: a competing borrow can't read or write that same value at the same time. The compiler can often see those paths directly in local code. An ECS query instead describes a set of components selected from a world at runtime. Bevy therefore checks the query's declared access when it initializes a system, before the body starts iterating.

The lab represents the relationship with two roles. A source entity carries Source, a RowId, and a Sample. A preview carries its own Sample and a PreviewFor that names the source row it wants. Reading the source while writing a distinct preview is valid. The difficulty is showing that the two queries really reach distinct components, rather than relying on what we meant those role names to imply.

Consider this intentionally conflicting parameter excerpt. It is not part of the successful reference program. If registered as an ordinary system, it can compile as Rust and then fail Bevy's access validation with B0001 when initialized:

sources: Query<(&RowId, &Sample), With<Source>>,
previews: Query<(&PreviewFor, &mut Sample)>,

Read the two signatures as permissions: the first may read Sample on a source entity, and the second may write Sample on an entity with preview data. An entity could carry both Source and PreviewFor, so it could match both queries. Its one sample would then be accessible through a shared path and a mutable path at once. The fixture might not contain such an entity today, but the parameter list hasn't ruled it out.

Make the sets genuinely disjoint

Before changing a filter, decide what should happen to that dual-role entity. In this lab, source samples are authoritative inputs to presentation. A source must therefore remain protected even if it also carries preview data. Adding Without<Source> to the mutable query expresses that policy directly: anything read by the source query has the marker, and anything written by the preview query lacks it. No entity can meet both conditions.

The resulting asymmetry is intentional. The source query can still read a row with both roles, while the preview query can't write it. Excluding that row from both queries would make its source value disappear from lookup as well, which would be a different policy. This is why it's worth stating who owns the authoritative value before trying filters: a filter that makes the error disappear might also change the work you wanted.

Membership under the selected policy
Entity dataAccess granted to this system
Source, RowId, SampleRead as a source; never write as a preview.
PreviewFor, Sample, no SourceWrite as a preview; not read as a source.
Source, RowId, PreviewFor, SampleRead as a source; excluded from preview mutation.
Sample aloneNeither query includes it.

Bevy 0.18.1's disjoint-query documentation explains the access rule. The official B0001 explanation is a useful diagnostic reference. Here the meaningful question is “which entity could both queries reach?”, followed by “should that entity belong to both roles?”

Use a fixture that could reveal a mistake

We can test that policy by putting a dual-role row into the fixture rather than hoping none appears. Give it sample 900 and a request to preview row 1. The ordinary preview should copy row 1's sample of 60, while the dual-role row must stay at 900. A test with only separate source and preview entities would exercise copying, but wouldn't reveal whether we protected this boundary.

The fixture also creates source row 2, with sample 20, before row 1. That order challenges a different mistake: copying the first source visited would update the ordinary preview to 20 instead of 60. Match the requested RowId explicitly. The relationship comes from those IDs, not from the order in which a query happens to visit entities.

For a missing-source case, another preview asks for row 99 and begins with sample 777. This small helper leaves that value alone when lookup fails. That is retention behavior, not proof that 777 remains fresh. A production inspector would need to represent freshness or a missing-source status separately, as in the Option lesson; the lab isolates which assignments this updater is permitted to make.

Before you write the loop, predict the ordinary preview, the dual-role row, and a sample with neither role after one refresh. The lookup body decides which value to copy into an eligible preview. Query membership decides which entities the body can touch at all. Keeping those two reasons separate will make a failed assertion easier to diagnose.

Hint 1: decide eligibility before lookup

The mutable query already excludes every source. The loop cannot write the protected dual-role row through that query, regardless of its requested ID.

Hint 2: copy only a matching borrowed value

For each eligible preview, search source rows by RowId. If a match exists, assign its sample number into the preview. If none exists, perform no assignment.

Prediction answer

The ordinary preview becomes 60, the dual-role row remains 900, and the unrelated sample remains 333. The source lookup explains the copied 60. The disjoint filter and required preview data explain the protected and unrelated values.

#[derive(Component)]
struct Source;
#[derive(Component)]
struct RowId(u32);
#[derive(Component)]
struct PreviewFor(u32);
#[derive(Component, Debug, PartialEq, Eq)]
struct Sample(i32);

fn update_previews(
    sources: Query<(&RowId, &Sample), With<Source>>,
    mut previews: Query<(&PreviewFor, &mut Sample), Without<Source>>,
) {
    let _ = (sources, &mut previews);
    todo!("refresh only permitted previews from their matching source")
}

fn preview_schedule() -> Schedule {
    let mut schedule = Schedule::default();
    schedule.set_executor_kind(ExecutorKind::SingleThreaded);
    schedule.add_systems(update_previews);
    schedule
}

struct Fixture {
    world: World,
    source: Entity,
    preview: Entity,
    protected: Entity,
    missing: Entity,
    unmarked: Entity,
}

fn fixture() -> Fixture {
    let mut world = World::new();
    world.spawn((Source, RowId(2), Sample(20)));
    let source = world.spawn((Source, RowId(1), Sample(60))).id();
    let preview = world.spawn((PreviewFor(1), Sample(0))).id();
    let protected = world.spawn((Source, RowId(9), PreviewFor(1), Sample(900))).id();
    let missing = world.spawn((PreviewFor(99), Sample(777))).id();
    let unmarked = world.spawn(Sample(333)).id();
    Fixture { world, source, preview, protected, missing, unmarked }
}

fn sample(world: &World, entity: Entity) -> i32 {
    world.get::<Sample>(entity).expect("fixture entity has a sample").0
}

fn main() {
    let mut f = fixture();
    preview_schedule().run(&mut f.world);
    println!("source={} preview={} protected={} missing={} unmarked={}",
        sample(&f.world, f.source), sample(&f.world, f.preview),
        sample(&f.world, f.protected), sample(&f.world, f.missing),
        sample(&f.world, f.unmarked));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn matching_source_is_copied_without_mutation() {
        let mut f = fixture();
        preview_schedule().run(&mut f.world);
        assert_eq!(sample(&f.world, f.preview), 60);
        assert_eq!(sample(&f.world, f.source), 60);
    }

        preview_schedule().run(&mut f.world);
        assert_eq!(sample(&f.world, f.protected), 900);
    }

    #[test]
    fn missing_source_and_unmarked_rows_keep_their_previous_values() {
        let mut f = fixture();
        preview_schedule().run(&mut f.world);
        assert_eq!(sample(&f.world, f.missing), 777);
        assert_eq!(sample(&f.world, f.unmarked), 333);
    }

        f.world.get_mut::<Sample>(f.source).unwrap().0 = 41;

        assert_eq!(sample(&f.world, f.preview), 41);
        assert_eq!(sample(&f.world, f.source), 41);
        assert_eq!(sample(&f.world, f.protected), 900);
    }
}

use bevy_ecs::{prelude::*, schedule::ExecutorKind};

#[derive(Component)]
struct Source;
#[derive(Component)]
struct RowId(u32);
#[derive(Component)]
struct PreviewFor(u32);
#[derive(Component, Debug, PartialEq, Eq)]
struct Sample(i32);

fn update_previews(
    sources: Query<(&RowId, &Sample), With<Source>>,
    mut previews: Query<(&PreviewFor, &mut Sample), Without<Source>>,
) {
    for (wanted, mut preview) in &mut previews {
        if let Some((_, source)) = sources.iter().find(|(id, _)| id.0 == wanted.0) {
            preview.0 = source.0;
        }
    }
}

fn preview_schedule() -> Schedule {
    let mut schedule = Schedule::default();
    schedule.set_executor_kind(ExecutorKind::SingleThreaded);
    schedule.add_systems(update_previews);
    schedule
}

When the same entities really must be visited twice

The filter works because authoritative sources and writable previews are meant to be separate roles. Other systems may legitimately need to visit the same entities twice, first gathering measurements and then updating them from a summary. Excluding the overlap with Without would remove part of that requested work. Such a system needs to separate access in time instead.

Bevy's ParamSet allows potentially conflicting parameters to be accessed in separate stages through methods such as p0() and p1(). You can use the first accessor to collect an owned summary, let that borrow end, and then obtain the second accessor for the update. The ownership of the summary matters: retaining a borrowed component from the first stage while asking for conflicting access in the second would keep the very overlap you're trying to remove, so the borrow rules reject it.

Our preview updater doesn't need ParamSet, because its read and write roles really are disjoint. Another design could represent source samples and rendered values with distinct component types. That may be useful if they are different concepts in the application, but it should also make the ownership model easier to explain. Choose between these approaches by the data relationship you need, rather than treating them as interchangeable ways to suppress a diagnostic.

Bring back the access question

Return to the rejected system and imagine commenting out the assignment inside its loop. It still declares a mutable query, so why would Bevy now assume that query won't reach a conflicting entity? The permissions arrive in the parameter list before any particular branch of the body runs. When writing is unnecessary, change the requested access itself.

Recall answer

An ordinary Query<&mut Sample> declares possible mutable access. Validation cannot assume that a branch will avoid the conflicting entity. Change the signature to shared access when writing is unnecessary, establish genuine disjointness when roles differ, or sequence overlapping access deliberately.

The query validation and ParamSet contracts used here were checked against the cached bevy_ecs-0.18.1 source. The failing parameter excerpt remains a diagnostic exercise outside the successful reference. Passing the four tests establishes this small projection policy; when reviewing a different system, you'll still need to reason about that system's complete set of accesses.

The source can now lend its sample while the preview updates, and the dual-role row stays protected because the signature states the policy. There is another way for a correct refresh to show the wrong value, though: it may run before the source has finished changing. Continue to ordering a schedule deliberately to see how two safe observations can disagree when they occur on different sides of a mutation.
