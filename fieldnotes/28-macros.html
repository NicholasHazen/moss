A selective Rust survey · 40 minutes

Read the code a macro asks Rust to check

You have written the same pair of assertions several times: this reading belongs to actor 7, and its reserve is a measured zero rather than unavailable. A small macro can give that familiar check a labeled call. But suppose the reading comes from an expression that collects a report. Expanding the two comparisons carelessly could collect it twice.

Account for the work inside a concise assertion

You'll complete the expansion of assert_reading!, preserving one evaluation per input and borrowing the reading so its owner can keep using it. We'll inspect how the matcher supplies syntax, how generated locals preserve the evaluation contract, and how a compiler error reduces to an ordinary Rust operation.

The expected result is an assertion whose behavior you can explain as precisely as its output. We'll also connect that reasoning to the Bevy derives you've already used: generated trait implementations grant capabilities, while explicit insertion and scheduling make the world do something. You can then decide when a macro earns its syntax and when an ordinary function or pair of assertions already does the job.

Keep the assertion smaller than the system

The value under test is a Reading with an owned name, an actor ID, and an optional reserve. Our assertion checks the last two fields and leaves the name available to its owner. That tells us exactly what a passing call means: the identity and measurement match the expectation. Comparing whole readings, establishing that an actor is alive, or checking a complete lifetime would need additional evidence.

We want a call that reads assert_reading!(reading, actor = 7, reserve = Some(0)), keeping the expected identity beside the expected measurement. The labels actor and reserve are tokens chosen for this macro's syntax; Rust does not interpret them as named function arguments. Their order is fixed, with an optional trailing comma to make a multiline call comfortable.

Before defining new syntax, keep in view what a function already offers. The supplied same_value<T: PartialEq> can perform the same comparison for many concrete types through an ordinary trait bound. Within one call, both arguments have the same T; another call can choose a different type. Integers, strings, vectors, and optional values do not need a macro merely because they have different types. When a clear function signature expresses the operation, that is enough.

The small benefit here is the labeled assertion form and the diagnostic labels it expands into. Each check is still an ordinary field comparison. The macro will not discover fields, infer their units, or decide a biological policy. If this calling form stops making tests easier to read, two explicit assert_eq! calls remain a complete way to state the requirement.

Read the matcher and the expansion

A macro_rules! definition describes the syntax it accepts with a matcher, then describes replacement syntax called the expansion. Our $reading:expr matcher accepts one Rust expression and binds that syntax to a metavariable. Using $reading in the expansion inserts the expression there. This differs from a function parameter: the macro is not handed a runtime value that has already been computed.

Follow what would happen if the expansion inserted $reading once to read the actor and again to read the reserve. A call with a simple variable might seem fine, but a call with a report-producing expression would execute that expression twice. The two checks could then describe different collections of data. Our contract instead evaluates the reading expression, expected actor, and expected reserve once each, in that order, before either assertion. If one expression itself panics, later evaluation naturally cannot continue.

We can preserve that contract by binding each input to a local and using those locals in the checks. The reading local holds a borrow, so asserting on an existing reading does not move its owned name. If the call supplies a temporary reading, the local borrow keeps it alive for the checks within the block. In the double braces, the outer pair delimits the macro's replacement and the inner pair becomes the block expression containing those locals.

The matcher's $(,)? handles a smaller syntax choice: it accepts zero or one trailing comma. It does not ask the expansion to evaluate any input again. That is the only repetition pattern this assertion needs. The macros-by-example reference explains fragment matchers, repetition, and expansion when you need to extend such a calling form.

Hint 1: retain one evaluation per expression

Bind let reading = &$reading;, then bind the expected actor as u64 and reserve as Option<u32>. Use these local values for the comparisons. Repeating the macro metavariable would repeat its supplied expression.

Hint 2: assert the two different meanings

Compare reading.actor with the expected actor and label the assertion “actor identity.” Then compare reading.reserve_units with the expected reserve and label it “reserve measurement.” Keep None distinct from measured zero.

Complete starter file: macros.rs
#[derive(Debug, PartialEq, Eq)]
struct Reading {
    actor: u64,
    name: String,
    reserve_units: Option<u32>,
}

fn same_value<T: PartialEq>(actual: &T, expected: &T) -> bool {
    actual == expected
}

macro_rules! assert_reading {
    ($reading:expr, actor = $actor:expr, reserve = $reserve:expr $(,)?) => {{
        let reading = &$reading;
        let actor: u64 = $actor;
        let reserve: Option<u32> = $reserve;
        let _ = (reading, actor, reserve);
        todo!("compare actor identity and the optional reserve measurement")
    }};
}

fn fixture() -> Reading {
    Reading {
        actor: 7,
        name: "Fern".into(),
        reserve_units: Some(0),
    }
}

fn main() {
    let reading = fixture();
    let mut evaluations = 0;
    assert_reading!(
        {
            evaluations += 1;
            &reading
        },
        actor = 7,
        reserve = Some(0)
    );
    println!(
        "{}: actor={} reserve={:?}",
        reading.name, reading.actor, reading.reserve_units
    );
    println!("source evaluations: {evaluations}");
    println!("zero equals unknown: {}", same_value(&Some(0_u32), &None));
}

#[cfg(test)]
mod tests {
    use super::*;
    use std::panic::catch_unwind;

    #[test]
    fn accepts_values_references_and_an_optional_trailing_comma() {
        let reading = fixture();
        assert_reading!(reading, actor = 7, reserve = Some(0));
        assert_reading!(&reading, actor = 7, reserve = Some(0),);
        assert_reading!(fixture(), actor = 7, reserve = Some(0));
    }

    #[test]
    fn borrowing_the_reading_does_not_move_its_owned_name() {
        let reading = fixture();
        assert_reading!(reading, actor = 7, reserve = Some(0));
        assert_eq!(reading.name, "Fern");
    }

    #[test]
    fn each_input_runs_once_in_the_documented_order() {
        let mut calls: Vec<&str> = Vec::new();
        assert_reading!(
            {
                calls.push("reading");
                fixture()
            },
            actor = {
                calls.push("actor");
                7
            },
            reserve = {
                calls.push("reserve");
                Some(0)
            },
        );
        assert_eq!(calls, vec!["reading", "actor", "reserve"]);
    }

    #[test]
    fn generated_bindings_do_not_capture_callers_with_the_same_names() {
        let reading = fixture();
        let actor = 7_u64;
        let reserve = Some(0_u32);
        assert_reading!(reading, actor = actor, reserve = reserve);
        assert_eq!((actor, reserve), (7, Some(0)));
        assert_eq!(reading.name, "Fern");
    }

    #[test]
    fn measured_zero_does_not_match_unknown() {
        let result = catch_unwind(|| {
            assert_reading!(fixture(), actor = 7, reserve = None);
        });
        let panic = result.expect_err("wrong reserve must fail");
        let message = panic.downcast_ref::<String>().unwrap();
        assert!(message.contains("reserve measurement"), "{message}");
    }

    #[test]
    fn wrong_identity_is_rejected_even_with_a_matching_reserve() {
        let result = catch_unwind(|| {
            assert_reading!(fixture(), actor = 8, reserve = Some(0));
        });
        let panic = result.expect_err("wrong actor must fail");
        let message = panic.downcast_ref::<String>().unwrap();
        assert!(message.contains("actor identity"), "{message}");
    }

    #[test]
    fn unknown_can_be_the_expected_measurement() {
        let reading = Reading {
            reserve_units: None,
            ..fixture()
        };
        assert_reading!(reading, actor = 7, reserve = None);
        assert!(same_value(&reading.reserve_units, &None));
    }

    #[test]
    fn generic_function_handles_other_types_without_new_syntax() {
        assert!(same_value(&String::from("Fern"), &String::from("Fern")));
        assert!(!same_value(&vec![2, 10], &vec![10, 2]));
        assert!(same_value(&None::<u32>, &None));
    }
}

Hygiene does not evaluate your expression

The expression-count tests cover how often generated work runs. Next, check whether the generated bindings can change which caller values that work refers to. Both the expansion and its caller may use the same local names. The hygiene test deliberately names caller variables reading, actor, and reserve, matching the bindings generated by the macro. The expressions supplied at the call still refer to their caller's variables, while the generated locals have their own context. Their matching spellings therefore do not accidentally redirect those references.

This behavior is part of declarative macros' mixed-site hygiene. It does not mean every kind of name is resolved in a universally isolated scope. Paths to other items have their own lookup rules, and an exported macro may need $crate to reach a helper in its defining crate. Our private single-file assertion has no such exported helper, so its local-binding example is enough to investigate the problem here.

Name resolution and evaluation count remain separate questions. Try replacing the shared reading local with (&$reading).actor in one check and (&$reading).reserve_units in the other. The generated names may still resolve correctly, but the report-producing expression is now present twice. The side-effect test catches the two evaluations that a simple variable argument could conceal.

Reduce a generated error to ordinary Rust

When the compiler points into an expansion, reduce the problem to the ordinary operation the macro generated. The following probe keeps the actor-type constraint from our assertion while removing the other fields. Save it separately as work/macros-practice/wrong_actor.rs; it is an intentional failing experiment outside the passing lab.

macro_rules! actor_id {
    ($value:expr) => {{
        let actor: u64 = $value;
        actor
    }};
}
fn main() {
    println!("{}", actor_id!("7"));
}
rustc +1.93.1 --edition=2024 work/macros-practice/wrong_actor.rs -o work/macros-practice/wrong_actor

Rust 1.93.1 reports E0308 because the invocation supplies a &str where the generated binding requires u64. Replace the call mentally with let actor: u64 = "7"; and the error becomes an ordinary type mismatch. Accepting an expression in a matcher does not promise that expression has the type the expansion needs. Normal type checking still applies to the generated Rust.

Immediate correction

Change only actor_id!("7") to actor_id!(7_u64). Rerun the compile command, then run work/macros-practice/wrong_actor; it prints 7. If the input truly comes from text, parse it and handle the Result before calling. Removing the type constraint would conceal a different input contract.

Recognize the derive you already use

We can now read our own expansion, so let's connect that method to the generated implementations already present in the ECS examples. The assertion is a declarative macro, but its function-like call syntax does not identify that implementation mechanism on its own. A procedural macro can also use a function-like call. Procedural macros run compiler-invoked Rust code that consumes and produces token streams, and they can additionally appear as attributes or custom derives. Keeping invocation syntax separate from implementation helps when you trace a macro supplied by a library.

You have already used procedural macros through Bevy's #[derive(Component)] and #[derive(Resource)]. They generate trait implementations that let your types participate in those ECS APIs. To connect that capability to behavior, recall the operations that follow: component values must be placed on entities, resources inserted into the world by type, and systems scheduled to act on them. Deriving the capability does not perform those operations.

The optional main.rs below makes that separation visible with pinned Bevy 0.18.1. Its types already have the derives when an empty world is created, yet the world still contains no entities and no tick resource. Only the subsequent explicit insertion operations give it a marker containing seven and a tick resource containing zero.

Complete Bevy derive observation
use bevy_ecs::prelude::*;

#[derive(Component)]
struct Marker(u32);

#[derive(Resource)]
struct Tick(u64);

fn main() {
    let mut world = World::new();
    assert_eq!(world.entities().len(), 0);
    assert!(world.get_resource::<Tick>().is_none());
    let entity = world.spawn(Marker(7)).id();
    world.insert_resource(Tick(0));
    assert_eq!(world.get::<Marker>(entity).unwrap().0, 7);
    assert_eq!(world.resource::<Tick>().0, 0);
    println!("marker=7 tick=0");
}

For the code we have here, finding the invocation and reducing its generated operation already gives us a practical debugging method.

Concise syntax still has work to account for

The opening assertion now borrows one evaluated reading, checks the expected identity and measurement, and leaves the name available. Its tests can reject repeated work as well as an incorrect value. Reading the expansion also gives compiler errors an ordinary operation to point to. The same approach explains why a derive can supply an ECS capability while leaving insertion and execution to explicit code.
