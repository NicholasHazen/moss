Start with evidence · 35 minutes

Who owns the next change?

Suppose you pause beside Fern and write down her reserve: 60 units. You let the world run for three more ticks, then check again. Fern now has 57, while your note still says 60. Both readings are useful, provided you know which moment each describes.

This is an isolated Rust exercise in ownership.rs, using the distinction between ticks and observations from the previous lesson. You'll implement capture in a scratch project; the live movement assignment in NOW.md stays where it is.

Save a reading the world can leave behind

You'll build an observation that keeps Fern's earlier reserve and name while the caller continues using its live values. First we'll decide what the function needs to borrow and what its result needs to own; then you'll complete the capture and examine a borrow the compiler rejects. The finished example should explain why a saved 60 and a current 57 can coexist without either being wrong.

Read Fern's reserve without taking it away

The inspector needs to see the reserve that belongs to the simulation. Afterward, the simulation still needs that value so it can pay Fern's upkeep on the next tick. That gives us a useful starting point for the function's signature: capture should borrow the reserve while it reads it. In Rust, the parameter reserve: &Reserve asks for that access. The & means the function receives a reference to the caller's value, so it can inspect the reserve without becoming its owner.

Borrowing is enough to read the value now, but our note needs to survive what happens next. If we want it to remember 60 after Fern's reserve becomes 57, the returned observation must store a number of its own. We'll therefore borrow the live reserve at the entrance to capture, then put a copy into the observation we return. These two choices fit together: borrowing describes how we access the input, while copying describes what we keep.

Our Reserve is a small struct containing one u32. It derives Copy, which allows Rust to duplicate that value when an expression needs to provide an owned Reserve. The copy is independent of the original. Once we have saved it, a later assignment to Fern's live reserve affects only the live value, just as changing a measurement doesn't rewrite an earlier note.

You can read a function's parameter types as a description of this relationship with its caller. Keep the following table nearby while working through the example; the important distinction is what the function receives and what the caller can still use afterward.

How each parameter relates to the caller's value
ParameterMeaning in this lab
reserve: ReserveThe function receives an owned value. Because Reserve implements Copy, passing it also leaves the caller's value available.
reserve: &ReserveThe function borrows the caller's value for reading.
reserve: &mut ReserveThe function borrows exclusive mutable access, allowing it to change the caller's value.
name: StringThe function receives ownership of the string. Passing an existing variable moves that string unless the caller explicitly provides a clone.

The String row shows why we need to look at the type, rather than guess from the size of a variable or whether it sits on the stack. A String owns a growable text buffer and doesn't implement Copy. Duplicating its text requires an explicit operation. We'll use that distinction to give the saved reserve a name.

Keep the name with the measurement

A reserve of 60 isn't much of a historical record unless we also know whose reserve it was. Our Observation will contain both the copied Reserve and an owned String. Keeping its own name means that the observation can still say “Fern” even if someone later changes the live nickname to “Fern the hare.” The whole reading should describe the moment we captured it.

To read the name, capture takes a &str: a borrowed view of UTF-8 text, also called a string slice. This gives callers some flexibility. They can pass the literal "Fern", or borrow an existing String with &nickname; Rust can convert that reference to the string slice the function expects. In either case, the function can read the text while its existing owner keeps it.

Inside the function, we'll turn that borrowed text into an owned string with name.to_owned(). This allocation is doing useful work: it gives the observation text that can outlive changes to the nickname. The reserve field takes a different route. Writing *reserve reads through the reference, and using that expression to initialize the field copies our Copy value. The asterisk is a dereference operator; it isn't a request to clone an arbitrary object. If Reserve instead owned a non-copyable buffer, Rust would reject an attempt to move it out through this shared reference.

Our Observation contains that owned String and does not implement Copy, so transferring the whole observation will move it. Before filling in the function, follow one observation through its caller. We capture Fern at 60, change the live reserve to 57, and then write let saved = reading;. Predict the live reserve, the saved reserve, and the saved name at the end. In particular, consider whether giving the observation a new owner changes the values stored inside it.

Hint 1: what access do the inputs allow?

Both inputs are shared references. They let capture read the caller's data, but they don't let it take an owned string away from the caller or assign a new value to the caller's reserve. The returned observation therefore needs its own values.

Hint 2: build the two fields

Construct an Observation with name.to_owned() in its name field and *reserve in its reserve field. The first expression creates owned text; the second provides a copy of this small struct.

Prediction answer

The live reserve ends at 57, while the saved observation contains 60 and “Fern.” The assignment to saved moves ownership of the existing observation, including its string. It doesn't make another observation or alter the one we already captured. After that move, use saved to access it; reading is no longer available as an observation.

Complete starter file: ownership.rs 
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Reserve { units: u32 }

#[derive(Debug, PartialEq, Eq)]
struct Observation {
    name: String,
    reserve: Reserve,
}

fn capture(name: &str, reserve: &Reserve) -> Observation {
    let _ = (name, reserve);
    todo!("save owned text and a copied reserve")
}

fn main() {
    let nickname = String::from("Fern");
    let mut reserve = Reserve { units: 60 };
    let reading = capture(&nickname, &reserve);
    reserve.units = 57;
    let saved = reading;
    println!("{}: live={} saved={}", nickname, reserve.units, saved.reserve.units);
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn capture_preserves_the_source() {
        let name = String::from("Fern");
        let reserve = Reserve { units: 60 };
        let reading = capture(&name, &reserve);
        assert_eq!(name, "Fern");
        assert_eq!(reserve.units, 60);
        assert_eq!(reading.name, "Fern");
        assert_eq!(reading.reserve.units, 60);
    }

    #[test]
    fn captured_reserve_is_independent() {
        let mut reserve = Reserve { units: 60 };
        let reading = capture("Fern", &reserve);
        reserve.units = 57;
        assert_eq!(reserve.units, 57);
        assert_eq!(reading.reserve.units, 60);
    }

    #[test]
    fn captured_text_is_independent() {
        let mut name = String::from("Fern");
        let reading = capture(&name, &Reserve { units: 60 });
        name.push_str(" the hare");
        assert_eq!(name, "Fern the hare");
        assert_eq!(reading.name, "Fern");

Complete worked answer: ownership.rs 
#[derive(Clone, Copy, Debug, PartialEq, Eq)]

#[derive(Debug, PartialEq, Eq)]
struct Observation {
    name: String,
    reserve: Reserve,
}

fn capture(name: &str, reserve: &Reserve) -> Observation {
    Observation { name: name.to_owned(), reserve: *reserve }
}

In the answer, the only persistent data created by capture is the observation it returns. Its inputs are borrowed for the duration of the call, so the caller can carry on using the nickname and reserve afterward. Running the program prints Fern: live=57 saved=60, making the difference between the live value and the saved measurement visible.

Why can the caller change Fern afterward?

The saved reading works, but we should also be able to explain why Rust permits the caller's next change. We have borrowed Fern's reserve and then changed it in the same caller. That may seem at odds with the idea of a shared reference: if somebody is reading the reserve, shouldn't Rust prevent us from changing it? The missing detail is when that access is still needed. Our capture function returns owned data, so nothing in its result continues to borrow the input. Once the call finishes, that shared borrow has done its job, and the caller can mutate the live reserve.

Now keep a reference to the live value instead of making a saved observation. The following fragment intentionally fails to compile; consider it separately from your working file. Pay attention to the order of the assignment and the final print.

let mut reserve = Reserve { units: 60 };
let borrowed = &reserve;
reserve.units = 57;
println!("{}", borrowed.units);

The print still needs borrowed, so the shared borrow remains in use across the attempted assignment. Rust rejects that mutation because we would be changing the value while the shared reference is still needed. Moving the print before the assignment gives the borrow an earlier last use and allows the later change. Keeping an independent copy would solve a different problem: it would let us print the earlier value after changing the live one, which is exactly what our observation does.

The word mut has a specific part in this story. Declaring let mut reserve allows us to assign to that local value; lending &mut reserve would let a function change it through an exclusive reference. Our inspector asks only for &Reserve, because reading is all it needs.

What if the variable holding the reference is mutable?

A mutable binding that holds a shared reference lets you assign a different reference to that binding. It still holds a shared reference, so it doesn't gain permission to mutate the referred-to reserve.

This gives us a more useful response to an ownership error than cloning everything until the compiler accepts it. Decide what needs to remain usable and what needs to be remembered. Here, a short borrow provides access, a copy preserves the measurement, and an owned string preserves its name. Each operation has a reason in the design.

An old reading can be the right reading

We can now explain the two numbers that opened the lesson. Fern has 57 because the world has continued to change; the saved observation has 60 because it owns the measurement taken earlier. The remaining responsibility belongs to the interface: it must tell the reader that 60 is historical. If it labels that value “current reserve,” correct ownership won't rescue the misleading display. A fuller journal would attach a tick and run identity to each observation, then decide how many old observations to keep.

Before leaving the example, trace the data once more and identify where duplication actually occurs: when we pass &reserve, when we store *reserve, or when we move reading into saved. Being able to distinguish these operations will help when an ECS query lends you access to a much larger world.

Recall answer

Passing &reserve gives borrowed access. Storing *reserve copies our Copy struct, producing an independent measurement. Moving the observation into saved transfers ownership of the existing data, without allocating another string. The text was duplicated earlier, when to_owned() created the observation's name.

The exercise checks those ownership decisions in a small function. In the next lesson, we'll use the same reasoning to describe an ECS system's access: which entities it can read, and which components it is allowed to change.
