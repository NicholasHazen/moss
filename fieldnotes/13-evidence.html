The ECS contract · 40 minutes

Make a test disagree with a plausible mistake

The percentage helper passes its tests, but the inspector still says 99. You fix the update and now its current value is 37, yet a downstream observer still records 99. Before changing the arithmetic again, we need evidence about the rest of that path: which sample was selected, whether the projection ran, and when the observer read its result.

Isolated evidence lab. These are presentation samples in a miniature Bevy ECS 0.18.1 world. You will complete a projection system and investigate deliberately incomplete or misordered schedules. Nothing is installed into Moss, and the live movement exercise remains unchanged.

Choose a check that can expose the mistake

First you'll complete a projection and compare the value it leaves with the value its observer actually saw. Then you'll write your own tests and try them against six supplied defects, using their failures or survival to improve the evidence. The optional compiled-Rust panel extends that investigation into the browser. Throughout, the goal is to connect each claim to a check that reaches the part of the program capable of making it false.

Name the claim before choosing a check

Start by making the claim small enough to check. “The percentage is correct” might mean the helper floors a fraction correctly, the system chooses the intended entity, an observer sees the updated result, or the browser displays it. A test must reach the part of the program that could make its particular claim false. Otherwise the test can remain green while the defect survives somewhere it never looked.

Give those possibilities different visible results. The selected sample contains three used units out of eight, which our floor-based reporting rule turns into 37. An unselected sample contains one out of two and would produce 50. The display begins at a stale 99. Choosing these distinct values is part of designing the fixture: 50 suggests the wrong input, while 99 suggests that an old value reached the observation.

The projection writes a DisplayValue resource, and the observer copies that resource into a trace. Checking the resource tells us where the projection eventually left the world; checking the trace tells us what its consumer actually read. This is a native consumer in our miniature schedule. It lets us test the timing relationship before adding the separate question of browser presentation.

A helper is a local contract

The supplied percentage helper has a deliberately local job. Given used units and capacity, it returns absence for zero capacity, caps an amount above capacity, and floors the percentage otherwise. It widens the intermediate arithmetic to u64 before multiplying by 100, so a valid large u32 input does not overflow during that calculation.

Neither integer tells the helper which entity was selected or when a system should execute. That makes its arithmetic easy to test in isolation: if an input produces the wrong percentage, there are few possible causes to inspect. It also explains why those tests cannot establish selection or scheduling behavior. Those relationships need fixtures that actually contain them.

Your edit belongs in project_selected, where the query requests samples carrying Selected. When exactly one sample matches, the system projects it through the supplied helper. When no sample or several samples match, it must clear the display to None. Leaving 99 untouched would make an unsuccessful selection look like a successful reading retained from the previous run.

For this exercise, both zero capacity and nonunique selection lead to an unavailable display. A fuller interface could keep their reasons distinct, as the Result lesson did. Our immediate requirement is narrower: the display must contain a newly justified value or explicitly say none is available. That gives the projection a useful contract without adding error wording to the task.

Let the world supply the result

To check that contract in use, install the projection and observer as real Bevy systems and chain them in that order. The integration fixture creates their entities and resources, executes the schedule, and reads the changed display and collected trace. It asks the world for evidence of what ran. Calculating the percentage a second time in a test would only repeat the arithmetic and leave the schedule unexamined.

Inside the projection body, single asks the query for exactly one matching item. The Bevy 0.18.1 Query documentation for single specifies the returned result. Handling its error explicitly lets the system enforce our uniqueness requirement instead of accepting whichever row an iteration happens to visit first.

Follow the signature and body together. A perfectly correct call to percentage produces 50 if the query gives it the unselected sample. A perfectly correct projection produces nothing if the schedule never calls it. The two-row fixture and installed schedule bring both opportunities for failure within the test's reach.

The deferred-command lesson showed why we also retain an observer: a row could exist when the schedule returned yet have been absent at the moment an earlier system looked. Here the display could finish at 37 after the observer already copied 99. Reading final state would miss that mistake, so the trace preserves the earlier moment for an assertion.

Predict two plausible defects

Use that distinction to predict two defects before running them. In a world beginning with stale display 99, omit the projection and run only the observer. Then start a fresh world at 99 and run the observer before the projection. For each schedule, predict the final display and the trace separately; follow the writes and copies in order rather than letting the eventual result overwrite your memory of what happened earlier.

Hint 1: a passing helper does not execute itself

The incomplete schedule never calls the projection. No system changes the display before the observer reads it.

Hint 2: later writes cannot refresh an owned trace entry

The reversed schedule eventually updates the current display, but the observer already copied its previous value into the trace.

Prediction answer

Omitting projection leaves both display and trace at 99. Reversing the systems leaves the final display at 37 but records 99 in the trace. Only the correctly ordered schedule both displays 37 and records 37.

The supplied tests deliberately run those wrong schedules and check the predicted differences. Such a test passes when it exposes the counterexample correctly. The normal installed schedule has its own assertion requiring 37 in both places. Reading which schedule a test built is therefore part of understanding what its green result establishes.

Complete starter: evidence.rs
use bevy_ecs::{prelude::*, schedule::ExecutorKind};

#[derive(Component)]
struct Selected;
#[derive(Component)]
struct Sample { used: u32, capacity: u32 }
#[derive(Resource)]
struct DisplayValue(Option<u32>);
#[derive(Resource, Default)]
struct Trace(Vec<Option<u32>>);

fn percentage(used: u32, capacity: u32) -> Option<u32> {
    if capacity == 0 { return None; }
    Some(((u64::from(used.min(capacity)) * 100) / u64::from(capacity)) as u32)
}

fn project_selected(
    samples: Query<&Sample, With<Selected>>,
    mut display: ResMut<DisplayValue>,
) {
    let _ = (samples, &mut display);
    todo!("project one selected row; clear the display when selection is not unique")
}

fn observe_display(display: Res<DisplayValue>, mut trace: ResMut<Trace>) {
    trace.0.push(display.0);
}

fn installed_schedule() -> Schedule {
    let mut schedule = Schedule::default();
    schedule.set_executor_kind(ExecutorKind::SingleThreaded);
    schedule.add_systems((project_selected, observe_display).chain());
    schedule
}

fn fixture() -> World {
    let mut world = World::new();
    world.insert_resource(DisplayValue(Some(99)));
    world.init_resource::<Trace>();
    world.spawn(Sample { used: 1, capacity: 2 });
    world.spawn((Selected, Sample { used: 3, capacity: 8 }));
    world
}

fn main() {
    let mut world = fixture();
    installed_schedule().run(&mut world);
    println!("display={:?} trace={:?}", world.resource::<DisplayValue>().0,
        world.resource::<Trace>().0);
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn helper_defines_rounding_bounds_and_zero_capacity() {
        assert_eq!(percentage(3, 8), Some(37));
        assert_eq!(percentage(9, 8), Some(100));
        assert_eq!(percentage(0, 0), None);
        assert_eq!(percentage(u32::MAX, u32::MAX), Some(100));
    }

    #[test]
    fn installed_projection_uses_the_selected_row_before_observation() {
        let mut world = fixture();
        installed_schedule().run(&mut world);
        assert_eq!(world.resource::<DisplayValue>().0, Some(37));
        assert_eq!(world.resource::<Trace>().0, vec![Some(37)]);
    }

    #[test]
    fn no_selected_row_clears_a_previous_display_value() {
        let mut world = fixture();
        let selected: Vec<_> = world.query_filtered::<Entity, With<Selected>>()
            .iter(&world).collect();
        for entity in selected { world.entity_mut(entity).remove::<Selected>(); }
        installed_schedule().run(&mut world);
        assert_eq!(world.resource::<DisplayValue>().0, None);
        assert_eq!(world.resource::<Trace>().0, vec![None]);
    }

    #[test]
    fn multiple_selected_rows_do_not_silently_pick_one() {
        let mut world = fixture();
        world.spawn((Selected, Sample { used: 1, capacity: 2 }));
        installed_schedule().run(&mut world);
        assert_eq!(world.resource::<DisplayValue>().0, None);
        assert_eq!(world.resource::<Trace>().0, vec![None]);
    }

    #[test]
    fn a_green_helper_does_not_detect_an_omitted_system() {
        assert_eq!(percentage(3, 8), Some(37));
        let mut world = fixture();
        let mut incomplete = Schedule::default();
        incomplete.set_executor_kind(ExecutorKind::SingleThreaded);
        incomplete.add_systems(observe_display);
        incomplete.run(&mut world);
        assert_eq!(world.resource::<DisplayValue>().0, Some(99));
        assert_eq!(world.resource::<Trace>().0, vec![Some(99)]);
        assert_ne!(world.resource::<Trace>().0, vec![Some(37)]);
    }

    #[test]
    fn correct_final_display_can_hide_an_early_observer() {
        let mut world = fixture();
        let mut reversed = Schedule::default();
        reversed.set_executor_kind(ExecutorKind::SingleThreaded);
        reversed.add_systems((observe_display, project_selected).chain());
        reversed.run(&mut world);
        assert_eq!(world.resource::<DisplayValue>().0, Some(37));
        assert_eq!(world.resource::<Trace>().0, vec![Some(99)]);
        assert_ne!(world.resource::<Trace>().0, vec![Some(37)]);
    }
}

Know which kind of red you see

When a check fails, first locate how far execution got. A missing toolchain prevents the intended compilation; a compiler diagnostic prevents the test assertion from running. An assertion failure means the program did run and its observation disagreed with the expected result. The starter's todo! is another runtime failure with a known cause: you reached an unfinished body. These cases call for different repairs, even though they can all appear as a failed command.

A successful exit also needs interpretation. If a filter selects zero tests, none of the intended assertions ran. For a focused manual check, list the available test names before selecting the complete name with --exact. The following commands identify and run one precise integration check in this package:

cargo +1.93.1 test --locked -- --list
cargo +1.93.1 test --locked tests::installed_projection_uses_the_selected_row_before_observation -- --exact

That focused command should report one passed test. The course runner similarly checks that the canonical named tests were discovered and passed, so an empty selection cannot count as completion. The Rust Book's test-running chapter explains the filtering rules and harness output when you need to interpret another selection.

Write evidence that the broken program cannot satisfy

So far, the course supplied the assertions and you repaired the implementation. Now keep the implementation fixed and choose the evidence yourself. The starting test checks percentage(1, 2) == Some(50). It accepts the correct program, but it also accepts six deliberately defective versions, including one whose schedule never projects anything. That result gives us a concrete question for test design: what observation would make each wrong program disagree with the right one?

The test-design command runs your actual test file, so it differs from the implementation checker that substitutes canonical tests. It first requires your tests to pass against the correct program. It then compiles each of six wrong programs and runs the same tests against them. A defect counts as detected only when its program compiles and a named test fails. A compiler error, ignored test, or empty selection cannot show that an assertion distinguished the behavior.

python3 learning/scripts/evidence_practice.py prepare --dest work/evidence-test-design
python3 learning/scripts/evidence_practice.py check --file work/evidence-test-design/evidence_tests.rs

Hint: why final state alone lets the ordering defect survive

The reversed schedule records 99 and then updates the current display to 37. If your test checks only the final display, the wrong order passes. The trace is the evidence that the dependent observer saw the current value. Keep the stale starting value distinct from the expected result.

A browser claim needs browser evidence

The optional panel below lets you inspect that next boundary. Its projection and schedule execute a WebAssembly build of the exact Rust program checked by the local runner.

These contrasts come from Rust resources read by the host, rather than a percentage recalculated in JavaScript.

After editing the implementation, rerun the preview command and rebuild: an already compiled program cannot pick up that source change on its own. A failed check or build does not publish a replacement, and the course builder omits a preview whose checked source changed. An already open page still represents its displayed build until reloaded. As in the native implementation checker, canonical tests replace test edits in the practice copy during this build.

The same discipline applies when you return to current Moss. Pause, reset, and press Step three times at the maintenance-only checkpoint; the paired expectation is tick 3 and reserve 57. Record what that particular browser build actually shows. A still creature in a screenshot does not reveal whether its reserve was charged correctly, just as this native projection test cannot certify a separate Moss browser build.

If the browser result disagrees, trace the value inward from the displayed text to the projected resource, installed schedule, and helper inputs. Find the first boundary where expected and observed values diverge. That keeps the repair tied to evidence: rewriting correct arithmetic before discovering that its system never ran could add another defect while leaving the original one in place.

Carry a counterexample into the next review

Look once more at the fixture and name the wrong program each feature can expose. Why did we include an unselected sample, begin with stale 99, and preserve the observer's trace instead of checking only the final display? This is the reasoning you can carry into the next test you design.

Recall answer

The unselected sample exposes incorrect query selection or “take the first row.” The stale initial value exposes omitted projection and failure to clear unavailable data. The trace exposes an observer that ran before the update even when final state is correct.
