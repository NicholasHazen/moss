A selective Rust survey · 45 minutes

Accept asynchronous results at a tick boundary

You request one settings import, then replace it with another. The newer result arrives first, but the older worker is still running; meanwhile, a reset could make both answers belong to a previous world. Each worker may parse its input correctly and use memory safely while still delivering an answer the application must refuse.

Let delayed work finish without accepting a stale result

You'll implement receive, the boundary that checks a completion's run and request identity before staging its settings. We'll use controlled native workers to deliver results out of order, then follow an accepted result to the explicit tick that applies it. Replacement, cancellation and reset will each give us a way to withdraw permission before that commit.

Alongside the receiver, a small real future will help distinguish creating async work from driving it. You should finish able to explain which guarantees belong to Rust's transfer rules, which belong to application identity, and why neither a completed worker nor a valid staged value changes the world between ticks.

Isolated concurrency and async lab. Native worker threads parse owned strings into two toy settings. No network or file I/O is implemented, no biological rule runs, and no import is installed in live Moss. Controlled messages determine completion order without sleeps.

Put three boundaries in the design

Begin by separating the worker's job from the application's decision. The worker can say, “I finished parsing this request.” Only the application knows whether that request is still current. If it is, the application stages an accepted input for the next executed tick, where the authoritative settings change together. This gives us three moments to follow: completion produces data, acceptance grants permission to use it, and the tick commits it.

Use two small settings so a partial update will be easy to see. The cost must be positive and no greater than capacity, while capacity may be at most one hundred. We begin with cost two and capacity ten, and each successful import replaces the pair as one value. These are illustrative configuration values for the lab. Their relationship gives validation something meaningful to protect without adding a balance rule to Moss.

The worker owns the string it parses and sends back a Completion containing the request's run/request key and a Result. It never borrows the authoritative world. Consequently, finishing a parse cannot mutate the world on its own. The receiver can inspect the owned message and discard it if its key has become stale, even when its parsed settings are otherwise valid.

Separate concurrency, threads, and futures

Before implementing acceptance, clarify how delayed work gets to that boundary. Threads and futures can both appear in such a design, but they don't start or drive work in the same way. Our two imports can be in progress during overlapping periods, which is concurrency. Whether their parsing actually executes at the same instant is a separate question about parallelism. The lab uses native operating-system threads, but its correctness will depend on the messages we receive and accept, not on proving that the two processors were doing work simultaneously.

A Rust future is another way to represent work whose result may come later. Calling an async function returns that future; it does not start a thread by itself. As the Future reference describes, polling either produces the ready result or reports that the work is pending. A runtime normally arranges later polling after the task is woken, allowing other work to proceed while a result is unavailable.

We can inspect the language mechanism without introducing an I/O library. parse_ready has no suspension point or I/O, so its body can finish during its first poll. Constructing that future still does not execute the parse. One test uses an async block with a visible flag: the flag stays unchanged when the future is created and changes when the test polls it. This makes the distinction between creating work and driving it observable.

The supplied poll_ready probe pins the future and polls it once using a no-op waker. It is deliberately limited to our immediately ready example and panics if the result is pending. There is no mechanism here to arrange another poll after a socket or timer becomes ready, so this probe is not an executor for asynchronous I/O.

The native worker is what moves this parsing work away from the caller. Merely writing async around an expensive synchronous parse would not make the calculation yield: once polled, it would keep executing until it returned or reached a real suspension point. A larger import should choose its worker or runtime arrangement according to the I/O and CPU work involved. The acceptance rule we are about to write remains necessary whichever arrangement delivers the result.

Read Send and Sync as access constraints

Moving owned messages between native threads also asks Rust to check their transfer capabilities. Send permits transferring ownership of a value between threads, while Sync permits transferring a shared reference to it. The Rust Book's concurrency chapter explains these marker traits and how their automatic implementations depend on the constituent types.

Our completion contains owned, transferable data, and a compile-time assertion checks that it implements both traits. The worker closure moves its input string and channel sender into the new thread, so neither depends on a borrow of the caller's world. We need no unsafe implementations to establish that ownership relationship.

Those guarantees answer whether the data may cross a thread boundary safely. They cannot answer whether the user still wants request one after choosing request two. A correctly transferred old message could still overwrite the newer choice unless the receiver rejects it. Conversely, a future that is always driven on one thread may not need Send at all. Choose the transfer bounds for the execution platform and the identity checks for the application's meaning.

Use two identities to reject two kinds of staleness

Give each request a key containing both run identity and request number. Within one run, a new request supersedes the previous request and clears any result already staged for it. Reset starts a new run, where the numbering can begin again. Comparing only request one with request one would then confuse two different operations, so the run identity has to travel with the completion too.

The receiver first asks whether there is a current request. It then checks that the completion belongs to the authoritative run, matches the current request's whole key, and has not already been processed. If any check fails, the message is ignored. Once the checks succeed, receive marks the request completed before examining success or failure, ensuring that a duplicate message cannot later replace the first accepted outcome.

Now the contents of a current message can matter. Revalidate a successful settings value before storing it as AcceptedInput; receiving a typed value does not excuse the boundary from protecting the settings relationship. A current error becomes interface error state and leaves the world's settings unchanged. A stale error never reaches that stage, so it cannot erase a newer staged success or tell the user that their replacement request failed.

Cancellation follows the same idea by clearing the current request and any staged result. It does not have to terminate the operating-system thread to prevent a stale commit. The worker may still finish and send its owned message, but the receiver will find no current permission to accept it. Cooperative cancellation could avoid wasted work in a larger implementation; checking acceptance is still necessary when a completion races with cancellation.

Keep the authoritative tick synchronous

Even an accepted completion waits before changing the world. At the next tick, the application takes the staged input, checks its identity again, and assigns the settings pair before updating the completed-tick counter. The tick does not receive from a channel, block for a worker, or await a future. That keeps the state transition synchronous and lets an unfinished import remain separate from simulation advancement.

This choice also explains what pausing means. A valid result can be ready and staged while the world is paused, but it will not apply between ticks. If the user replaces or cancels the request before stepping, the staged result is cleared instead. Another application could choose an immediate application boundary; ours gives the pending change a named moment whose behavior we can test.

The same boundary matters for reproducible experiments. Wall-clock arrival time alone cannot tell a replay what the world accepted. A replay would need the accepted typed settings and the tick on which they were applied. This lab establishes that distinction without implementing an input journal or persistence.

Control completion order with messages

To test replacement reliably, make the newer completion arrive first on purpose. A standard channel carries the completions, and each worker waits on its own start gate. The driver releases the newer worker and receives its answer before releasing the older one. This gives the test an explicit sequence instead of asking a sleep duration to predict which thread will finish first.

The driver can block while coordinating this native test because it operates outside the authoritative tick. It also joins both workers before returning, making their completion and cleanup part of the fixture. A browser event loop would need an appropriate nonblocking integration; the blocking driver exists to control this test's order, not to prescribe that interface.

Predict the acceptance before editing

Follow three cases before editing the receiver. First, stage a valid result, then start a replacement request before the tick. Next, reset and create request one again before delivering the old run's request one. Finally, try a payload with cost three and a malformed capacity. In each case, separate what the worker produced from what the receiver may stage and what the tick may commit.

Hint 1: replacement invalidates completed work too

The latest-request rule applies to permission to commit, not merely work still in progress. Starting the new request clears the old staged input.

Hint 2: compare the entire identity and validate the entire value

A repeated request number belongs to a different run after reset. A malformed second field must reject the whole settings value rather than committing its valid first field.

Prediction answer

The replaced staged input never commits. The old run's request is ignored despite the reused number. The malformed payload produces a current error, and both authoritative settings retain their previous values.

Your edit is only receive, where those acceptance decisions meet. Prepare a separate practice file; the request lifecycle, worker gates, and synchronous tick are already supplied. That leaves the body responsible for rejecting stale or duplicate messages and staging only a valid current outcome.

Complete starter: async.rs
use std::future::Future;
use std::sync::mpsc::{self, Sender};
use std::task::{Context, Poll, Waker};
use std::thread::{self, JoinHandle};

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Key { run: u64, request: u64 }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Settings { cost: u32, capacity: u32 }
impl Settings {
    fn valid(self) -> bool { self.cost > 0 && self.cost <= self.capacity && self.capacity <= 100 }
}
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum ImportError { Malformed, InvalidSettings }
#[derive(Debug)]
struct Completion { key: Key, result: Result<Settings, ImportError> }
#[derive(Clone, Copy)]
struct AcceptedInput { key: Key, settings: Settings }
#[derive(Clone, Copy)]
struct Request { key: Key, completed: bool }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct World { run: u64, tick: u64, settings: Settings }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum Reception { Staged, Failed, Ignored }
struct App {
    world: World,
    next_request: u64,
    current: Option<Request>,
    staged: Option<AcceptedInput>,
    error: Option<ImportError>,
}
impl App {
    fn new() -> Self {
        Self { world: World { run: 1, tick: 0, settings: Settings { cost: 2, capacity: 10 } },
            next_request: 0, current: None, staged: None, error: None }
    }
    fn request(&mut self) -> Key {
        self.next_request = self.next_request.checked_add(1).expect("request identity exhausted");
        let key = Key { run: self.world.run, request: self.next_request };
        self.current = Some(Request { key, completed: false });
        self.staged = None;
        self.error = None;
        key
    }
    fn receive(&mut self, completion: Completion) -> Reception {
        let _ = completion;
        todo!("accept only the current uncompleted request and stage one validated value")
    }

    fn tick(&mut self) {
        let next_tick = self.world.tick.checked_add(1).expect("tick exhausted");
        if let Some(input) = self.staged.take() {
            if input.key.run == self.world.run && self.current.map(|request| request.key) == Some(input.key) {
                self.world.settings = input.settings;
                self.current = None;
            }
        }
        self.world.tick = next_tick;
    }
    fn cancel(&mut self) { self.current = None; self.staged = None; self.error = None; }
    fn reset(&mut self) {
        let run = self.world.run.checked_add(1).expect("run identity exhausted");
        self.cancel();
        self.next_request = 0;
        self.world = World { run, tick: 0, settings: Settings { cost: 2, capacity: 10 } };
    }
}
async fn parse_ready(payload: String) -> Result<Settings, ImportError> {
    let (cost, capacity) = payload.split_once(',').ok_or(ImportError::Malformed)?;
    let settings = Settings { cost: cost.parse().map_err(|_| ImportError::Malformed)?,
        capacity: capacity.parse().map_err(|_| ImportError::Malformed)? };
    if settings.valid() { Ok(settings) } else { Err(ImportError::InvalidSettings) }
}
// One poll of a known-ready lab future. This is not an I/O executor.
fn poll_ready<F: Future>(future: F) -> F::Output {
    let mut future = std::pin::pin!(future);
    let mut context = Context::from_waker(Waker::noop());
    match future.as_mut().poll(&mut context) {
        Poll::Ready(value) => value,
        Poll::Pending => panic!("this probe accepts only immediately ready futures"),
    }
}
fn worker(key: Key, payload: String, output: Sender<Completion>) -> (Sender<()>, JoinHandle<()>) {
    let (start, gate) = mpsc::channel();
    let handle = thread::spawn(move || {
        gate.recv().unwrap();
        let result = poll_ready(parse_ready(payload));
        output.send(Completion { key, result }).unwrap();
    });
    (start, handle)
}
fn newer_first(old: Key, new: Key) -> [Completion; 2] {
    let (send, receive) = mpsc::channel();
    let (old_gate, old_handle) = worker(old, "3,30".to_owned(), send.clone());
    let (new_gate, new_handle) = worker(new, "4,40".to_owned(), send);
    new_gate.send(()).unwrap();
    let newer = receive.recv().unwrap();
    old_gate.send(()).unwrap();
    let older = receive.recv().unwrap();
    new_handle.join().unwrap(); old_handle.join().unwrap();
    [newer, older]
}
fn completion(key: Key, cost: u32, capacity: u32) -> Completion {
    Completion { key, result: Ok(Settings { cost, capacity }) }
}
fn main() {
    let mut app = App::new();
    let old = app.request(); let new = app.request();
    let [newer, older] = newer_first(old, new);
    println!("received new={:?} old={:?}", app.receive(newer), app.receive(older));
    println!("before tick={} cost={} capacity={}", app.world.tick, app.world.settings.cost, app.world.settings.capacity);
    app.tick();
    println!("after tick={} cost={} capacity={}", app.world.tick, app.world.settings.cost, app.world.settings.capacity);
    app.reset();
    println!("after reset stale={:?} run={}", app.receive(completion(new, 4, 40)), app.world.run);
}

The complete acceptance boundary

The complete answer uses only the standard library. Read receive beside request, cancel, reset, and tick to follow how permission begins, ends, and becomes an applied value. Parsing and thread orchestration deliver a message to that state machine; no completed message directly assigns the world's settings.

Complete worked answer: async.rs
use std::future::Future;
use std::sync::mpsc::{self, Sender};
use std::task::{Context, Poll, Waker};
use std::thread::{self, JoinHandle};

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Key { run: u64, request: u64 }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Settings { cost: u32, capacity: u32 }
impl Settings {
    fn valid(self) -> bool { self.cost > 0 && self.cost <= self.capacity && self.capacity <= 100 }
}
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum ImportError { Malformed, InvalidSettings }
#[derive(Debug)]
struct Completion { key: Key, result: Result<Settings, ImportError> }
#[derive(Clone, Copy)]
struct AcceptedInput { key: Key, settings: Settings }
#[derive(Clone, Copy)]
struct Request { key: Key, completed: bool }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct World { run: u64, tick: u64, settings: Settings }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum Reception { Staged, Failed, Ignored }
struct App {
    world: World,
    next_request: u64,
    current: Option<Request>,
    staged: Option<AcceptedInput>,
    error: Option<ImportError>,
}
impl App {
    fn new() -> Self {
        Self { world: World { run: 1, tick: 0, settings: Settings { cost: 2, capacity: 10 } },
            next_request: 0, current: None, staged: None, error: None }
    }
    fn request(&mut self) -> Key {
        self.next_request = self.next_request.checked_add(1).expect("request identity exhausted");
        let key = Key { run: self.world.run, request: self.next_request };
        self.current = Some(Request { key, completed: false });
        self.staged = None;
        self.error = None;
        key
    }
    fn receive(&mut self, completion: Completion) -> Reception {
        let Some(request) = self.current.as_mut() else { return Reception::Ignored; };
        if completion.key.run != self.world.run || completion.key != request.key || request.completed {
            return Reception::Ignored;
        }
        request.completed = true;
        let result = completion.result.and_then(|settings| {
            if settings.valid() { Ok(settings) } else { Err(ImportError::InvalidSettings) }
        });
        match result {
            Ok(settings) => {
                self.staged = Some(AcceptedInput { key: completion.key, settings });
                self.error = None;
                Reception::Staged
            }
            Err(error) => {
                self.staged = None;
                self.error = Some(error);
                Reception::Failed
            }
        }
    }
    fn tick(&mut self) {
        let next_tick = self.world.tick.checked_add(1).expect("tick exhausted");
        if let Some(input) = self.staged.take() {
            if input.key.run == self.world.run && self.current.map(|request| request.key) == Some(input.key) {
                self.world.settings = input.settings;
                self.current = None;
            }
        }
        self.world.tick = next_tick;
    }
    fn cancel(&mut self) { self.current = None; self.staged = None; self.error = None; }
    fn reset(&mut self) {
        let run = self.world.run.checked_add(1).expect("run identity exhausted");
        self.cancel();
        self.next_request = 0;
        self.world = World { run, tick: 0, settings: Settings { cost: 2, capacity: 10 } };
    }
}
async fn parse_ready(payload: String) -> Result<Settings, ImportError> {
    let (cost, capacity) = payload.split_once(',').ok_or(ImportError::Malformed)?;
    let settings = Settings { cost: cost.parse().map_err(|_| ImportError::Malformed)?,
        capacity: capacity.parse().map_err(|_| ImportError::Malformed)? };
    if settings.valid() { Ok(settings) } else { Err(ImportError::InvalidSettings) }
}

        Poll::Pending => panic!("this probe accepts only immediately ready futures"),
    }
}

    let (start, gate) = mpsc::channel();

        gate.recv().unwrap();

    let (send, receive) = mpsc::channel();

    Completion { key, result: Ok(Settings { cost, capacity }) }
}

    let mut app = App::new();

Completion leaves the acceptance decision open

The old import can finish without overwriting the newer choice because its run/request key no longer grants acceptance. Owned messages make it safe to deliver and discard results; identity checks decide whether to stage them; the synchronous tick decides when accepted settings take effect. Cancellation can therefore prevent a commit even while the worker continues. Check that you can explain both limits: why transfer safety doesn't authorize an old result, and why the single-poll probe wouldn't drive a future that needs to wait for I/O.

Recall answers

Transfer safety says nothing about request identity. Cancellation removes acceptance permission even if work continues. A pending I/O future needs wakeup and further scheduling, which the known-ready probe intentionally does not provide.

The native tests follow actual worker threads in a controlled completion order and poll a real async future. They also check reset, replacement, cancellation, duplicate and stale errors, whole-value validation, and application at an executed tick. These results concern the native lab. A browser integration would still need platform and UI checks, including what it displays while a valid result waits for the user to step.
