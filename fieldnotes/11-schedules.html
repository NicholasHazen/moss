The ECS contract · 35 minutes

Give the observations an order

You add a “before” reading and an “after” reading to a counter update, expecting to see seven followed by eight. The counter does finish at eight in each of three schedules, but one trace says eight twice and another says seven twice. The arithmetic can be correct while both readings miss the moment they were meant to capture.

Isolated Bevy ECS 0.18.1 schedule lab. You will wire three prepared systems around one ordinary counter. This is not an energy formula, simulation tick implementation, or new biological rule. The lab changes no live Moss schedule, and NOW.md remains the active assignment.

Make before and after describe real moments

You'll wire three supplied systems into a schedule that records the old counter, increments it, and records the new value. We'll derive the two required ordering relationships, predict a second execution, and compare deliberately wrong schedules with the correct one. The useful result is both seven before and eight after; a final counter of eight alone cannot show that the observations happened where they belonged.

Safe access does not choose the right order

The previous lesson made reading a source and writing a preview safe by proving that their queries reached different entity sets. That gives each system valid access to its data. It leaves another question open: does an observer read that data before the change it is supposed to report, or afterwards? To make our two labels meaningful, we need to express those relationships between systems.

Keep the arithmetic small so we can follow that relationship directly. record_before reads the counter and appends a labeled observation; increment adds one to the counter; record_after reads the counter and appends its own observation. Both observers use the value they find in the world. If either one runs at the wrong time, it will faithfully record the wrong stage of the update rather than reconstructing the number we expected.

Bevy already knows that these systems cannot all access the counter at once. The observers request shared access to Counter, while increment requests mutable access. The observers also both write the trace. Those declarations let the executor prevent incompatible work from overlapping, but either observation can safely happen before or after the mutation. Safety therefore leaves several possible sequences, only one of which meets our reporting requirement.

Using a single-threaded executor makes the trace easier to follow because only one system runs at a time. It still leaves those possible sequences open. A system's name and its position in a registration tuple do not supply a guaranteed domain order without explicit dependencies, so changing the executor alone would leave our reporting requirement unstated.

Draw the two required edges

Start with what each observer needs to see. The “before” observer needs the old counter, so it must finish before increment runs. The “after” observer needs the new counter, so it must run after that mutation. These are the two edges shown below. If a test checks only the final eight, it cannot tell whether either edge was respected.

The labels are ordinary values appended by the observer functions. Calling a function record_before does not make Bevy move it earlier: if it executes after the increment, it records “Before 8.” The number accurately describes the state it read. It is our choice of schedule that failed to make the label true.

For this three-system sequence, .chain() adds the ordering constraints between successive systems in the tuple. The ordinary default prelude imports the configuration trait that supplies the method. Bevy 0.18.1's versioned schedule-configuration source describes the chain and the related before/after operations, which can express individual edges when a complete sequence is unnecessary.

A chain is a good fit here because every pair of neighboring steps has a reason to be ordered. A larger schedule may contain independent work as well. Named system sets and selected edges let you preserve that independence while stating the relationships the model relies on. Drawing the needed dependencies first makes it easier to distinguish a real requirement from an order added merely because the functions appeared next to each other.

Predict the next execution

Now run the correctly ordered schedule twice, beginning at seven and keeping the trace between runs. The first increment changes the resource in the world; building the schedule did not capture a private copy of its initial value. Use that fact to predict all four observations, especially the second “Before” reading.

Hint 1: the schedule owns instructions, not a copied initial counter

Each system reads the resources of the world passed to that execution. The first run leaves the counter at eight, so the next run begins from eight.

Hint 2: trace append order is part of the evidence

The helper does not clear the trace. Preserve both pairs in their actual sequence rather than sorting observations afterward.

Prediction answer

The trace is Before 7, After 8, Before 8, After 9. The final counter is nine. Sorting the trace would destroy some of the timing evidence; its vector order records the sequence of append operations.

Your edit is the body of observation_schedule, so you can focus on expressing those two edges. The three system bodies and world setup are already supplied. Create a single-threaded schedule, add the systems in their required chain, and return it. Reimplementing the counter calculation inside the factory would bypass the integration question the trace is meant to answer.

use bevy_ecs::{prelude::*, schedule::ExecutorKind};

#[derive(Resource)]
struct Counter(u32);

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum Phase { Before, After }

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Observation {
    phase: Phase,
    count: u32,
}

#[derive(Resource, Default)]
struct Trace(Vec<Observation>);

fn record_before(counter: Res<Counter>, mut trace: ResMut<Trace>) {
    trace.0.push(Observation { phase: Phase::Before, count: counter.0 });
}

fn increment(mut counter: ResMut<Counter>) {
    counter.0 = counter.0.checked_add(1).expect("counter overflow");
}

fn record_after(counter: Res<Counter>, mut trace: ResMut<Trace>) {
    trace.0.push(Observation { phase: Phase::After, count: counter.0 });
}

fn observation_schedule() -> Schedule {
    todo!("build a single-threaded schedule: before, increment, after")
}

fn world_at(count: u32) -> World {
    let mut world = World::new();
    world.insert_resource(Counter(count));
    world.init_resource::<Trace>();
    world
}

fn main() {
    let mut world = world_at(7);
    let mut schedule = observation_schedule();
    schedule.run(&mut world);
    schedule.run(&mut world);
    for observation in &world.resource::<Trace>().0 {
        println!("{:?} {}", observation.phase, observation.count);
    }
    println!("final={}", world.resource::<Counter>().0);
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn observations_bracket_one_real_mutation() {
        let mut world = world_at(7);
        observation_schedule().run(&mut world);
        assert_eq!(world.resource::<Trace>().0, vec![
            Observation { phase: Phase::Before, count: 7 },
            Observation { phase: Phase::After, count: 8 },

    }

    #[test]
    fn successive_runs_append_fresh_observations_in_execution_order() {
        let mut world = world_at(41);
        let mut schedule = observation_schedule();
        schedule.run(&mut world);
        schedule.run(&mut world);
        assert_eq!(world.resource::<Trace>().0, vec![
            Observation { phase: Phase::Before, count: 41 },
            Observation { phase: Phase::After, count: 42 },
            Observation { phase: Phase::Before, count: 42 },
            Observation { phase: Phase::After, count: 43 },

        assert_eq!(world.resource::<Counter>().0, 43);
    }

    #[test]

        observation_schedule().run(&mut correct);

Test meaning rather than scheduler luck

The expected trace gives us a claim to test: each observer saw the intended stage of the update. To see whether the checks can establish it, follow what they read and which wrong schedules they distinguish. The first test reads both observation values and their sequence after one execution. That gives each edge a visible consequence. The second test changes the starting value and executes the schedule twice, so a hard-coded pair of readings cannot satisfy it. In both cases, the assertions examine resources changed by the installed systems; they do not substitute a second helper calculation for the work we wanted to run.

To see why those observations matter, the final two tests construct deliberately wrong schedules with explicit ordering. One increments before both observations; the other increments after both. Each still reaches the correct final counter, but each produces a different trace. These counterexamples demonstrate a concrete mistake the trace catches and a counter-only assertion misses.

Removing .chain() is a less reliable way to demonstrate the mistake. An unconstrained scheduler might happen to choose the desired order in your current build, so the trace could still pass on that run. The explicitly wrong schedules make the counterexample reproducible. When reviewing the real configuration, also look for the declared dependencies: an observed success alone cannot establish an ordering promise the program never made.

The same reasoning explains why switching executors would not repair the missing relationship. The 0.18.1 executor reference describes the available execution modes, but the application still has to say which valid system must precede another. This lab uses one thread to simplify observation and explicit edges to establish meaning.

Registration and order are separate responsibilities

There are two places to check when expected work is absent. First, the function must actually be added to the schedule you run; defining it in a Rust module does not arrange an execution. Then its dependencies must be configured within that schedule. An ordering expression in another schedule cannot organize this run just because it names the same function.

When using before or after, find both ends of the relationship and confirm that the referenced systems or sets are present in the relevant schedule. Mentioning a function as the other end of an edge does not replace registering its work. Our add_systems call and chain put registration and order together, making both responsibilities visible in one place.

You can trace the same relationship in Moss's current crates/moss-sim/src/simulation.rs: its installed chain runs maintenance before complete_tick. The completed-tick count consequently describes scheduled work that has already finished. The prepared movement adapter is still absent at this checkpoint. It joins that sequence only after review of the active exercise and the explicit transition described in its guide; an isolated helper passing does not install its system.

The vector is enough for this short experiment because we execute the schedule only once or twice. Keeping observations indefinitely in a browser would introduce further requirements: identities to say what was observed, a retention limit, and coverage labels to explain what remains. Correct timing gives a record its meaning, but it does not by itself make an unlimited journal a suitable design.

Give each observation its place in the schedule

Return to the original counter that reached eight under every schedule. Explain why its final value was insufficient, using the access declarations, the two ordering edges, and the collected trace. Each supplies a different part of the explanation.

Recall answer

Access declarations constrain which work can safely overlap. The chain supplies required relative execution order. The trace records the values actually observed during this specific run. A final counter alone could agree while either observation phase was misplaced.

The schedule methods, chain semantics, and executor choice were checked against cached Bevy ECS 0.18.1 source and its versioned references. The lesson's native checks exercise a miniature installed schedule; they do not execute the real Moss schedule or verify browser presentation. No claim about deferred commands is implied by ordinary resource mutation here.

The readings can now say seven and eight for a reason we have expressed and checked: one observer runs before the mutation and the other after it. The next module keeps that observation question but changes how the mutation happens. A structural change queued through commands is applied later, so even a correctly ordered observer needs to run on the right side of that application point.
