Consume once, even before removal

Two hunters reach the same prey. The first succeeds and queues its removal, but the prey's entity is still present when the second hunter gets a turn. We need one capture to produce one reward, and we need the prey to miss its own later action.

Make a capture take effect before cleanup

You'll implement claim, combining the finite meal's accounting with the terminal transition's eligibility check. A supplied Bevy schedule will resolve both hunters, try the prey's action, and inspect the result while deferred removal is still pending. Leaving the entity present makes the immediate availability change visible.

By the end, you should be able to show why only one hunter receives a reward, why a rejected claim leaves both participants unchanged, and why the consumed prey performs no later action. We'll then apply the queued cleanup and check what remains: one owned interaction record, independent of the entity's continued existence.

This isolated Bevy ECS 0.18.1 lab proposes a whole-prey meal at same-cell contact, converting biomass to reserve one for one only when the entire gain fits. These teaching rules don't activate hunting, death, or movement in live Moss.

Combine a transfer with a terminal transition

Finite meals made two consumers share one current supply, while terminal history stopped a dead animal from acting before cleanup. A hunt brings both concerns into one accepted interaction. The hunter gains reserve, the prey loses biomass and eligibility, and an owned record explains the change.

Our hunters have stable IDs 9 and 2. Each starts with zero reserve and capacity ten, and both target prey 40 at cell zero. The prey contains three biomass units. We spawn hunter 9 first but resolve by ascending stable ID, so hunter 2 gets the first opportunity. Its successful capture should leave nothing for hunter 9 to receive.

This meal also differs deliberately from eating part of a patch. Our terminal policy consumes the whole prey, so all three units must fit. If a hunter has room for only one, we reject before claiming anything. Otherwise, accepting the kill and crediting one would imply a discarded remainder that the model never accounted for.

The ID priority makes this small contest repeatable. It doesn't show fairness or real predator behavior: lower IDs keep winning otherwise identical contests. Once accounting and eligibility are established, another priority policy can be compared against them without confusing a change of winner with a double reward.

Leave a rejected prey available

A hunter that cannot accept the whole meal must leave the next hunter's opportunity intact. We'll establish every condition before claiming the prey, starting when the resolver locates the hunter's selected prey by stable ID. If that identity is missing, it doesn't redirect the action toward another animal. The claim helper then checks that the hunter is alive, the prey remains available with positive biomass, both occupy the same cell, and the hunter's reserve is valid.

A valid reserve lets us calculate room as capacity minus reserve. The full biomass must fit in that room before any participant changes. This matters for the order of the contest: if hunter 2 starts at nine of ten units, rejecting its three-unit meal must leave prey 40 available for hunter 9.

After acceptance, the helper computes the new reserve with checked addition. It then writes three connected changes: the prey becomes unavailable, its biomass becomes zero, and the hunter receives the full gain. The returned Some(gain) lets the caller record those actual units and queue structural cleanup.

Rejected attempts return None. That intentionally combines the reasons in this focused lab; an inspector could use the named rejection style from the meal lesson if it needed to explain each one. Whatever return type we choose, the failed attempt must leave both participants unchanged so another eligible action can still resolve correctly.

Make unavailability visible immediately

Commands::despawn requests removal through a command buffer. While that command is pending, another query can still find the prey's components. The immediately written available field is therefore the state that prevents a second capture: hunter 9 reads the change made by hunter 2 before attempting its own claim.

Queuing a Dead marker wouldn't automatically solve the timing problem. If its insertion were still pending, later systems couldn't use it to exclude the prey yet. A marker can serve another design well, but its visibility must match the moment at which the actor loses permission. Here the component field changes at the accepted transaction.

The prey's action system illustrates the same distinction. Its query still finds entities with Prey, then checks availability before incrementing their action counts. The consumed prey remains present during this experiment but performs zero actions. Query membership answers whether the data exists; the eligibility field answers whether this rule may act on it.

We need to check the schedule as well as the helper. Even a correct claim would permit a different tick outcome if prey action ran first. Conversely, the intended phase order couldn't prevent duplicate rewards if claim left availability unchanged. The next part of the fixture makes both promises observable.

Keep the entity present long enough to inspect it

The schedule chains hunt resolution, prey action, and observation of pending state. We also select the single-threaded executor, but the chain is what states our semantic order. The observation should find prey 40 still present, with zero biomass, unavailable, and an action count of zero.

To expose that intermediate state, the lab turns off automatic intermediate deferred application and final deferred application. Bevy 0.18.1 supports automatic application along ordering dependencies and at the end of a schedule; allowing cleanup to happen there would hide the state we're investigating. These settings serve this experiment rather than prescribe how every schedule should be configured.

After schedule.run, the program prints the pending observation and then calls schedule.apply_deferred on that same schedule. Its systems own the queued commands. Calling a different schedule wouldn't flush those command buffers and wouldn't complete this cleanup.

Checking only the last row wouldn't establish why the second reward or prey action was prevented. Holding cleanup open lets the tests show that eligibility changed while the entity was still accessible.

Record both participants in the same event

Cleanup will remove the prey's components, so the accepted interaction needs an explanation that belongs to neither live participant. The capture records run seven, tick one, prey ID 40, hunter ID 2, and the three units gained. A future biography for either participant can refer to this interaction. Producing separate “matching” events for each biography would introduce another opportunity for their identities, times, or amounts to disagree.

These are application IDs rather than retained ECS handles. Handles help the resolver access current entities; owned run and actor identities keep the record interpretable after despawn. The fixture assumes unique hunter and prey IDs within the run and assigns separate roles. It doesn't define role changes or cannibalism.

The journal is a short vector because this fixture performs only a few controlled resolutions. A long-running world would need the previous lesson's bounded retention and visible coverage around these records too. Pursuit, injury, and escape also remain outside this one-contact transaction.

Try another claim before cleanup

Predict both hunter reserves, terminal-record count, and prey action count after the schedule runs but before commands are applied. Then run that schedule again with cleanup still pending. Finally, start a fresh fixture where hunter 2 has room for only one unit and decide who receives the three-unit prey.

Hint 1: read the changed field

The later hunter and repeated execution both encounter the prey's current unavailability. Its entity can remain present without becoming eligible for another reward.

Hint 2: follow rejection before mutation

The whole meal must fit. Hunter 2's insufficient-capacity attempt leaves the prey available for the next hunter.

Prediction answer

In the ordinary fixture, hunter 2 gains three, hunter 9 gains zero, one terminal event exists, and the prey performs zero actions. Repeating resolution before cleanup adds nothing. In the capacity fixture, hunter 2 stays at nine and hunter 9 gains the prey's three units instead.

Complete starter: predation.rs
use bevy_ecs::prelude::*;
use bevy_ecs::schedule::{ExecutorKind, ScheduleBuildSettings};

#[derive(Component, Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord)]
struct Id(u32);
#[derive(Component)]
struct Hunter { target: Id, cell: i32, reserve_units: u32, capacity_units: u32, alive: bool }
#[derive(Component)]
struct Prey { cell: i32, biomass_units: u32, available: bool, actions: u32 }
#[derive(Resource)]
struct Moment { run: u32, tick: u64 }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Terminal { run: u32, tick: u64, prey: Id, hunter: Id, gained_units: u32 }
#[derive(Resource, Default)]
struct Journal(Vec<Terminal>);
#[derive(Resource, Default)]
struct Audit { pending: Vec<(Id, bool, u32, u32)>, acted: Vec<Id> }

fn claim(prey: &mut Prey, hunter: &mut Hunter) -> Option<u32> {
    let _ = (prey, hunter);
    todo!("validate the whole-prey transfer, then immediately claim and credit it")
}

fn resolve_hunts(
    mut commands: Commands,
    moment: Res<Moment>,
    mut hunters: Query<(Entity, &Id, &mut Hunter)>,
    mut prey_query: Query<(Entity, &Id, &mut Prey)>,
    mut journal: ResMut<Journal>,
) {
    let mut order: Vec<(Id, Entity)> = hunters.iter().map(|(entity, id, _)| (*id, entity)).collect();
    order.sort_by_key(|(id, _)| *id);
    for (_, entity) in order {
        let (_, hunter_id, mut hunter) = hunters.get_mut(entity).unwrap();
        for (prey_entity, prey_id, mut prey) in &mut prey_query {
            if *prey_id != hunter.target { continue; }
            if let Some(gained_units) = claim(&mut prey, &mut hunter) {
                journal.0.push(Terminal { run: moment.run, tick: moment.tick,
                    prey: *prey_id, hunter: *hunter_id, gained_units });
                commands.entity(prey_entity).despawn();
            }
            break;
        }
    }
}
fn prey_action(mut prey_query: Query<(&Id, &mut Prey)>, mut audit: ResMut<Audit>) {
    for (id, mut prey) in &mut prey_query {
        if !prey.available { continue; }
        prey.actions = prey.actions.checked_add(1).expect("action count exhausted");
        audit.acted.push(*id);
    }
}
fn observe_pending(prey_query: Query<(&Id, &Prey)>, mut audit: ResMut<Audit>) {
    audit.pending = prey_query.iter().map(|(id, prey)|
        (*id, prey.available, prey.biomass_units, prey.actions)).collect();
    audit.pending.sort_by_key(|row| row.0);
}
fn hunt_schedule() -> Schedule {
    let mut schedule = Schedule::default();
    schedule.set_executor_kind(ExecutorKind::SingleThreaded);
    schedule.set_build_settings(ScheduleBuildSettings {
        auto_insert_apply_deferred: false, ..Default::default()
    });
    schedule.set_apply_final_deferred(false);
    schedule.add_systems((resolve_hunts, prey_action, observe_pending).chain());
    schedule
}
fn fixture(order: [u32; 2]) -> (World, Entity) {
    let mut world = World::new();
    world.insert_resource(Moment { run: 7, tick: 1 });
    world.init_resource::<Journal>();
    world.init_resource::<Audit>();
    for id in order {
        world.spawn((Id(id), Hunter { target: Id(40), cell: 0, reserve_units: 0,
            capacity_units: 10, alive: true }));
    }
    let prey = world.spawn((Id(40), Prey { cell: 0, biomass_units: 3,
        available: true, actions: 0 })).id();
    (world, prey)
}
fn reserves(world: &mut World) -> Vec<(Id, u32)> {
    let mut rows: Vec<_> = world.query::<(&Id, &Hunter)>().iter(world)
        .map(|(id, hunter)| (*id, hunter.reserve_units)).collect();
    rows.sort_by_key(|row| row.0);
    rows
}
fn main() {
    let (mut world, _) = fixture([9, 2]);
    let mut schedule = hunt_schedule();
    schedule.run(&mut world);
    println!("reserves={:?}", reserves(&mut world));
    println!("pending={:?}", world.resource::<Audit>().pending);
    println!("terminal records={}", world.resource::<Journal>().0.len());
    schedule.apply_deferred(&mut world);
    println!("prey after cleanup={}", world.query::<&Prey>().iter(&world).count());
}

Inspect the real schedule

The complete reference below uses the course's pinned Bevy ECS dependency. Its mutable queries write different component types, Hunter and Prey, while both read identity. Follow a successful claim into the journal write and queued despawn, then continue through prey action to the pending observation.

Complete worked answer: predation.rs
use bevy_ecs::prelude::*;
use bevy_ecs::schedule::{ExecutorKind, ScheduleBuildSettings};

#[derive(Component, Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord)]
struct Id(u32);
#[derive(Component)]
struct Hunter { target: Id, cell: i32, reserve_units: u32, capacity_units: u32, alive: bool }
#[derive(Component)]
struct Prey { cell: i32, biomass_units: u32, available: bool, actions: u32 }
#[derive(Resource)]
struct Moment { run: u32, tick: u64 }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Terminal { run: u32, tick: u64, prey: Id, hunter: Id, gained_units: u32 }
#[derive(Resource, Default)]
struct Journal(Vec<Terminal>);
#[derive(Resource, Default)]
struct Audit { pending: Vec<(Id, bool, u32, u32)>, acted: Vec<Id> }

fn claim(prey: &mut Prey, hunter: &mut Hunter) -> Option<u32> {
    if !hunter.alive || !prey.available || prey.biomass_units == 0
        || hunter.cell != prey.cell || hunter.reserve_units > hunter.capacity_units {
        return None;
    }
    let gain = prey.biomass_units;
    let room = hunter.capacity_units - hunter.reserve_units;
    if gain > room { return None; }
    let reserve = hunter.reserve_units.checked_add(gain).expect("gain fits validated room");
    prey.available = false;
    prey.biomass_units = 0;
    hunter.reserve_units = reserve;
    Some(gain)
}

fn resolve_hunts(
    mut commands: Commands,
    moment: Res<Moment>,
    mut hunters: Query<(Entity, &Id, &mut Hunter)>,
    mut prey_query: Query<(Entity, &Id, &mut Prey)>,
    mut journal: ResMut<Journal>,
) {
    let mut order: Vec<(Id, Entity)> = hunters.iter().map(|(entity, id, _)| (*id, entity)).collect();
    order.sort_by_key(|(id, _)| *id);
    for (_, entity) in order {
        let (_, hunter_id, mut hunter) = hunters.get_mut(entity).unwrap();
        for (prey_entity, prey_id, mut prey) in &mut prey_query {
            if *prey_id != hunter.target { continue; }
            if let Some(gained_units) = claim(&mut prey, &mut hunter) {
                journal.0.push(Terminal { run: moment.run, tick: moment.tick,
                    prey: *prey_id, hunter: *hunter_id, gained_units });
                commands.entity(prey_entity).despawn();
            }
            break;
        }
    }
}
fn prey_action(mut prey_query: Query<(&Id, &mut Prey)>, mut audit: ResMut<Audit>) {
    for (id, mut prey) in &mut prey_query {
        if !prey.available { continue; }
        prey.actions = prey.actions.checked_add(1).expect("action count exhausted");
        audit.acted.push(*id);
    }
}
fn observe_pending(prey_query: Query<(&Id, &Prey)>, mut audit: ResMut<Audit>) {
    audit.pending = prey_query.iter().map(|(id, prey)|
        (*id, prey.available, prey.biomass_units, prey.actions)).collect();
    audit.pending.sort_by_key(|row| row.0);
}
fn hunt_schedule() -> Schedule {
    let mut schedule = Schedule::default();
    schedule.set_executor_kind(ExecutorKind::SingleThreaded);
    schedule.set_build_settings(ScheduleBuildSettings {
        auto_insert_apply_deferred: false, ..Default::default()
    });
    schedule.set_apply_final_deferred(false);
    schedule.add_systems((resolve_hunts, prey_action, observe_pending).chain());
    schedule
}
fn fixture(order: [u32; 2]) -> (World, Entity) {
    let mut world = World::new();
    world.insert_resource(Moment { run: 7, tick: 1 });
    world.init_resource::<Journal>();
    world.init_resource::<Audit>();
    for id in order {
        world.spawn((Id(id), Hunter { target: Id(40), cell: 0, reserve_units: 0,

    }
    let prey = world.spawn((Id(40), Prey { cell: 0, biomass_units: 3,
        available: true, actions: 0 })).id();

}
fn reserves(world: &mut World) -> Vec<(Id, u32)> {
    let mut rows: Vec<_> = world.query::<(&Id, &Hunter)>().iter(world)

    rows.sort_by_key(|row| row.0);

}

One claim settles the contest

The opening contest now resolves without depending on immediate removal. Hunter 2's accepted claim changes the prey's eligibility and supply before either hunter 9 or the prey itself gets another opportunity. Cleanup can follow at its chosen boundary because it no longer carries responsibility for preventing another action.

Recall why the checks precede the claim

Deferred insertion and despawn may both remain unapplied while other work runs, so the immediate availability change supplies this lab's eligibility boundary. A hunter that cannot hold the full gain must reject before that change, preserving the prey for another eligible hunter.
