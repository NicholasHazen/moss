A proposal is not yet a move

Begin with a small case you can follow by hand: current cell (2, 2), target (4, 4), reserve 59, and a price of two energy units per cell. The selected rule moves along x before y and allows at most one cardinal step per call. Its candidate next position is therefore (3, 2), one cell away at a cost of two. We can work out that proposal before deciding to accept it.

The function receives &mut Position, which gives it access to the caller's actual position. Writing through that reference changes the world immediately. Instead, copy the small Position value into a local next and calculate the proposed step there. The local value can change while the caller stays at (2, 2). If validation fails, discarding that copy is enough; if it succeeds, a later write through the reference commits the proposal.

Now lower the starting reserve to one. The same proposed step costs two, so the accepted distance must be zero and both position and reserve must remain unchanged. If you moved the caller first, returning zero would only report a rejection after the move had already happened. Keeping the proposal separate gives rejection the behavior the return value promises.

The earlier distinction between requested and actual payment matters here. Maintenance spends what the reserve can supply and saturates at zero. Movement accepts a step only when the whole price can be paid. A saturating subtraction would still produce a valid number for the one-unit animal, but it would let that animal travel without funding the step. The selected rule tells us which arithmetic operation is appropriate.

Validate the coordinates before committing

Affordability is only one reason to reject the proposal. Before committing a paid step, we also need to establish that the coordinates describe a valid move within this world. In a world of width 32, x may be zero through 31; a negative x or x equal to 32 is outside the world. Check both the current position and the target before changing either mutable value. A valid destination cannot make an invalid starting position a sound basis for movement, which is why the canonical answer validates before committing.

We can also use the guarantees already established by construction. WorldConfig limits dimensions to 8 through 256, so converting those dimensions to signed coordinates is safe. The helper then uses checked arithmetic for distance and cost. Under this one-cell policy, the distance is zero or one; calculating it explicitly still makes the units and the assumptions behind payment visible.

A call represents one opportunity to take a cardinal step. The rule does not include diagonals, obstacles, pathfinding, or several cells of travel at once. That small unit of work is deliberate: the ECS adapter calls the helper for eligible animals, and later ticks provide later opportunities. Adding a loop here would change what one call means and what its tests are meant to establish.

Prediction: what should happen when only y differs?

If the start is (4, 2) and the target is (4, 4), x already agrees. The next proposal is (4, 3). With exactly two reserve units and a rate of two, it commits that position and leaves zero. The else if in the canonical answer chooses one axis, so a call cannot move diagonally.

The adapter resolves the target now

The helper knows a destination position, but the ECS adapter has to find a currently eligible destination first. Fern carries Meadow's stable ID in her authored target. The prepared move_to_food system resolves that ID against current patches and requires positive biomass before calling the helper. If the patch is missing or empty, no movement call occurs and no travel is charged.

The target ID can remain stored even if Meadow changes, just as the snapshot lookup lesson retained a report about an earlier world. That earlier report may be accurate for its observation time while no longer answering whether Fern may act now. The adapter performs the current lookup at the action boundary because neither a remembered target nor a displayed row supplies that fact.

The query also decides which animals are eligible to attempt movement. It requires FoodTarget, mutable Position, mutable Energy, and the Creature marker. Flint has position and energy but no authored food target, so the system does not visit him. That difference comes from his component set; the system does not branch on his nickname or fox species.

To read a patch position while mutating an animal position, the queries must describe disjoint access. The patch query excludes creatures, and the mutable query requires them, following the same reasoning as the preview lesson. The adapter copies Meadow's small position into the helper, then borrows Fern's position and energy for the possible change. The copy supplies the destination without creating another authoritative world.

A green helper is one checkpoint

After replacing the function body, rerun the exact focused test and read its assertions together. Returned distance, final position, and final reserve describe different consequences of one decision. They must agree: reporting a traveled cell without moving should fail, and the low-energy and invalid-coordinate cases must preserve both mutable values. This is the helper's contract before any system is installed.

A passing helper is the point to request the review specified in NOW.md; the canonical guide provides a short review request. That review checks the selected rule and deliberately connects the prepared adapter to the installed schedule. Until this transition is performed in your working checkout, the correct helper remains available code rather than active movement.

The intended schedule runs maintenance, then movement, then tick completion. Consider an animal starting a tick with reserve two: maintenance spends one, leaving too little for a two-unit step. Movement must therefore reject it. Reversing the first two systems would allow a different outcome, even if both bodies were individually correct. Explicit ordering makes this chosen meaning part of the installed program.

Two prepared installed-world tests are ignored at the current checkpoint. During reviewed activation, they become checks of target resolution, affordability after maintenance, the journey, and reset. Those tests reach relationships the helper cannot see, including whether its adapter was installed at all. The course's Rust terrarium currently shows the maintenance-only checkpoint, where Fern remains stationary despite the prepared movement code.

Across the first nine ticks, Fern pays nine maintenance units and nine steps at two units each, leaving 60 − 9 − 18 = 33. On tick ten she is already at the target, so only maintenance is charged. Arriving on a patch does not yet consume its food: eating is a separate proposed rule. Unchanged biomass is therefore consistent with this completed movement journey.

Debug the tenth tick: why might the reserve fall to 30 instead?

A three-unit decrease would suggest that two travel units were charged despite zero actual distance, assuming maintenance remains one. Inspect the helper's returned distance and the location of payment before changing the UI. A retained target tells you the intended destination; it does not prove a cell was traveled.
