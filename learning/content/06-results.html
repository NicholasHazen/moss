Suppose an inspector form asks for a report beginning at tick 12 and covering three ticks. We can turn that into a window containing 12, 13, and 14. Now change the count to zero. The text still parses as a number, but the request no longer satisfies the report's rules.

You'll implement a constructor in the isolated results.rs lab, then compare it with Moss's existing configuration code. The 4,096-tick limit is an illustrative reporting policy. This exercise doesn't add a live form or change the movement task in NOW.md.

Turn a request into a value callers can trust

You'll build a constructor that either produces a valid reading window or explains why it cannot. We'll separate parsing from the report's policy, follow errors through the supplied parsing function, and test both accepted and rejected endpoints. That gives a request for ticks 12 through 14 a dependable representation, while keeping a zero count or an overflowing endpoint from becoming a misleading report.

Follow a request from text to meaning

A form begins with strings, so our first question is whether each input can be read as the integer type we've chosen. “Three” can't be parsed as a u64; “3” can. But parsing only gives us a representable number. It doesn't know what our report considers a useful count, which is why “0” gets through this first step.

We'll give the report an explicit policy: a requested window must contain at least one tick and at most 4,096. Its stored endpoints will be an inclusive start and an exclusive end. Starting at 12 with a count of 3 therefore produces an end of 15, describing ticks 12, 13, and 14. This convention makes the count equal to end minus start and lets adjacent windows meet without sharing a tick.

The field name end_tick_exclusive keeps that convention visible in code. It also belongs in the explanation a reader sees. Two unlabeled endpoints would leave us wondering whether 15 was included, and a correct calculation wouldn't prevent the resulting off-by-one misunderstanding.

There's one more numerical constraint: the exclusive end must fit in u64. Even a valid count of one can overflow if the start is already the maximum. We'll check the count first and the addition second, giving each failure its own explanation.

A value that passes these checks means “this is a well-formed requested window.” It doesn't establish that its ticks have happened or that observations were retained for all of them. When we build history, we'll compare the request with available coverage. Keeping those questions separate continues the previous lesson's distinction between a valid identity and an available reading.

Give the caller enough information to respond

The target lesson used Option when asking whether a selected ID was present. For a rejected form request, the caller also needs a reason. Result<ReadingWindow, WindowError> describes the two outcomes: Ok(window) carries the accepted value, and Err(reason) carries an explanation of failure.

We'll make WindowError an enum, using the same data-bearing alternatives we used for target status. An invalid-integer error identifies the field. A count-range error keeps the rejected count. An end-overflow error keeps the start and count that couldn't be combined. The caller can match the variant and decide what to show beside the input.

The integer error deliberately groups malformed text, negative values, and text larger than the unsigned type can hold. That is enough detail for this lab to identify the field that needs attention. It doesn't retain the original text or the parser's full diagnostic. A form could keep the entered text separately; an import tool might preserve the underlying error as well. Result can carry whichever error type the caller needs.

The Rust Book's recoverable-error chapter explains how these unsuccessful outcomes travel as values. That fits a form naturally: invalid input is something to report so the user can revise it, rather than a reason to pretend a report was successfully created.

Make accepted windows dependable

We want the same rules to apply whether numbers come from a form, a file, or a test. We'll put them in ReadingWindow::new, a constructor that accepts numeric inputs. It validates the count, checks the endpoint addition, and constructs the window only when both succeed. A failed check returns an error without supplying a partially validated value.

This gives the later getters a useful fact to rely on. In a window produced by the constructor, the end is greater than the start and their difference is between 1 and 4,096. The tick_count getter can therefore subtract them directly. It doesn't need to repeat the count and overflow checks whenever someone asks how many ticks were requested.

The fields are private, but Rust's privacy boundary needs a precise reading here. Code outside the owning module and its descendants can't directly access private fields. In this single-file lab, code in the defining module or a descendant module still could construct them itself. Using the constructor is therefore a local convention here; the next lesson will use modules to make the intended path enforceable for callers across that boundary.

Keeping fields unchanged through the getter interface preserves the relationship established at construction. Direct construction inside the allowed module still carries responsibility for that relationship. “Private” doesn't mean that one particular method is the only code capable of touching a field.

We also need to decide what rejection means. Clamping a request for 4,097 ticks to 4,096 would silently change what the caller asked for. This constructor rejects the unsupported count instead. An interface could offer a suggested correction afterward, but the accepted value should describe a request the caller actually agreed to make.

Read the validation pipeline

The constructor gives us one place to enforce the policy for numeric inputs; the form still begins with text. The supplied parse_window function connects those text inputs to the constructor. It parses the start, then the count, and finally calls ReadingWindow::new. Keeping that final call matters: successfully parsing two integers mustn't bypass the report's range policy.

After each parse, map_err converts the parser's error into our field-specific WindowError. The following question mark either yields the successful integer for continued work or returns the error from parse_window. It saves us an explicit match for propagation. It doesn't log a message, retry, or decide which correction the user should make.

Inside the constructor, checked_add presents a slightly different shape: it returns an Option, because its failed result carries no reason of its own. We know what failure means at this point, so ok_or turns None into EndOverflow with the relevant inputs. A question mark then propagates that error in the same way as the parsing failures.

The Option conversion reference and Result error-mapping reference describe these transformations. In this example, they let several operations speak the same error language. The final constructor call already returns the right Result, so parse_window returns it directly.

Write the constructor's checks

Try the accepted and rejected edges before implementing them. Starting at 12, counts of 1 and 4,096 should succeed, while 4,097 should fail. For the endpoint, compare a count of one starting at u64::MAX - 1 with the same count starting at u64::MAX. Only the first can represent its exclusive end.

Hint 1: include both supported count endpoints

Check the inclusive range from 1 through MAX_WINDOW_TICKS. Outside it, return CountOutOfRange carrying the rejected count.

Hint 2: construct only after successful addition

Use checked_add for the endpoint. Convert its missing result into EndOverflow and return that error before constructing the window.

Prediction answer

Counts 1 and 4,096 are accepted, while 4,097 is rejected. Maximum minus one plus one reaches the exact representable endpoint and succeeds. Maximum plus one doesn't fit. Accepting the exact boundary matters just as much as rejecting the value beyond it.

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct ReadingWindow {
    start_tick: u64,
    end_tick_exclusive: u64,
}

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum WindowError {
    InvalidInteger { field: &'static str },
    CountOutOfRange { tick_count: u64 },
    EndOverflow { start_tick: u64, tick_count: u64 },
}

impl ReadingWindow {
    fn new(start_tick: u64, tick_count: u64) -> Result<Self, WindowError> {
        let _ = (start_tick, tick_count);
        todo!("validate the count, check the end, then construct the window")
    }

    fn start_tick(self) -> u64 { self.start_tick }
    fn end_tick_exclusive(self) -> u64 { self.end_tick_exclusive }
    fn tick_count(self) -> u64 { self.end_tick_exclusive - self.start_tick }
}

fn parse_window(start: &str, count: &str) -> Result<ReadingWindow, WindowError> {
    let start_tick = start.parse::<u64>()
        .map_err(|_| WindowError::InvalidInteger { field: "start tick" })?;
    let tick_count = count.parse::<u64>()
        .map_err(|_| WindowError::InvalidInteger { field: "tick count" })?;
    ReadingWindow::new(start_tick, tick_count)
}

const MAX_WINDOW_TICKS: u64 = 4096;

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct ReadingWindow {
    start_tick: u64,
    end_tick_exclusive: u64,
}

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum WindowError {
    InvalidInteger { field: &'static str },
    CountOutOfRange { tick_count: u64 },
    EndOverflow { start_tick: u64, tick_count: u64 },
}

impl ReadingWindow {
    fn new(start_tick: u64, tick_count: u64) -> Result<Self, WindowError> {
        if !(1..=MAX_WINDOW_TICKS).contains(&tick_count) {
            return Err(WindowError::CountOutOfRange { tick_count });
        }
        let end_tick_exclusive = start_tick.checked_add(tick_count)
            .ok_or(WindowError::EndOverflow { start_tick, tick_count })?;
        Ok(Self { start_tick, end_tick_exclusive })
    }

    fn start_tick(self) -> u64 { self.start_tick }
    fn end_tick_exclusive(self) -> u64 { self.end_tick_exclusive }
    fn tick_count(self) -> u64 { self.end_tick_exclusive - self.start_tick }
}

fn parse_window(start: &str, count: &str) -> Result<ReadingWindow, WindowError> {
    let start_tick = start.parse::<u64>()
        .map_err(|_| WindowError::InvalidInteger { field: "start tick" })?;
    let tick_count = count.parse::<u64>()
        .map_err(|_| WindowError::InvalidInteger { field: "tick count" })?;
    ReadingWindow::new(start_tick, tick_count)
}

Carry the accepted value forward

The request for zero ticks now has a useful outcome. Parsing recognizes the number, the constructor rejects its meaning for this report, and the caller receives the count-range reason. For a valid request, the caller instead receives a window whose getters can rely on the checks already performed.

Recall why the getter can subtract directly

The constructor establishes an end greater than the start, with a supported difference. Keeping those fields unchanged preserves the relationship. Parsing alone wouldn't establish it, and code that directly constructs fields inside the owning module must still uphold it.

We have one remaining design task: make this construction path the one other parts of the program actually use. Put the boundary in the code follows the same contract into modules and visibility, where the layout of the program can help preserve the promises we've just tested.
