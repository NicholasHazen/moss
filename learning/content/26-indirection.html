The inspector wants “Inspector: actor=7 tick=5 reserve=10,” while a compact diagnostic panel wants “7@5:10.” Both should read the same retained report without changing it. We can support those two formats with an enum.

Start with the known choices

Begin with the value being presented. Our Report owns its actor ID, tick, and optional reserve measurement, so it does not depend on a live entity or an allocation in the history journal. The formatter borrows that report long enough to produce a string. It must retain the meaning of the option: None prints “unknown,” while Some(0) prints zero. The compact line is diagnostic text for this exercise; a stored interchange format would need a versioned schema of its own.

For two known choices, Style can describe everything we need. Its named variant owns a prefix, and its compact variant needs no extra data. A render method matches the variant and produces the appropriate line. Because both choices are values of the same enum type, a Vec<Style> already stores them together without a separate box for each element. Adding a variant also makes exhaustive matches ask what that new choice means.

Now suppose a separately written formatter needs to join the same list. The test's IdOnly type knows how to print an identity but is not another Style variant. We want the collection's rendering loop to accept it through a shared interface. That extension is the reason to consider a trait object here. If the program continues to need only the two known styles, keeping the enum is a complete design.

Separate the owner from the call

The collection needs to own its formatters after the construction function returns, including a named formatter's prefix. Box<T> supplies an owning pointer, ordinarily to heap storage. Moving the box transfers that ownership to the recipient, and the recipient can borrow the stored value for a call. A zero-sized value such as our empty CompactFormat needs no allocation. The boxed module documentation describes that storage behavior; it is separate from choosing which render method to execute.

The rest of the type, dyn ReportFormat, supplies the common calling interface. Behind each pointer is a particular formatter value, but the collection only needs to know that its render operation is available. Calling through the trait object selects the implementation using its dispatch information. The trait-object reference describes the data pointer and virtual method table involved. Combining this interface with Box lets one vector own formatter values of different concrete types.

You can use the interface without transferring ownership. render_borrowed accepts &dyn ReportFormat, so it can temporarily borrow a local Style::Compact without putting it in a box. render_generic<F: ReportFormat> also borrows a formatter, but its caller selects a concrete type for F rather than using object dispatch. All three paths can render the same report. Decide first whether the call needs a borrowed value or a stored owner, then whether it needs a concrete type or a trait-object interface.

There is a lifetime promise in the returned Box<dyn ReportFormat> too: this lab's return type defaults to a 'static object lifetime bound. A named formatter meets it by owning its prefix instead of borrowing a local string from construction. The box can still be dropped whenever its owner is finished with it; the bound says its contents cannot depend on a shorter-lived borrow. A formatter designed to borrow the caller's prefix would need an explicitly bounded object lifetime.

Know which methods can cross the object boundary

We have a working collection of formatters; before adding methods to its interface, we need to know which calls it can continue to support. Look at what a call through the trait object has to know. Our render method takes a shared receiver, a concrete report argument, and returns an owned string, so the caller can make the same kind of call through every object. A method with its own generic type parameter asks for an additional choice of type at the call site. The object's dispatch information cannot provide a separate callable implementation for every type a future caller might select, so that generic method cannot be dispatched through this trait object. Share a snapshot only when needed

We have decided how to store formatters and call their methods. A separate question arises if two panels must each keep the same report after the function that created them returns. The program's last line uses two Rc<Report> handles for that situation. Rc::clone adds another owner of the same allocation, so dropping the first handle leaves the second able to read the report. The separate Report::clone test instead creates a new report value whose reserve can change independently.

Shared ownership is useful when those readers have independent lifetimes on one thread. If two inspector functions merely need the report during their calls, ordinary &Report borrows are enough. Rc uses non-atomic reference counting and is neither Send nor Sync, so its handles cannot be used to transfer this ownership across threads. The Rc documentation also explains the cycle limitations that matter when owned values point back to one another.

For readers on different threads, Arc uses atomic reference counting. With the default allocator, Arc<T> can be Send and Sync when T satisfies both bounds. Our native test establishes those bounds for this report, shares it with a worker that formats it, joins the worker, and reads the report again. The atomic ownership count permits this sharing; it does not make an arbitrary payload safe. This is a native-thread example, so a browser worker would need its own setup and checks.

Read the two bounds in terms of the access you need. Send permits transferring a value between threads; Sync permits sending shared references to that value between threads. A plain Box<dyn ReportFormat> does not retain either promise in its exposed type, even if a particular implementation happens to satisfy them. An API requiring both must say so with bounds such as dyn ReportFormat + Send + Sync and accept only implementations that meet them.

Interior mutability still has rules

So far the shared report has been read-only. To decide what a changing cache would require, separate keeping an allocation alive from accessing its contents. Keeping several owners alive does not grant any of them unrestricted permission to mutate it. If a local preview cache needs to change through a shared API, an interior-mutability type can supply a specific operation for that purpose. Cell supports copying or replacing small values, while RefCell lets code obtain borrows whose exclusivity is checked at runtime.

Follow the cache test in two stages. While a read guard is alive, try_borrow_mut() returns an error because writing would conflict with that read. Dropping the guard ends the borrow, allowing the next attempt to update the preview. Calling ordinary borrow_mut() during the conflict would panic instead. The access rule has not disappeared; its check now happens at runtime, and the guard determines how long the access lasts. The RefCell methods describe both forms.

That runtime borrowing mechanism is local to a thread. RefCell<T> is not Sync, although it can be Send when T is. Adding an atomic ownership count with Arc does not change the payload's sharing capability. If the real requirement is concurrent shared mutation, synchronization types such as Mutex or RwLock address it. The Arc thread-safety section connects these bounds to the inner value.

Give each extra type a specific job

The two lines from the opening still describe the same unchanged report. An enum keeps the known styles together; a trait object gives independently implemented formatters a common calling interface; a box lets the collection own them. Readers with independent lifetimes may need shared ownership, and mutation or cross-thread access adds further requirements. Keeping those decisions separate lets you choose the access the example actually needs.

In accepting asynchronous results, an owned value will arrive after its request has been replaced. We'll use that delay to distinguish safe ownership transfer from the application's permission to accept the result.
