JavaScript requests a step or reset and draws the returned readings; the maintenance calculation still runs in Rust. Start by comparing a change to that world with a change to its presentation.

Follow three ticks through the boundary

In a fresh run, Fern and Flint each have 60 reserve units. The installed maintenance rule spends one per animal on every executed tick, so three single Steps should produce tick 3 with both reserves at 57. Meadow keeps biomass 80, and Fern stays at cell (10, 10). The current live checkpoint has not scheduled the unfinished movement exercise, so losing reserve doesn't yet make Fern approach the grass.

Now use Redraw only several times and change the label size. Redrawing reads the components and rebuilds the display without calling Rust's tick function; label size changes the styling. The next reading should still show tick 3 and reserve 57. Watching those values stay fixed checks this host's request boundary, which is the distinction you predicted before clicking. It doesn't by itself check every camera and timing path in the main application.

The table gives absence a visible meaning too. Meadow has biomass but no reserve component, so its reserve cell says “Not present.” A depleted animal instead has a reserve whose value is zero. The named shapes and the table let you identify individuals without relying on color, and the table retains the meaningful readings if the diagram isn't useful to you.

Why do both animals remain at zero?

The installed maintenance system uses saturating subtraction without implementing death, eating, or movement. From a fresh run, seven batches of ten ticks reach tick 70 with both animals still present at zero and Meadow still at 80. That result describes the current lifecycle boundary. Build the same runtime locally

The static lessons remain readable without a Rust build. To include this executable view, follow the pinned toolchain and dependency setup in the local workbench, then run the commands below from the repository root. The WebAssembly target needs installing only if it is missing:

rustup target add wasm32-unknown-unknown --toolchain 1.93.1
python3 learning/scripts/runtime.py check
python3 learning/scripts/runtime.py build
python3 learning/scripts/build.py
python3 learning/scripts/serve.py

If the course server is already running, keep it and reload after the build. The runtime has its own Cargo lockfile and output under learning/work, but depends directly on crates/moss-sim. Its native checks therefore exercise the installed schedule you'll observe here, without adding another rule to that schedule.

How the page identifies a current build

The builder fingerprints the simulation, host sources, and relevant manifests. If those inputs change, rebuilding the pages omits the stale binary and asks for another runtime build. An older binary therefore isn't presented as the result of your new sources. After an intentional simulation change, review the expected trace in this page too: the build can establish source freshness without establishing that the explanation still describes the new behavior.

Keep the tick separate from the picture

A passing helper test explains its subtraction cases, but can't establish which schedule ran in the browser. An animation alone doesn't identify the source of its numbers. Following the dependency to the actual simulation and checking the native schedule alongside this view makes the result easier to explain when one layer differs from your expectation.
