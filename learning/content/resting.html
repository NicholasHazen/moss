A rest restores capacity for effort, but doesn't feed the grazer

Reserve already has a clear job in our world: it pays upkeep, movement and birth contributions. We'll keep that meaning and give fatigue a separate one. Every cell the grazer actually travels adds two fatigue points, while a rest action removes up to two. These rules allow a tired grazer to recover even as its reserve falls, which is the tradeoff we want to investigate.

Charging actual travel matters here. A grazer that can't afford a step hasn't done the work of moving, so an attempted journey shouldn't add fatigue. Neither should observing a patch, choosing it, or eating a stationary meal. The isolated rest lesson charged each abstract foraging tick; now that we have real movement to measure, we can attach effort to that specific outcome instead.

For the first policy, fatigue has a maximum of ten points. A grazer enters rest when a decision finds it at six or more, and it can leave only when fatigue is two or less and it has completed at least two rest actions. The two conditions happen to finish together in the ordinary journey. Later we'll change recovery so we can see why both are needed.

Keep these quantities recognizable in your code. Reserve units pay for an action, fatigue points describe its effort, and the rest commitment counts executed actions. They're related by our rules, but they aren't interchangeable merely because each can be represented by an integer.

Remember what the grazer has committed to

We need the state of a resting grazer to explain what it can do next. Fatigue alone can't do that: an animal might have recovered enough while still owing an action, or finished its minimum pause while remaining too tired to leave. Sketch a representation that can express both situations before opening the answer.

The reference uses Activity::Foraging and Activity::Resting { remaining_ticks }. This is a useful job for an enum because the countdown belongs only to the resting state. With two separate booleans such as resting and ready, we'd have to explain which combinations are meaningful and keep them synchronized. The enum gives the countdown a home in the state that needs it. If that pattern is unfamiliar, the Rust Book's enum chapter develops it, and its match chapter shows how to access a variant's data.

In this API, remaining_ticks means executed rest actions still owed. Merely calling a decision system, waiting in the browser, or reading a report doesn't reduce it. Zero is also a valid resting state: the minimum commitment is complete, but the next decision still needs to check whether fatigue is low enough.

That distinction suggests two systems. The decision system enters rest with a full commitment, stays with the current activity when its exit conditions aren't met, or wakes the grazer when they are. The action system then performs the chosen rest by reducing fatigue and spending one owed action. Keeping these jobs separate prevents a decision from accidentally doing the work it was only meant to authorize.

The diagram follows a fast recovery, where fatigue reaches zero after the first rest action. The grazer still owes another action, so it remains resting through the next tick and wakes only at a later decision. That later decision also gives it a fresh look at the world. Entering rest clears the current target through the choice phase; an old observation may remain in the inspector as history, but it cannot authorize movement or feeding. When the grazer wakes, observation runs before choice, even if it ends up choosing the same patch again.

Write the system that performs a rest

Now implement execute in src/mobile/rest/systems.rs, including its parameters and iteration. Start by asking what information the job needs. It must read the executed clock, stable identity and grazer eligibility so it knows who may act. It must change the mobile actor's rest state and update the rest accounting resource. Position and reserve aren't part of that mutation: recovery changes neither, so the system doesn't need mutable access to them.

Use the ordering pattern you've already met in the action systems: collect entity handles together with stable IDs, sort the pairs, then visit the actors through the query. Recoveries don't compete for a shared food store, but their event order still matters once a bounded journal begins discarding old entries. A stable processing order keeps that evidence reproducible.

Before applying recovery, check whether this actor can perform a rest action now. Dead grazers, foragers, children before their first eligible tick and actors that already rested this tick must all be skipped. For an eligible resting actor, the actual recovery is the smaller of its current fatigue and the policy's recovery amount. Subtract that amount, then reduce a positive commitment without allowing it to underflow.

Notice what happens when fatigue is already zero. Recovery contributes zero points, but the actor may still be completing an owed action. It must therefore spend that commitment and record a Rested event. If you skip the whole action when recovery is zero, a fast-recovering grazer can remain committed forever. Prepare the counter additions before changing the actor, including the eviction counter if recording this action displaces an old event. This keeps state and evidence together without making a full journal prevent recovery.

Put rest where it can affect the next action

The new decision must run early enough to stop an otherwise valid journey. Install it before observation, then keep observation, choice, travel, rest execution, contact and meals in that order. Upkeep and growth have already happened; starvation and birth resolution follow the actions. The complete schedule shows how this fits around the existing deferred boundaries. Even a single-threaded schedule needs these dependencies, because a different order would describe a different rule.

Upkeep remains a cost for every eligible living grazer, including one that is resting beside food. Rest blocks travel, feeding and reproduction, and this policy has no hunger override. A grazer can therefore starve while its fatigue is recovering. That's an uncomfortable consequence of the chosen behavior, but it gives us a reason to investigate the policy rather than quietly crediting reserve during recovery.

Movement also needs to respect the available fatigue capacity. At fatigue nine, with a maximum of ten and a cost of two points per cell, there isn't room for even one whole step. Accepting the step and clipping its fatigue charge afterward would make position, energy payment and effort disagree about what happened. Extend the movement plan to limit accepted cells before committing any of those changes; the complete movement module shows how the two accounting resources are prepared together.

Crossing the rest threshold during travel doesn't undo that travel or start a second decision. The current foraging action may still finish with a meal at valid contact, and the next tick's decision will see the new fatigue. The same separation works in the other direction: completing recovery doesn't grant an extra foraging action later in the same tick. Each tick follows the activity chosen for it.

Prediction answer: could a stationary grazer rest forever?

If a forager never travels, its fatigue remains zero under this effort rule. It does not enter rest just because ticks pass. Once an actor is resting, it may execute extra recovery actions after its minimum reaches zero if fatigue remains above the exit threshold. These are different reasons for staying in the current activity.

#[test]
fn fast_recovery_does_not_cancel_the_second_committed_action() {
    let scenario = MobileScenario::resting_journey().with_rest(policy(2, 6));
    let mut world = CourseWorld::new_mobile(scenario).unwrap();
    for _ in 0..3 { world.step(); }
    let third = world.rest_snapshot().unwrap();
    assert_eq!(third.grazers[0].fatigue_points, 6);
    assert_eq!(third.grazers[0].activity, Activity::Foraging);
    assert!(world.mobile_snapshot().unwrap().grazers[0].target.is_some());

    world.step();
    let fourth = world.rest_snapshot().unwrap();
    let fourth_mobile = world.mobile_snapshot().unwrap();
    assert_eq!((fourth.tick, fourth.grazers[0].fatigue_points), (4, 0));
    assert_eq!(fourth.grazers[0].activity, Activity::Resting { remaining_ticks: 1 });
    assert_eq!((fourth.ledger.rest_actions, fourth.ledger.recovered_points), (1, 6));
    assert_eq!(fourth_mobile.grazers[0].cell, Cell { x: 3, y: 0 });
    assert!(fourth_mobile.grazers[0].target.is_none());
    assert_eq!(fourth_mobile.base.grazers[0].reserve_units, 13);
    assert_eq!((fourth_mobile.ledger.travel_cells, fourth_mobile.base.ledger.eaten_units), (0, 0));
    assert_eq!(fourth_mobile.base.ledger.maintenance_units, 1);
    assert_eq!(world.rest_snapshot().unwrap(), fourth);
    assert_eq!(world.mobile_snapshot().unwrap(), fourth_mobile);

    world.step();
    let fifth = world.rest_snapshot().unwrap();
    let fifth_mobile = world.mobile_snapshot().unwrap();
    assert_eq!(fifth.grazers[0].activity, Activity::Resting { remaining_ticks: 0 });

    assert_eq!((fifth.ledger.rest_actions, fifth.totals.rest_actions), (1, 2));
    assert_eq!(fifth_mobile.grazers[0].cell, Cell { x: 3, y: 0 });
    assert!(fifth_mobile.grazers[0].target.is_none());

    let sixth_mobile = world.mobile_snapshot().unwrap();

#[test]
fn two_and_three_actions_change_arrival_and_later_opportunities() {
    let mut two = CourseWorld::new_mobile(
        MobileScenario::resting_journey().with_rest(policy(2, 2)),
    ).unwrap();
    let mut three = CourseWorld::new_mobile(
        MobileScenario::resting_journey().with_rest(policy(3, 2)),
    ).unwrap();
    for _ in 0..6 { two.step(); three.step(); }
    let two_mobile = two.mobile_snapshot().unwrap();
    let three_mobile = three.mobile_snapshot().unwrap();
    assert_eq!((two_mobile.tick, three_mobile.tick), (6, 6));
    assert_eq!((two_mobile.grazers[0].cell.x, two_mobile.base.grazers[0].reserve_units), (4, 10));
    assert_eq!((three_mobile.grazers[0].cell.x, three_mobile.base.grazers[0].reserve_units), (3, 11));
    assert_eq!(two.rest_snapshot().unwrap().grazers[0].activity, Activity::Foraging);
    assert_eq!(three.rest_snapshot().unwrap().grazers[0].activity, Activity::Resting { remaining_ticks: 0 });

    two.step(); three.step();
    let two_mobile = two.mobile_snapshot().unwrap();
    let three_mobile = three.mobile_snapshot().unwrap();
    assert_eq!((two_mobile.grazers[0].cell.x, two_mobile.base.ledger.eaten_units), (5, 2));
    assert_eq!((three_mobile.grazers[0].cell.x, three_mobile.base.ledger.eaten_units), (4, 0));
    assert_eq!(three_mobile.base.patches[0].biomass_units, 20);

    two.step(); three.step();
    let two_mobile = two.mobile_snapshot().unwrap();
    let three_mobile = three.mobile_snapshot().unwrap();
    assert_eq!((two_mobile.grazers[0].cell.x, two_mobile.base.grazers[0].reserve_units), (5, 9));
    assert_eq!((three_mobile.grazers[0].cell.x, three_mobile.base.grazers[0].reserve_units), (5, 9));
    assert_eq!(three_mobile.base.ledger.eaten_units, 2);
    assert_eq!(two.rest_snapshot().unwrap().grazers[0].activity, Activity::Resting { remaining_ticks: 1 });
    assert_eq!(three.rest_snapshot().unwrap().grazers[0].activity, Activity::Foraging);

    two.step(); three.step();
    assert_eq!(two.snapshot().grazers[0].reserve_units, 8);
    assert_eq!(three.snapshot().grazers[0].reserve_units, 10);
}

Does a longer rest help this meadow?
