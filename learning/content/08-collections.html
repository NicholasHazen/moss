Collect a report that survives its inputs

You'll build a collector that selects creatures, gives each row its own data, and orders the rows by numeric identity. We'll trace those decisions through an iterator, then use reversed inputs, missing measurements, and duplicate IDs to challenge the result. The completed report should stay usable after its sources change or disappear, with IDs 3, 5, and 9 in the same order and an unknown reserve still distinct from zero.

Choose membership, ownership, then order

Our input arrives as Flint, Fern, Meadow, and Unmeasured. It contains three creatures and one display source: Meadow isn't a creature, so it shouldn't become a report row. Among the creatures, Fern has 57 reserve units, Flint has a measured zero, and Unmeasured has no collected reserve. The finished report should keep all three creatures and order them by numeric ID: 3, 5, then 9.

To produce that result, we need to make three decisions. We first select which sources belong in the report, then construct an owned Row for each selected source, and finally put those rows in display order. Keeping the stages visible gives us a useful way to diagnose a wrong result. Meadow appearing in the report points to membership; a historical name changing later points to ownership; shuffled rows point to ordering.

The collector only needs to inspect the caller's existing sequence, so its input is a borrowed slice, &[Source]. A vector, an array, or a smaller contiguous view can supply that slice without handing over ownership or letting the collector grow the source sequence. The output has a different job: an owned Vec<Row> gathers the selected rows into a growable sequence that the caller can keep after collection ends.

Owning the vector alone wouldn't make the report independent. A Vec<&Source> owns the sequence of references, but every reference still borrows a source value. We need each row to own its String and contain copied numeric data instead. Then dropping the source vector removes the original observations without removing the information saved in the report.

Read an iterator as a sequence of decisions

We can express those first two decisions as an iterator chain. Start with sources.iter(), which yields shared references to the source values. filter keeps the sources marked as creatures, and map describes how each one becomes a row. Those adapters describe work; collect is what asks the chain for results and builds the output vector. As it consumes the iterator, each source is examined and each selected source becomes an owned row. Without a consuming operation, constructing the chain wouldn't produce a completed report.

The small expression |source| source.creature tells filter how to make its decision. It is a closure: a function expression whose argument is supplied by the iterator and whose result is the creature flag. The compiler can infer the argument type from that surrounding use. At the other end of the chain, the Vec<Row> annotation tells collect which kind of collection should receive the results.

Inside map, cloning source.name gives the row its own text storage. The ID and Option<u32> can be copied directly. Notice what copying the option preserves: None is still absence, and Some(0) is still an available measurement whose value is zero. We don't have to invent a number for Unmeasured to keep that creature in the report.

You might reach for filter_map when an input contains an option. That adapter transforms each item and discards results that are None, which would suit a request for only available measurements. Our question is different: which creatures were present, and what did we know about their reserves? Filtering on the reserve option would remove Unmeasured entirely. Select on the creature flag and carry the option into the row so its absence remains visible.

Make order part of the output contract

After collection, sort the rows by numeric ID. Fern then occupies the same place in the report even if the source sequence was reversed. This order is a presentation choice: it doesn't claim that a lower ID is older, closer, or entitled to food first. A later rule that resolves competition would need its own reason for choosing an order.

There is a subtle limit to what sorting can guarantee. sort_by_key is stable, meaning equal keys retain their previous relative order. If two different rows share the same ID, reversing the input could therefore reverse those two rows in the output as well. More fundamentally, the report couldn't say which row that ID identifies. Rather than treating a stable sort as a solution to ambiguous identity, this lab rejects duplicate selected IDs.

Sorting makes that validation easier: every repeated ID must sit beside another equal ID. windows(2) lends each adjacent pair so the function can compare their IDs and return ReportError::DuplicateId(id) on a collision. If no pair collides, return Ok(rows). An empty input naturally produces an empty vector with no adjacent pairs to inspect.

#[derive(Debug)]
struct Source {
    id: u64,
    name: String,
    reserve: Option<u32>,
    creature: bool,
}

#[derive(Debug, PartialEq, Eq)]
struct Row { id: u64, name: String, reserve: Option<u32> }

#[derive(Debug, PartialEq, Eq)]
enum ReportError { DuplicateId(u64) }

fn collect_report(sources: &[Source]) -> Result<Vec<Row>, ReportError> {
    let mut rows: Vec<Row> = sources.iter()
        .filter(|source| source.creature)
        .map(|source| Row {
            id: source.id,
            name: source.name.clone(),
            reserve: source.reserve,
        })
        .collect();
    rows.sort_by_key(|row| row.id);
    for pair in rows.windows(2) {
        if pair[0].id == pair[1].id {
            return Err(ReportError::DuplicateId(pair[0].id));
        }
    }
    Ok(rows)
}

fn find_row(rows: &[Row], id: u64) -> Option<&Row> {
    rows.iter().find(|row| row.id == id)
}

    }

Lookup is a different question from display order

The ordered report is ready to keep or display. A caller asking about one creature has a narrower need, so we'll separate finding a stored row from collecting the report again. find_row returns Option<&Row>, where the outer option answers whether that ID appears in the report. The row's reserve is a separate option. ID 404 has no row at all; ID 5 has a row that records an unavailable reserve. Those are different answers, even though both involve absence.

A successful lookup lends a row already stored in the report. It doesn't clone the name or collect another snapshot, and the pointer-identity assertion checks that it returns the existing row. While the caller continues using that reference, it can't make a conflicting change to the vector that owns it. If the caller only needs the small reserve value, copying that value lets the borrow end sooner.

A linear search is enough for this small report. If a consumer repeatedly looks up many IDs, a map can provide an index after the collector has validated uniqueness. The following separate exploration fragment builds a borrowed index: the map owns its keys and references, while the vector continues owning the rows they point to.

use std::collections::HashMap;
let by_id: HashMap<_, _> = rows.iter().map(|row| (row.id, row)).collect();
assert_eq!(by_id.get(&9).unwrap().reserve, Some(0));

The index answers where to find an ID, but it doesn't inherit the vector's display order. Iterating that HashMap need not reproduce the sorted report. Keep using the vector for presentation and the map for lookup, or choose a collection with the ordering contract you need. Since a borrowed index also has a lifetime and a cost to rebuild, add one when an actual consumer benefits from those repeated lookups.

Retain a reading without freezing the world

We started with a display that changed when its input order changed. The completed collector makes the output order deliberate and owns enough information for the report to survive its sources. A later lookup can borrow from that report for as long as the caller needs a row. These two ownership choices let the world continue changing while a user reads or sorts a saved panel.

Recall answer: why not replace every None with zero?

A zero reserve is an observed number. An absent reserve is a gap in the observation. Replacing absence with zero would turn the unmeasured creature into evidence of depletion, even though the collector never recorded such a measurement. The row's identity survives both cases; the measurement's meaning does not.

Reverse the inputs once more, then change their names and drop them: the saved report should keep the same ordered rows and the same distinction between zero and absence.
