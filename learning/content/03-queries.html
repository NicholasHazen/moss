Suppose you add an animal to the world, run maintenance, and find that nothing happened to it. The subtraction may be perfectly correct: the animal might never have entered the loop. We'll build a small world with two ordinary creatures and two deliberately awkward entities, then use a Bevy query to work out who pays and why.

This isolated lab uses Bevy ECS 0.18.1, matching the repository. It builds on borrowed and copied values from the ownership lesson. We'll inspect Moss's existing maintenance system afterward; the live movement assignment stays in NOW.md.

Decide which entities maintenance can use

A list of identical animal structs would give every animal the same fields. An ECS world lets different entities carry different combinations of data. An entity supplies an identity; its components might hold a species, reserve, or name. Systems request access to the components they need and operate on the entities that satisfy that request.

That flexibility makes “the animal exists” insufficient for our maintenance rule. To choose a cost, we need its species. To charge the cost, we need mutable access to its reserve. We also want a creature marker, because some other entity could have species and reserve data for a display experiment without belonging to the simulated population. The query can express all three requirements.

Here are the parameters from the lab's maintenance function. Read the query as a description of both membership and access:

rates: Res<Rates>,
mut creatures: Query<(&Species, &mut Reserve), With<Creature>>,

The tuple asks for Species and Reserve together on each matching entity. The species reference is shared because the rule only reads it; the reserve reference is mutable because the rule changes it. With<Creature> adds a membership requirement without returning the marker's value. An entity must have all three components to appear in the loop.

The other parameter, Res<Rates>, borrows a resource from the world. Resources hold shared world-level data, while components belong to entities. Our Rates resource contains one table of species costs. The system reads the table on each execution, so changing it affects later charges without rewriting every stored reserve when the new rates are inserted.

Try the query against an awkward fixture

We'll start Fern and Flint at 60 units and give them all the required components. To check the boundaries, we'll also create “Incomplete,” a creature with no reserve, and “Display sample,” an entity with species and reserve but no creature marker. These last two make mistakes visible that a world full of ordinary creatures would conceal.

Before running the program, use the query signature to decide which rows reach its body. Then apply a Hare rate of one unit and a Fox rate of two units over three executions. The table gives the expected result for comparison:

Membership and reserve after three maintenance executions
Entity and componentsExpected result
Fern: Creature, Hare, Reserve(60), NameIncluded; reserve becomes 57.
Flint: Creature, Fox, Reserve(60), NameIncluded; reserve becomes 54.
Incomplete: Creature, Hare, NameExcluded; no Reserve exists to change.
Display sample: Hare, Reserve(60), NameExcluded; its reserve remains 60.

“Incomplete” is different from a creature with Reserve(0). Zero is a value that the system can read and leave at the floor. A missing component means there is no reserve for this required query to return. We need that distinction to explain an unchanged entity without inventing a number for it.

Hint 1: check every required component

Start with entities carrying Species, keep those that also carry Reserve, then apply the Creature filter. A familiar name doesn't compensate for a missing component.

Hint 2: apply the rate after membership

The shared rates resource supplies the numbers used inside the loop. It doesn't select entities. Only after an entity matches does its species determine which configured cost the body reads.

Answer: Fern and Flint pay

Fern pays three units and Flint pays six. “Incomplete” never enters the mutation loop, while “Display sample” is excluded by the marker filter. Both exclusions matter: a test with only Fern and Flint could pass even if that filter were missing.

Follow the access into the loop

The body of maintenance uses two mutable bindings that are worth distinguishing before reading the full file. mut creatures lets the loop request mutable access through the query. Each returned reserve is a Bevy mutable component wrapper; mut reserve lets the assignment operate through that wrapper. The value being changed still belongs to the entity in the world.

The species borrow stays shared throughout. A match chooses the Hare or Fox rate and the reserve assignment applies it. The name plays no part in that decision, so renaming Fern wouldn't change her cost. You can see most of this separation in the signature before reading the arithmetic: the system asks to change reserve, read species, and restrict its work to creatures.

We'll run that system with the single-threaded executor to keep the execution setup simple. There is only one system here, so we haven't yet had to decide which of two rules goes first. Adding more systems will require explicit dependencies when their order matters; one thread alone doesn't state that policy. Moss's maintenance-then-completion chain is an example of an order chosen by the application. The 0.18.1 executor documentation describes the execution modes separately from those scheduling choices.

Run the world you just traced

The following is a complete isolated src/main.rs. Its declarations use #[derive(Component)] and #[derive(Resource)] to supply the traits Bevy needs for entity data and world resources. Start with maintenance, then find the four entities in fixture. In main, three calls to schedule.run execute maintenance three times. This lab has no simulation clock; the installed Moss schedule additionally records tick completion.

For now, use audit as supplied reporting code. It will help us see “Incomplete” even though maintenance can't act on it. After the run, we'll look at the small change in its query that makes this possible. The later collections lesson will return to the iterator and sorting operations used to assemble its output.

use bevy_ecs::{prelude::*, schedule::ExecutorKind};

#[derive(Component)]
struct Creature;

#[derive(Component)]
struct Name(&'static str);

#[derive(Component, Clone, Copy)]
enum Species { Hare, Fox }

#[derive(Component, Debug, PartialEq, Eq)]
struct Reserve(u32);

#[derive(Resource)]
struct Rates { hare: u32, fox: u32 }

fn maintenance(
    rates: Res<Rates>,
    mut creatures: Query<(&Species, &mut Reserve), With<Creature>>,
) {
    for (species, mut reserve) in &mut creatures {
        let cost = match *species {
            Species::Hare => rates.hare,
            Species::Fox => rates.fox,
        };
        reserve.0 = reserve.0.saturating_sub(cost);
    }
}

fn fixture() -> (World, Schedule, Entity) {
    let mut world = World::new();
    world.insert_resource(Rates { hare: 1, fox: 2 });
    world.spawn((Creature, Name("Fern"), Species::Hare, Reserve(60)));
    world.spawn((Creature, Name("Flint"), Species::Fox, Reserve(60)));
    world.spawn((Creature, Name("Incomplete"), Species::Hare));
    let display = world.spawn((Name("Display sample"), Species::Hare, Reserve(60))).id();
    let mut schedule = Schedule::default();
    schedule.set_executor_kind(ExecutorKind::SingleThreaded);
    schedule.add_systems(maintenance);
    (world, schedule, display)
}

fn audit(world: &mut World) -> Vec<(&'static str, Option<u32>)> {
    let mut query = world.query_filtered::<(&Name, Option<&Reserve>), With<Creature>>();
    let mut rows: Vec<_> = query.iter(world)
        .map(|(name, reserve)| (name.0, reserve.map(|value| value.0)))
        .collect();
    rows.sort_by_key(|row| row.0);
    rows
}

fn main() {
    let (mut world, mut schedule, _) = fixture();
    for _ in 0..3 { schedule.run(&mut world); }
    for (name, reserve) in audit(&mut world) {
        println!("{name}: {reserve:?}");
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn required_components_and_marker_define_membership() {
        let (mut world, mut schedule, display) = fixture();
        for _ in 0..3 { schedule.run(&mut world); }
        assert_eq!(audit(&mut world), vec![
            ("Fern", Some(57)), ("Flint", Some(54)), ("Incomplete", None),
        ]);
        assert_eq!(world.get::<Reserve>(display), Some(&Reserve(60)));
    }

    #[test]
    fn optional_read_exposes_missing_data() {
        let (mut world, _, _) = fixture();
        let required_count = world.query_filtered::<&Reserve, With<Creature>>()
            .iter(&world).count();
        assert_eq!(required_count, 2);
        let rows = audit(&mut world);
        assert_eq!(rows.len(), 3);
        assert_eq!(rows.iter().filter(|(_, reserve)| reserve.is_none()).count(), 1);
    }

    #[test]
    fn next_execution_reads_the_current_resource() {
        let (mut world, mut schedule, _) = fixture();
        world.resource_mut::<Rates>().hare = 4;
        schedule.run(&mut world);
        assert_eq!(audit(&mut world), vec![
            ("Fern", Some(56)), ("Flint", Some(58)), ("Incomplete", None),
        ]);
    }
}

Explain the extra row in the audit

Fern and Flint's numbers match our prediction, but the report also contains “Incomplete.” The audit asks for (&Name, Option<&Reserve>) with With<Creature>. Name and the creature marker are still required. Reserve is now optional: a matching entity gives us Some(reference) when it has that component and None when it doesn't.

This is why the third row can be reported without assigning it a reserve of zero. Option describes two alternatives, carrying a value only in Some. The audit's map copies the numeric field when a reference is present and preserves None otherwise. Its returned vector owns the numbers and holds references to static name literals; it doesn't keep borrows of the world's components. We can continue working with the world after collecting the reading.

The two queries serve different purposes. Maintenance needs a reserve to perform its operation, while the audit needs to describe creatures whose reserves may be missing. Making maintenance's reserve optional would force its body to decide what to do without one. That may suit some systems, but it isn't necessary to make this report useful.

There is still a boundary to the audit: a creature without Name wouldn't appear either. It reports this missing-reserve case, rather than validating every possible malformed entity. When consulting Bevy's versioned Query reference, keep asking which terms change membership and which change the data returned. That question connects its type signatures to the rows you actually see.
