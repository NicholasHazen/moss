Read in the browser, then bring the compiler to the question.

You can follow the explanations, diagrams, and teaching models without setting up Rust first. When you're ready to edit a lab, the local workbench compiles and tests your saved file. That gives you Rust's actual diagnostics while keeping the lesson beside your editor. The small browser teaching models provide a quicker way to test a prediction; their labels distinguish them from compiled Rust.

A workbench you can trust

By the end of this guide, you should have the course beside your editor and know whether a command is checking the printed answer or your own file. We’ll open the reading edition, verify the pinned toolchain, and run a small reference before preparing an unfinished exercise. That order separates a setup problem from a mistake in the code you are learning to write. The browser-build commands come afterward, for the lessons that need a compiled view.

Open this edition

From the root of the Moss checkout containing learning, build and serve the course. You need Python 3.11 or newer, with no additional Python packages:

python3 learning/scripts/build.py
python3 learning/scripts/serve.py

Open Moss Fieldnotes on port 8091 and leave the terminal running while you read. Control-C stops the server, which binds only to your computer. Rebuild and reload after changing lesson sources. Keeping the same port also keeps the browser origin consistent, so your locally saved notes remain available.

Check the tools selected by Moss

The repository pins Rust 1.93.1 and Bevy ECS 0.18.1, the combination used for the course examples. From the same repository root, confirm that the toolchain is available:

scripts/with-toolchain.sh rustc +1.93.1 --version
scripts/with-toolchain.sh cargo +1.93.1 --version

If rustup reports that it is missing, install it and repeat those checks:

rustup toolchain install 1.93.1 --profile minimal --component rustfmt --component clippy

The first two labs use only the standard library. The query lab also needs the locked Bevy ECS dependencies in Cargo's cache, which a normal Moss build prepares. On a new machine, use docs/development/README.md for the complete project setup. If a command can't find a cached crate, resolve that setup problem before interpreting it as a result of your exercise.

Check the answer's starting point

Run the opening references once to see the workbench's test output and sample trace:

python3 learning/scripts/labs.py check observe
python3 learning/scripts/labs.py check ownership
python3 learning/scripts/labs.py check queries

Each command extracts the exact marked example from its lesson, compiles it separately, requires its named tests to run, and then executes the sample program. The output identifies this as PRINTED REFERENCE. Its passing result establishes that the published example works for those cases on your machine; the next step is to select an edit of your own.

Make an edit that belongs to you

The ownership lesson starts with an unfinished inspector function. Prepare a fresh copy, open it in your editor, then check the file you've selected:

python3 learning/scripts/labs.py prepare ownership --dest work/ownership-practice
python3 learning/scripts/labs.py check ownership --file work/ownership-practice/ownership.rs

The first check fails at the intended todo!. Replace the body of capture, save, and repeat the second command. Both checks identify the source as LEARNER FILE and name your path; after the edit, the required tests should pass. That label distinguishes feedback on your file from a run of the printed answer. Preparation refuses an existing destination; return to the same file for another attempt.

Which tests are used for a short lab?

When checking your copy, the runner uses the reference's trailing test module as the required course checks. Changing a copied assertion therefore cannot make an incorrect solution pass those checks. Keep additional exploratory tests in a separate scratch file. Later, the continuing project has a different workflow that retains and runs learner-authored integration tests alongside its required suites.

See checked Rust run in the browser

The maintenance terrarium runs the actual simulation crate, while the evidence lesson can run your completed projection exercise in a browser host. Both use local compilation. To reproduce their included references, install the pinned WebAssembly target and build the hosts:

rustup target add --toolchain 1.93.1 wasm32-unknown-unknown
python3 learning/scripts/runtime.py check
python3 learning/scripts/runtime.py build
python3 learning/scripts/preview.py evidence
python3 learning/scripts/build.py

For your own completed evidence exercise, add --file work/evidence-practice/evidence.rs to its preview command, then rebuild the course and reload. The panel identifies the source kind and compiled build. Rust source stays in the local workbench rather than being sent to a compiler service.

The continuing route begins in one saved meadow project and keeps that directory through population, movement and local observation, rest, and hunting. Those guides supply their stage-specific check and preview commands, along with complete source answers. Follow their instructions as you extend the project; don't prepare a replacement copy each time you begin a new guide.

Keep that same directory for the independent refuge capstone. Its stage check runs your growing collection of tests, and its native example compares shelter placements through printed reports. There is no additional refuge browser mode. If you want to reopen an earlier browser view after changing the source, rebuild it with that guide's preview command; a current build still displays only the rules and reports that its mode supports.

What does the runner execute?

These are local Rust programs running with your normal process permissions. The workbench runs original course examples or a file you explicitly select; it is not a sandbox for untrusted code. It doesn't accept source from the browser or start a local execution API. Build artifacts stay under learning/work, separate from the live simulation sources and active assignment.

Open the live terrarium when a lesson calls for it

The main Moss application has its own server. From the repository root, run:

scripts/with-toolchain.sh trunk serve --locked --release

It opens at port 8080, separately from Fieldnotes; keep one simulation preview on that port. At the current live checkpoint, maintenance runs while the unfinished movement rule remains unscheduled. Full workspace tests still encounter that intentional exercise, so use the focused command named by a lesson when you're inspecting an existing rule.

Know which file your test is checking

When you return to active Moss development, open NOW.md. Your course work can help explain the decision in front of you while the live assignment remains the place to make that project change.
