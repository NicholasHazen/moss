Two parents have stride values of two and six cells per action. One child ends up with a stride of one; another has seven. To explain those children, we need to know more than their final numbers: which parent supplied the starting value, what change was proposed, and whether the trait's limits altered that proposal. We'll build an inheritance function that keeps this little history with each result, so variation remains something we can inspect.

This standard-library exercise isolates one authored inheritance rule: choose a bounded integer trait from one of two parents, then optionally change it by one. It is a toy game model rather than real genetics, and it leaves live Moss and the current assignment in NOW.md unchanged.

Copying is one part of a birth

In the previous lesson, we made an accepted birth pay both parents, allocate one child identity and set the child's first eligible tick. That transaction gives us somewhere to put a new individual. Here we'll examine one decision inside that larger process: given the child and two known parents, how should we calculate a trait and remember where it came from?

We'll keep the parents fixed while exploring that calculation. They belong to run seven, with parent one carrying stride two and parent two carrying stride six. Stride means cells per completed action, with permitted values from one through eight. This file only generates the value; it doesn't run movement or charge energy for a stride. We'll be able to explain a child's seven without yet knowing whether seven helps that child in a world.

The function can make this decision through a shared reference to the parent pair. It reads their identities and traits, then returns an owned origin record for the child. There's no reason for inheritance to change the parents' stored traits, so the signature doesn't lend it mutable access to those values. The result also owns the information it needs, allowing us to keep the explanation after the borrowed parent data is no longer available.

The caller provides the child's already allocated identity. Our function can check that it is nonzero, differs from the parents and belongs to the same run, as well as rejecting duplicate parent identities. It can't see unrelated animals elsewhere in the world, though, so it cannot establish global uniqueness on its own. That responsibility stays with the birth allocator, which has the wider context.

Follow the change from parent to child

Start by separating the two operations that produced the child. Choosing parent one's stride copies an existing value of two. Proposing minus one then changes that inherited value to one. We call the second operation mutation, and we'll preserve both stages in the record so the final value doesn't hide the path that produced it.

Those operations generate variation at creation time. Growth would change the same individual during its lifetime, while learning would change its behavior through experience; neither happens in this function. Selection asks another question again: which variants contribute to later populations under the world's rules? We aren't running survival trials or reproducing descendants here, so the resulting table can explain inheritance without establishing an evolutionary advantage.

A mutation proposal can be minus one, zero or plus one. To apply it safely, we widen the inherited value to a signed integer, add the proposal, clamp the result to the trait's bounds, and convert the bounded result back to u8. That order lets us reason about a negative change before returning to the unsigned representation used for a valid stride.

At the lower bound, proposing minus one leaves a stride of one. That outcome looks identical to copying one with a zero proposal, but the two calculations tell different stories. Record both the proposed delta and the applied delta so we can distinguish them. Clamping is also part of the chosen variation policy: near a boundary, several proposals can lead to the same result, which changes the distribution of expressed values.

Make the draw protocol explicit

We also need an agreed way to choose a parent. If a generated index of zero means “the first array element,” simply reversing the caller's array could give the same seed a different meaning. The function therefore copies the pair and sorts it by stable key before making a choice. It leaves the caller's array untouched while giving our calculation a canonical order.

For the choices themselves, this lab uses a small integer generator whose entire calculation is visible in the file. It starts from the supplied seed, multiplies its 64-bit state by a fixed constant, adds a fixed increment and returns the upper 32 bits. Multiplication and addition deliberately wrap; the integer documentation defines those operations independently of whether overflow checks are enabled in a build. Here wrapping belongs to the algorithm, rather than being an accident we hope the compiler will tolerate.

The first output, reduced modulo two, chooses a parent from our sorted pair. The second, reduced modulo three, chooses the mutation proposal. We'll consume both outputs even when mutation is disabled, then use zero as the proposal in that copy-only mode. Making the draw sequence explicit keeps parent choice and the mutation setting from becoming unintentionally entangled.

The generator is useful here because a reader can reproduce every step without depending on a random-number library. That small scope comes with limits: remainder mapping can introduce bias, and the example doesn't promise independently uniform mutations. Use it to understand a repeatable protocol, rather than taking it as a recommended generator for scientific sampling, security or a larger simulation.

A seed is not a complete replay

Once the calculation works, imagine coming back to one of its children much later. A final stride of three wouldn't tell you whether it was inherited unchanged or produced by a mutation. Our origin record therefore keeps the parent keys and values, the selected parent, the inherited value, the proposal, the applied change and the expressed result. It also keeps the child key, seed, mutation setting and algorithm label, giving the calculation enough context to explain itself.

The label moss-traits-lcg64-v1 names the complete procedure: recurrence, output extraction, two-draw order, mapping and bounds. A seed only has meaning within such a procedure. Feeding the same integer to another library's generator, or changing our mapping while retaining the old label, wouldn't establish the same replay contract.

The tests make that contract concrete at two levels. A literal generator-output test checks selected points in its sequence, while the inheritance tests check complete child records for meaningful inputs. Together they support repeatability for this specified function and its validated inputs. They don't promise identical outcomes after an arbitrary dependency change or a redesigned world schedule.

In a larger simulation, generator ownership would become part of the design too. If every system shared one generator, an extra draw elsewhere could shift all later birth results. This exercise instead starts a local generator from each explicitly supplied seed, keeping that wider scheduling question outside the function. Whoever allocates birth-specific seeds must still decide how they are chosen; repeatedly supplying one seed won't create diverse siblings by itself.

The complete inheritance record

The complete answer keeps the calculation independent of live birth mutation. It borrows the parents for reading, works with small copied values and returns an owned record. If validation fails, no parent or child state has been partially changed. Compare that boundary with the birth planner: both functions describe a proposed result that a caller can accept as a whole.

const MIN_STRIDE: u8 = 1;
const MAX_STRIDE: u8 = 8;

#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord)]
struct Key { run: u32, id: u32 }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Parent { key: Key, stride_cells_per_action: u8 }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]

    child: Key,
    parents: [Key; 2],
    parent_strides: [u8; 2],
    mutation_enabled: bool,
    source_parent: Key,
    inherited: u8,
    proposed_delta: i8,
    applied_delta: i8,
    expressed: u8,
    seed: u64,
    algorithm: &'static str,
}
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum Rejected { Identity, ParentTrait }
struct Rng { state: u64 }
impl Rng {
    fn new(seed: u64) -> Self { Self { state: seed } }
    fn next_u32(&mut self) -> u32 {
        self.state = self.state.wrapping_mul(6_364_136_223_846_793_005)
            .wrapping_add(1_442_695_040_888_963_407);
        (self.state >> 32) as u32
    }
}
fn bounded_stride(inherited: u8, delta: i8) -> u8 {
    (i16::from(inherited) + i16::from(delta))
        .clamp(i16::from(MIN_STRIDE), i16::from(MAX_STRIDE)) as u8
}

fn inherit(parents: &[Parent; 2], child: Key, seed: u64, mutate: bool)
    -> Result<Origin, Rejected>
{
    if child.id == 0 || parents[0].key.id == 0 || parents[1].key.id == 0
        || parents[0].key == parents[1].key
        || parents.iter().any(|parent| parent.key.run != child.run || parent.key == child) {
        return Err(Rejected::Identity);
    }
    if parents.iter().any(|parent| !(MIN_STRIDE..=MAX_STRIDE)
        .contains(&parent.stride_cells_per_action)) { return Err(Rejected::ParentTrait); }
    let mut ordered = *parents;
    ordered.sort_by_key(|parent| parent.key);
    let mut rng = Rng::new(seed);
    let source = ordered[(rng.next_u32() % 2) as usize];
    let mutation_draw = (rng.next_u32() % 3) as i8 - 1;
    let proposed_delta = if mutate { mutation_draw } else { 0 };
    let inherited = source.stride_cells_per_action;
    let expressed = bounded_stride(inherited, proposed_delta);
    Ok(Origin { child, parents: [ordered[0].key, ordered[1].key],
        parent_strides: [ordered[0].stride_cells_per_action, ordered[1].stride_cells_per_action],
        mutation_enabled: mutate, source_parent: source.key, inherited, proposed_delta,
        applied_delta: expressed as i8 - inherited as i8, expressed,
        seed, algorithm: ALGORITHM })
}
fn parents() -> [Parent; 2] {
    [Parent { key: Key { run: 7, id: 2 }, stride_cells_per_action: 6 },
     Parent { key: Key { run: 7, id: 1 }, stride_cells_per_action: 2 }]
}
fn main() {
    let parents = parents();
    for (index, seed) in [3, 5, 6].into_iter().enumerate() {
        let origin = inherit(&parents, Key { run: 7, id: 100 + index as u32 }, seed, true).unwrap();
        println!("seed={} child={} source={} inherited={} proposed={} applied={} expressed={}",
            seed, origin.child.id, origin.source_parent.id, origin.inherited,
            origin.proposed_delta, origin.applied_delta, origin.expressed);
    }
    let copied = inherit(&parents, Key { run: 7, id: 103 }, 6, false).unwrap();
    println!("copy-only={} algorithm={}", copied.expressed, copied.algorithm);
}

To call one stride an improvement, we'd also need an outcome and world rules connecting that trait to the outcome; this function supplies the variation without running that comparison.
