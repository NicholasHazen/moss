Change eligibility before the next action

Growth and environmental input showed why a later phase must read the state produced by an earlier one. Here that state determines whether an animal can act at all. Our tick subtracts one reserve unit with a zero floor, resolves terminal transitions, and then allows only living animals to perform their action.

That sequence gives us three responsibilities to keep distinct. Life state answers whether the animal is eligible now. A terminal event records the accepted transition. Cleanup removes the inactive object after it is no longer needed in the live collection. If eligibility depended only on removal, an animal awaiting cleanup could still take its turn.

We'll first use ordinary structs and an ordered function so every step is easy to inspect. The next lesson puts the same concern into a Bevy schedule. The reason for checking eligibility again is the same in either form: an animal that was alive at the beginning of the tick can stop being alive before its action phase.

Give a death one event

The helper must distinguish a new death from an animal that remains dead, because only the transition earns a record. The resolve_terminal helper accepts exactly one situation: life is Alive and reserve is zero. It changes life to Dead, appends a terminal record, and returns true. Positive reserve or an already dead animal returns false without adding a record.

The life check is what makes a repeated call harmless. Zero reserve may remain true for many later ticks, but the alive-to-dead transition has already happened. If we recorded an event whenever the number was zero, a single animal could appear to die repeatedly. Checking both the condition and the current life state gives the event its once-only meaning.

It may be tempting to search history instead: if a death record exists, don't add another. That would make eligibility depend on how much history we retain. Once an old record was evicted, the same animal could qualify again. Current life state must own the decision, while history describes the decision that was made.

Our record calls the cause Starved, naming the toy rule that accepted the transition. An animal authored at zero qualifies too. The word doesn't supply a physiological model or a grace period. If we later want a rescue meal, health loss, or a delay at zero, we'll need to change the rule and its timing explicitly.

Keep a record that survives cleanup

After removing Fern, a borrowed reference into her old vector element wouldn't be a usable historical record. We'll instead copy a Key containing run and individual ID into each event, alongside the tick, sequence number, and cause. The journal then owns the information needed to identify the transition without keeping the animal borrowed.

The run number matters when a reset reuses individual IDs. Run seven's ID nine and run eight's ID nine identify different individuals. A nickname can't replace that context because names can repeat, change, or be absent. Within each run, this fixture assumes unique IDs.

Each journal also belongs to one run. We can keep the old journal beside a new world's animals, but its collected ticks describe only its own run. A cross-run query returns unknown rather than borrowing the old coverage as evidence about new events. This extends the same ownership idea we used for saved inspector readings: retaining a value is useful when its provenance stays attached.

Explain what a bounded journal can answer

Keeping every event indefinitely would let a long-running browser session consume memory without a bound. Our journal retains at most a selected positive number of events. It appends at the back of a VecDeque and removes the oldest record from the front when full. The standard VecDeque reference describes those operations; our length check supplies the retention rule. Reserving allocation capacity alone wouldn't enforce it.

Forgetting a row changes what the journal can prove, so it also tracks evicted-record count and a coverage interval. complete_from is the first completely retained tick; collected_through is the last completely collected one. Event sequence numbers keep increasing as old rows leave, preserving the distinction between the newest two records and the first two records ever produced.

A tick becomes collected only after all its terminal producers have finished. We must finish an empty tick too, because “we collected no events” supports a zero count while “we haven't collected this tick” doesn't. The supplied methods enforce consecutive collection and reject appending to a tick that is already sealed.

Eviction can also remove part of a tick. Suppose tick five produced several events and the oldest one is discarded while another tick-five event remains. We can still display the retained event, but we can no longer give a complete count for tick five. The conservative coverage boundary moves to tick six.

use std::collections::VecDeque;

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Key { run: u32, id: u32 }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum Life { Alive, Dead }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum Cause { Starved }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Terminal { sequence: u64, tick: u64, subject: Key, cause: Cause }
#[derive(Debug)]
struct Animal { key: Key, reserve_units: u32, life: Life, actions: u64 }
struct Journal {
    run: u32,
    limit: usize,
    events: VecDeque<Terminal>,
    evicted: u64,
    complete_from: u64,
    collected_through: u64,
    next_sequence: u64,
}
impl Journal {
    fn new(run: u32, limit: usize) -> Self {
        assert!(limit > 0, "this journal requires positive retention");
        Self { run, limit, events: VecDeque::new(), evicted: 0,
            complete_from: 1, collected_through: 0, next_sequence: 1 }
    }
    fn record(&mut self, tick: u64, subject: Key, cause: Cause) {
        assert_eq!(subject.run, self.run);
        assert_eq!(tick, self.collected_through.checked_add(1).unwrap());
        let sequence = self.next_sequence;
        self.next_sequence = sequence.checked_add(1).expect("event sequence exhausted");
        if self.events.len() == self.limit {
            let removed = self.events.pop_front().unwrap();
            self.evicted = self.evicted.checked_add(1).expect("eviction count exhausted");
            self.complete_from = self.complete_from.max(
                removed.tick.checked_add(1).expect("coverage tick exhausted"));
        }
        self.events.push_back(Terminal { sequence, tick, subject, cause });
    }
    fn finish_tick(&mut self, tick: u64) {
        assert_eq!(tick, self.collected_through.checked_add(1).unwrap());
        self.collected_through = tick;
    }
    fn terminal_count(&self, subject: Key, from: u64, through: u64) -> Option<usize> {
        if subject.run != self.run || from > through || from < self.complete_from
            || through > self.collected_through { return None; }
        Some(self.events.iter().filter(|event| event.subject == subject
            && event.tick >= from && event.tick <= through).count())
    }
}

fn step(animals: &mut [Animal], journal: &mut Journal) {
    let tick = journal.collected_through.checked_add(1).expect("tick exhausted");
    for animal in animals.iter_mut().filter(|animal| animal.life == Life::Alive) {
        animal.reserve_units = animal.reserve_units.saturating_sub(1);
    }
    for animal in animals.iter_mut() { resolve_terminal(animal, tick, journal); }
    for animal in animals.iter_mut().filter(|animal| animal.life == Life::Alive) {
        animal.actions = animal.actions.checked_add(1).expect("action count exhausted");
    }
    journal.finish_tick(tick);
}

}
