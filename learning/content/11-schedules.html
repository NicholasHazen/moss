Safe access does not choose the right order

The previous lesson made reading a source and writing a preview safe by proving that their queries reached different entity sets. That gives each system valid access to its data. It leaves another question open: does an observer read that data before the change it is supposed to report, or afterwards? To make our two labels meaningful, we need to express those relationships between systems.

Keep the arithmetic small so we can follow that relationship directly. record_before reads the counter and appends a labeled observation; increment adds one to the counter; record_after reads the counter and appends its own observation. Both observers use the value they find in the world. If either one runs at the wrong time, it will faithfully record the wrong stage of the update rather than reconstructing the number we expected.

Bevy already knows that these systems cannot all access the counter at once. The observers request shared access to Counter, while increment requests mutable access. The observers also both write the trace. Those declarations let the executor prevent incompatible work from overlapping, but either observation can safely happen before or after the mutation. Safety therefore leaves several possible sequences, only one of which meets our reporting requirement.

Using a single-threaded executor makes the trace easier to follow because only one system runs at a time. It still leaves those possible sequences open. A system's name and its position in a registration tuple do not supply a guaranteed domain order without explicit dependencies, so changing the executor alone would leave our reporting requirement unstated.

For this three-system sequence, .chain() adds the ordering constraints between successive systems in the tuple. The ordinary default prelude imports the configuration trait that supplies the method. Bevy 0.18.1's versioned schedule-configuration source describes the chain and the related before/after operations, which can express individual edges when a complete sequence is unnecessary.

A chain is a good fit here because every pair of neighboring steps has a reason to be ordered. A larger schedule may contain independent work as well. Named system sets and selected edges let you preserve that independence while stating the relationships the model relies on. Drawing the needed dependencies first makes it easier to distinguish a real requirement from an order added merely because the functions appeared next to each other.

Test meaning rather than scheduler luck

The first test reads both observation values and their sequence after one execution. That gives each edge a visible consequence. The second test changes the starting value and executes the schedule twice, so a hard-coded pair of readings cannot satisfy it. In both cases, the assertions examine resources changed by the installed systems; they do not substitute a second helper calculation for the work we wanted to run.

To see why those observations matter, the final two tests construct deliberately wrong schedules with explicit ordering. One increments before both observations; the other increments after both. Each still reaches the correct final counter, but each produces a different trace. These counterexamples demonstrate a concrete mistake the trace catches and a counter-only assertion misses.

Removing .chain() is a less reliable way to demonstrate the mistake. An unconstrained scheduler might happen to choose the desired order in your current build, so the trace could still pass on that run. The explicitly wrong schedules make the counterexample reproducible. When reviewing the real configuration, also look for the declared dependencies: an observed success alone cannot establish an ordering promise the program never made.

The same reasoning explains why switching executors would not repair the missing relationship. The 0.18.1 executor reference describes the available execution modes, but the application still has to say which valid system must precede another. This lab uses one thread to simplify observation and explicit edges to establish meaning.

Registration and order are separate responsibilities

There are two places to check when expected work is absent. First, the function must actually be added to the schedule you run; defining it in a Rust module does not arrange an execution. Then its dependencies must be configured within that schedule. An ordering expression in another schedule cannot organize this run just because it names the same function.

When using before or after, find both ends of the relationship and confirm that the referenced systems or sets are present in the relevant schedule. Mentioning a function as the other end of an edge does not replace registering its work. Our add_systems call and chain put registration and order together, making both responsibilities visible in one place.

You can trace the same relationship in Moss's current crates/moss-sim/src/simulation.rs: its installed chain runs maintenance before complete_tick. The completed-tick count consequently describes scheduled work that has already finished. The prepared movement adapter is still absent at this checkpoint. It joins that sequence only after review of the active exercise and the explicit transition described in its guide; an isolated helper passing does not install its system.

The vector is enough for this short experiment because we execute the schedule only once or twice. Keeping observations indefinitely in a browser would introduce further requirements: identities to say what was observed, a retention limit, and coverage labels to explain what remains. Correct timing gives a record its meaning, but it does not by itself make an unlimited journal a suitable design.
