Imagine that our birth system has already taken a payment from the first parent when it discovers that the second is still in cooldown. No child can be created, but one parent has lost reserve anyway. To prevent that half-finished result, we'll decide whether the entire birth can happen before changing either parent. That decision will also give the child an identity and establish when it gets its first turn.

This isolated Bevy exercise builds on rest and commitment, where recovery, reserve and permission to act had different meanings. Here we'll carry that distinction into deferred entity creation. The fixed costs and timing are authored teaching rules; the exercise leaves live Moss and NOW.md unchanged.

Make one acceptance cover both parents

Start with adults 1 and 2, each holding ten reserve units. Our rule charges three units to each parent and gives their child four, so an accepted birth leaves the parents at seven and seven. Of the six units they paid, four have moved into the child's reserve and two have been spent by the reproductive process. Following the units this way gives us a concrete accounting check before we involve the ECS world.

Affording the payment is only part of being an eligible parent. Each animal must also be an adult, have reached its first eligible tick and be out of cooldown. Both participants must be present, and they must be distinct individuals: finding the same animal twice doesn't produce a pair. If either participant fails a condition, we'll reject the whole request while leaving both reserves alone.

Cooldown determines when a successful parent may participate again. A birth on tick one assigns both parents a deadline of four, and the eligibility check accepts the parent once the current tick reaches that deadline. Ticks two and three are therefore too early; tick four is allowed. Expressing the rule in simulation ticks keeps its meaning stable when the browser draws more often or the reader pauses to inspect the world.

Those future values need to be representable before we accept the birth. The planner will use checked arithmetic for the cooldown deadline, the child's first eligible tick and the next identity. A wrapped deadline could make a parent eligible again immediately, while a wrapped identity could give a new child an old animal's history. An overflow should therefore reject the request for the same reason an unaffordable payment does: we can't fulfill the complete outcome we promised.

Plan with values; commit through borrows

We can make that promise easier to keep by calculating the result away from the live components. plan_birth receives two copied Animal values and returns a Result. On success, the value contains both proposed parent states, the child and the next allocator value. On failure, it contains the reason for rejection. Because the function never receives references to the world's parents, it cannot accidentally take one parent's payment on the way to an error.

The ECS resolver connects that calculation to the current world. It obtains mutable access to the two distinct parents, copies their states into the planner and, only if planning succeeds, writes the returned states back. All the expected ways to reject a birth therefore occur before those authoritative assignments. We're using a transaction in this local sense: one accepted result supplies all the changes. It doesn't promise durable storage or recovery if the process itself fails.

This is also a useful application of the earlier borrowing lesson. We copy the small values needed to consider a proposal, while keeping mutation of the real parents in one clearly defined place. Bevy's 0.18.1 get_many_mut method helps us request both mutable accesses together; it rejects aliased or unavailable query items. The planner then answers the domain question that Bevy cannot answer for us: are these two animals allowed to produce a child now?

The child needs a stable ID before its entity is spawned. As in the population lesson, the roster assumes those IDs are unique, so the resolver checks that the proposed child ID isn't already in the world. It advances the allocator immediately after each accepted birth. Otherwise, two accepted pairs could choose the same ID while both children were still waiting in the command queue, where a query wouldn't find them yet.

Resolve an unordered pair once

A second problem appears when we gather possible pairs. A neighborhood scan may encounter adults 1 and 2 as both (1, 2) and (2, 1), although they describe the same partnership. Sort the two IDs inside each pair and collect the resulting keys in a BTreeSet. Both encounters then produce one key, and the ordered set gives us a reproducible sequence for considering different pairs.

Deduplicating requests doesn't settle competition between different partnerships. Consider (1, 2) followed by (1, 3): the pairs are distinct, but parent 1 is shared. Once the first pair succeeds, its payment and cooldown change parent 1 immediately. The second request must read those current components and will find the parent ineligible. The set prevents repeated consideration of the same pair; current-state validation prevents a parent being reused by another pair.

Ordering pairs this way favors lower IDs, because (1, 2) precedes (1, 3). That's a deliberate simplification for a fixture whose result we want to explain exactly. A different pairing policy could use another recorded priority without changing the requirement that each attempt validate the current parents and commit one complete result.

Each resolver pass consumes its requests once. A rejected request doesn't wait around to become a birth on a later tick, and LastBirths is cleared for the next pass so it describes only that tick's accepted births. Parentage has a longer life: the child stores its parents' IDs in a separate field. Founders use None because this fixture supplies no parentage for them, rather than asserting that they had no parents.

Presence is not permission to act

After accepting the plan and paying the parents, the resolver queues the child with Commands::spawn. That queues a structural change rather than inserting the entity immediately. Our schedule explicitly applies the commands before the action phase, so the newborn will be present when that phase queries the world. We now need to decide whether being present is enough to earn a turn.

For this model, the child first acts on the following tick. A child born on tick one therefore receives first_eligible_tick = 2, and the action system checks that field whenever it visits an animal. The newborn can appear in an inspection on its birth tick while still having an action count of zero. On tick two, the same entity becomes eligible and records its first action.

Here an action only increments a counter, which lets us examine the timing without implementing movement or feeding again. Maturity remains a separate condition: the newborn has adult: false, so reaching its first action tick doesn't make it a potential parent. A later maturation rule would have to change that state explicitly.

We could try to delay the first turn by relying on a convenient command-flush position, but that would make the rule fragile when the schedule changes. The explicit eligibility field continues to explain the intended timing even if an observation phase needs to see newborns earlier. The versioned Commands documentation describes how structural changes become visible; the first-eligible tick states what a visible child may do.

#[derive(Resource, Default)]
struct Tick(u64);
#[derive(Resource)]
struct NextId(u64);
#[derive(Resource, Default)]
struct Requests(Vec<(u64, u64)>);
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Birth {
    tick: u64,
    child: u64,
    parents: [u64; 2],
}
#[derive(Resource, Default)]
struct LastBirths(Vec<Birth>);

fn begin_tick(mut tick: ResMut<Tick>) {
    tick.0 = tick.0.checked_add(1).expect("tick counter overflow");
}

fn resolve_births(
    mut commands: Commands,
    tick: Res<Tick>,
    mut next: ResMut<NextId>,
    mut requests: ResMut<Requests>,
    mut births: ResMut<LastBirths>,
    mut animals: Query<(Entity, &mut Animal)>,
) {
    births.0.clear();
    let ids: BTreeMap<_, _> = animals
        .iter()
        .map(|(entity, animal)| (animal.id, entity))
        .collect();
    let pairs: BTreeSet<_> = std::mem::take(&mut requests.0)
        .into_iter()
        .map(|(a, b)| (a.min(b), a.max(b)))
        .collect();
    for (a, b) in pairs {
        let (Some(&a_entity), Some(&b_entity)) = (ids.get(&a), ids.get(&b)) else {
            continue;
        };
        if ids.contains_key(&next.0) {
            continue;
        }
        let Ok([(_, mut left), (_, mut right)]) = animals.get_many_mut([a_entity, b_entity]) else {
            continue;
        };
        let Ok(plan) = plan_birth(*left, *right, tick.0, next.0) else {
            continue;
        };
        *left = plan.a;
        *right = plan.b;
        next.0 = plan.next_id;
        commands.spawn(plan.child);
        births.0.push(Birth {
            tick: tick.0,
            child: plan.child.id,
            parents: plan.child.parents.expect("a planned child has parentage"),
        });
    }
}

fn act(tick: Res<Tick>, mut animals: Query<&mut Animal>) {
    for mut animal in &mut animals {
        if tick.0 >= animal.first_eligible_tick {
            animal.actions = animal
                .actions
                .checked_add(1)
                .expect("action counter overflow");
        }
    }
}

fn schedule() -> Schedule {
    let mut schedule = Schedule::default();
    schedule.set_executor_kind(ExecutorKind::SingleThreaded);
    schedule.add_systems((begin_tick, resolve_births, ApplyDeferred, act).chain());
    schedule
}

fn fixture(requests: Vec<(u64, u64)>) -> World {

const CHILD_RESERVE: u32 = 4;
const COOLDOWN_TICKS: u64 = 3;

#[derive(Component, Clone, Copy, Debug, PartialEq, Eq)]
struct Animal {
    id: u64,
    reserve: u32,
    adult: bool,
    cooldown_until: u64,
    first_eligible_tick: u64,
    parents: Option<[u64; 2]>,
    actions: u32,
}

fn adult(id: u64, reserve: u32) -> Animal {
    Animal {
        id,
        reserve,
        adult: true,
        cooldown_until: 0,
        first_eligible_tick: 1,
        parents: None,
        actions: 0,
    }
}

#[derive(Debug, PartialEq, Eq)]
enum Rejected {
    SameParent,
    Ineligible,
    Unaffordable,
    InvalidChildId,
    CounterOverflow,
}

#[derive(Debug, PartialEq, Eq)]
struct BirthPlan {
    a: Animal,
    b: Animal,
    child: Animal,
    next_id: u64,
}

fn plan_birth(
    mut a: Animal,
    mut b: Animal,
    tick: u64,
    child_id: u64,
) -> Result<BirthPlan, Rejected> {
    if a.id == b.id {
        return Err(Rejected::SameParent);
    }
    if !a.adult
        || !b.adult
        || a.first_eligible_tick > tick
        || b.first_eligible_tick > tick
        || a.cooldown_until > tick
        || b.cooldown_until > tick
    {
        return Err(Rejected::Ineligible);
    }
    if a.reserve < PARENT_COST || b.reserve < PARENT_COST {
        return Err(Rejected::Unaffordable);
    }
    if child_id == 0 || child_id == a.id || child_id == b.id {
        return Err(Rejected::InvalidChildId);
    }
    let cooldown_until = tick
        .checked_add(COOLDOWN_TICKS)
        .ok_or(Rejected::CounterOverflow)?;
    let first_eligible_tick = tick.checked_add(1).ok_or(Rejected::CounterOverflow)?;
    let next_id = child_id.checked_add(1).ok_or(Rejected::CounterOverflow)?;
    a.reserve -= PARENT_COST;
    b.reserve -= PARENT_COST;
    a.cooldown_until = cooldown_until;
    b.cooldown_until = cooldown_until;
    let child = Animal {
        id: child_id,
        reserve: CHILD_RESERVE,
        adult: false,
        cooldown_until: 0,
        first_eligible_tick,
        parents: Some([a.id.min(b.id), a.id.max(b.id)]),
        actions: 0,
    };
    Ok(BirthPlan {
        a,
        b,
        child,
        next_id,
    })
}

Recall answer

Parent payments and cooldown take effect immediately so another pair can't reuse those resources or permissions. The child entity appears when commands are applied, but its stable identity and first-eligible tick already belong to the accepted plan. Reaching that tick permits an action; reaching maturity permits reproduction. They answer different questions about the same child.
