Follow one ordered tick

Both comparison scenarios start IDs 1 and 2 with three reserve units each. ID 1 needs two upkeep units per tick, while ID 2 needs one; both may take a meal of up to two units from patch 100. The patch starts empty and can hold eight. Before tracing the entire run, consider the first tick: upkeep will leave the animals with one and two units, so their next opportunity depends on whether growth occurs before they try to eat.

The diagram follows that opportunity through six phases. First advance the tick and clear its ledger. Then charge upkeep, accept growth on a lit tick, and resolve competing meals. Only after those meals do we mark any remaining zero-reserve grazers dead and seal the history interval. Reading a snapshot doesn't advance through these phases; it shows the result of the last completed step.

The four-tick day lights ticks one and two, then darkens ticks three and four. Limited supply requests two new units on each lit tick; generous supply requests six. Growth accepts only what fits in the patch. When the grazers eat, lower IDs claim first and each transfer immediately reduces the biomass available to the next grazer. This makes the result reproducible, although it gives no guarantee of fairness to the animal that goes second.

We can account for this tick because each operation has a different effect on stores. Upkeep removes units, growth adds units, and meals move units from one store to another. Consequently, ending stores plus actual upkeep paid must equal starting stores plus actual growth accepted. The word actual matters: an animal with one unit cannot pay a requested cost of three, and this model carries no unpaid debt. The ledger must describe what happened, because copying the requests would make that equality fail even when the state changes were correct.

Reconstruct a whole typed system

Upkeep is a useful first system to reconstruct because its arithmetic is small enough to hold in mind while choosing the ECS access. Read maintain in your copy of src/lifecycle.rs, then set its implementation aside and replace the complete function. Keep the imports and starve. Your function needs to choose its parameters, visit the intended entities, change their reserves, and leave an accurate ledger and event record.

Begin with what that responsibility requires. The system reads the clock and each stable identity, mutates each grazer, and writes the shared ledger and journal. It doesn't need a patch: the opportunity to eat belongs to a later phase. Writing a query that requests a Grazer expresses that membership directly, rather than making the function search arbitrary entities for something it can charge.

There is one less obvious requirement. Although upkeep payments don't compete with each other, their events enter the journal in traversal order. If reversing spawn order changes that sequence, it can also change which events a bounded history retains. Collecting and sorting owned IDs gives the system a declared order before it starts to mutate components. The acceptance suite checks that order as part of the complete snapshot.

Hint 1: write the access declaration first

Use Res<Clock>, a mutable query fetching (Entity, &Identity, &mut Grazer), and mutable ledger/history resources. Entity gives you a lookup handle, while Identity supplies the application ID whose order must remain stable.

Hint 2: separate ordering from mutation

Collect owned pairs of stable ID and entity handle, sort them, then fetch each mutable grazer. Skip dead rows and charge the smaller of available reserve and configured cost. Use that same actual amount for the reserve change and ledger, recording an event only when the payment is positive.

Complete replacement: maintain in src/lifecycle.rs
pub(crate) fn maintain(
    clock: Res<Clock>,
    mut grazers: Query<(Entity, &Identity, &mut Grazer)>,
    mut ledger: ResMut<TickLedger>,
    mut history: ResMut<History>,
) {
    let mut order: Vec<_> = grazers
        .iter()
        .map(|(entity, id, _)| (id.0, entity))
        .collect();
    order.sort_by_key(|(id, _)| *id);
    for (id, entity) in order {
        let (_, _, mut grazer) = grazers.get_mut(entity).expect("listed grazer still exists");
        if grazer.life != Life::Alive {
            continue;
        }
        let paid = grazer.reserve_units.min(grazer.maintenance_units_per_tick);
        grazer.reserve_units -= paid;
        ledger.maintenance_units = ledger
            .maintenance_units
            .checked_add(u64::from(paid))
            .expect("maintenance ledger exhausted");
        if paid > 0 {
            history.record(
                &clock,
                EventKind::Maintenance {
                    grazer: id,
                    units: paid,
                },
            );
        }
    }
}

Let a compiler error reveal a held borrow

The working function separates collecting IDs from mutating grazers. To see why that separation matters in Rust, temporarily replace the entire maintain function with the version below. It tries to keep query items for the later loop instead of copying just the IDs and handles. pub(crate) fn maintain(mut grazers: Query<(Entity, &Identity, &mut Grazer)>) {
    let borrowed: Vec<_> = grazers.iter().collect();
    for (entity, _identity, _old) in borrowed {
        let (_, _, mut grazer) = grazers.get_mut(entity).unwrap();
        grazer.reserve_units = grazer.reserve_units.saturating_sub(1);
    }
}

The expected error says that grazers cannot be borrowed mutably while an immutable borrow is still in use. Owning the vector doesn't make its contents independent of the world: the collected items still contain references into the query. The second loop uses those references while asking get_mut for exclusive access to the same component data, so the compiler cannot grant both accesses.

Restore the complete function above and compare what crosses the boundary between its two loops. IDs and entity handles are owned lookup values; keeping them doesn't retain a component borrow. Each later lookup can therefore borrow a grazer briefly, perform its work, and release that access before the next iteration. The repair follows from deciding what the second phase actually needs to remember. Bevy's 0.18.1 Query documentation describes these fetched component references and entity handles.

Growth hint

Return unless the current executed tick is lit. Sort owned patch IDs and handles, then accept the smaller of the growth request and remaining capacity. Increase biomass and the ledger by that accepted amount, preserving the same distinction between a configured request and an actual flow that you used for upkeep.

Complete replacement: grow in src/supply.rs
pub(crate) fn grow(
    clock: Res<Clock>,
    daylight: Res<Daylight>,
    mut patches: Query<(Entity, &Identity, &mut Patch)>,
    mut ledger: ResMut<TickLedger>,
    mut history: ResMut<History>,
) {
    if daylight.is_lit(clock.tick) != Some(true) {
        return;
    }
    let mut order: Vec<_> = patches
        .iter()
        .map(|(entity, id, _)| (id.0, entity))
        .collect();
    order.sort_by_key(|(id, _)| *id);
    for (id, entity) in order {
        let (_, _, mut patch) = patches.get_mut(entity).expect("listed patch still exists");
        let added = patch
            .growth_units_per_lit_tick
            .min(patch.capacity_units - patch.biomass_units);
        patch.biomass_units += added;
        ledger.added_units = ledger
            .added_units
            .checked_add(u64::from(added))
            .expect("growth ledger exhausted");
        if added > 0 {
            history.record(
                &clock,
                EventKind::Growth {
                    patch: id,
                    units: added,
                },
            );
        }
    }
}

Complete investigation.rs and the prediction it tests
use moss_course_ecosystem::{CourseWorld, Daylight, Life, Scenario};

#[test]
fn equal_potential_supply_can_have_different_timing_and_survivors() {
    let mut steady_setup = Scenario::generous_supply();
    steady_setup.daylight = Daylight::new(4, 4).unwrap();
    steady_setup.patches[0].growth_units_per_lit_tick = 3;
    let mut pulsed = CourseWorld::new(Scenario::generous_supply()).unwrap();
    let mut steady = CourseWorld::new(steady_setup).unwrap();
    let (mut pulsed_added, mut steady_added) = (0_u64, 0_u64);
    for _ in 0..12 {
        pulsed.step();
        steady.step();
        pulsed_added += pulsed.snapshot().ledger.added_units;
        steady_added += steady.snapshot().ledger.added_units;
    }
    let pulsed = pulsed.snapshot();
    let steady = steady.snapshot();
    assert_eq!(pulsed.grazers.iter().filter(|g| g.life == Life::Alive).count(), 1);
    assert_eq!(steady.grazers.iter().filter(|g| g.life == Life::Alive).count(), 2);
    assert_eq!((pulsed_added, steady_added), (34, 36));
    assert_eq!(steady.grazers.iter().map(|g| g.reserve_units).collect::<Vec<_>>(), vec![3, 3]);
    assert_eq!(steady.patches[0].biomass_units, 0);
}

With steady input, every tick restores ID 1 from one to three and ID 2 from two to three. Timing was the configuration we changed; unequal accepted supply is a consequence of how that timing interacts with capacity and consumption. The two runs therefore do not have equal actual intake.
