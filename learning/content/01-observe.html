Read the reserve together with the tick

In the current fixture, Fern and Flint each start with 60 reserve units and pay one unit of maintenance per executed simulation tick. After three ticks, each should have 57. Their positions can stay exactly where they were: the application has a maintenance rule, while movement is still unfinished and unscheduled. A changing reserve is already a consequence we can investigate.

To see that consequence clearly, we need to control how much work the world performs. Run the following command from the repository root, then open the local Moss preview. This starts the simulation application alongside the course you're reading.

scripts/with-toolchain.sh trunk serve --locked --release

Pause the simulation, reset the run, and make sure it is paused before stepping. Select Fern and read both her reserve and the completed-tick counter. Press Step three times. At this checkpoint, the expected pair is tick 3 and reserve 57. Now pan or zoom while paused and read the same pair again. You have changed the view, so there may be many new pictures, but you haven't requested any more simulation work.

The two numbers help diagnose a surprising result. If Fern already has less than 60 when you first inspect her, a nonzero tick counter may explain it: the run advanced before you paused. If three presses leave the counter at zero, follow the Step control before changing the maintenance arithmetic. Without the tick, “reserve 57” leaves us guessing when the measurement was taken.

Keeping observation separate from advancement also protects the simulation from its viewer. If drawing a creature charged its upkeep, a faster monitor could make it run out of reserve sooner. An offscreen creature might avoid the charge altogether. Moss gives advancement its own operation so that watching more often doesn't change the outcome.

Follow one request through the world

Open crates/moss-sim/src/simulation.rs and look for the installed schedule. It runs maintenance before complete_tick increments the counter. That order gives SimClock.tick a specific meaning: it counts work that has completed. The public tick(&mut World) function requests this schedule once, producing the transition shown below.

Notice where the first tick becomes visible. Maintenance has already reduced reserve to 59 by the time the counter says 1. A reader of that completed state can therefore interpret the two numbers together. Reading it again follows only the last box; it doesn't send another request through maintenance.

The host still has to decide when to request ticks. It can use elapsed time for pacing, and the browser may draw at a variable rate or become hidden. Those are reasons to make advancement explicit, rather than to ignore time altogether. For the same executed ticks and accepted inputs, a change in presentation should leave the simulation result unchanged. Moss also avoids catching up automatically after a hidden tab.

There is a useful limit to what the counter tells us. Tick 3 means the work installed in the schedule has completed three times. It can't establish that an unscheduled function ran. This explains the opening scene: maintenance can reduce Fern's reserve while the unfinished movement helper has no effect on her position.

Give two viewers the same three ticks

Let's make the distinction small enough to test without a browser. Imagine two sessions beginning at reserve 60. Session A advances three times and reads the state twice after each advance. Session B also advances three times, but reads it two hundred times after each one. Before looking at the Rust, predict their final reserves and identify which operation would have to be wrong for the results to differ.

We'll use an ordinary State struct containing the completed tick and the reserve. The function advance receives &mut State, allowing it to change the caller's state. The inspector receives &State, allowing it to read these fields. The signatures give us a place to look before tracing every call: the assignment to reserve belongs in the function with mutable access.

Hint 1: find the write

Look for the assignment to reserve_units inside advance. Calling the inspector doesn't reach that assignment, regardless of how often the caller asks for a reading.

Hint 2: trace completed states

Begin with (0, 60), then follow (1, 59), (2, 58), and (3, 57). Observations between two advances read the same pair. They don't add another pair to the trace.

Answer: both finish at 57

Each session makes three calls that change the state. The extra observations in session B leave it at the same completed tick and reserve as session A. A comparison of these runs can test that promise in the small program; we'll return to the real schedule after running it.

Run the small example

The complete file below contains both sessions, a program that prints one result, and three tests. Start with advance and inspect, then follow the loop in run. This deliberately small world has no movement, feeding, or death, so every change to its two fields is visible here.

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct State {
    completed_ticks: u64,
    reserve_units: u32,
}

fn initial_state() -> State {
    State { completed_ticks: 0, reserve_units: 60 }
}

fn advance(state: &mut State) {
    state.reserve_units = state.reserve_units.saturating_sub(1);
    state.completed_ticks = state.completed_ticks
        .checked_add(1).expect("tick counter overflow");
}

fn inspect(state: &State) -> (u64, u32) {
    (state.completed_ticks, state.reserve_units)
}

fn run(reads_per_tick: usize) -> State {
    let mut state = initial_state();
    for _ in 0..3 {
        advance(&mut state);
        for _ in 0..reads_per_tick {
            assert_eq!(inspect(&state).0, state.completed_ticks);
        }
    }
    state
}

fn main() {
    let state = run(200);
    println!("ticks={} reserve={}", state.completed_ticks, state.reserve_units);
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn observations_do_not_advance_time() {
        let state = initial_state();
        for _ in 0..120 {
            assert_eq!(inspect(&state), (0, 60));
        }
        assert_eq!(state, initial_state());
    }

    #[test]
    fn observation_frequency_does_not_change_outcome() {
        assert_eq!(run(2), run(200));
        assert_eq!(inspect(&run(2)), (3, 57));
    }

    #[test]
    fn empty_reserve_still_completes_a_tick() {
        let mut state = State { completed_ticks: 8, reserve_units: 0 };
        advance(&mut state);
        assert_eq!(inspect(&state), (9, 0));
    }
}

The expected output is ticks=3 reserve=57, with three passing tests. The comparison test checks the two observation frequencies from our prediction. The repeated-read test starts before any advance and checks that inspection alone leaves the initial state intact. Together, they give us more confidence than a printed result from just one session.

The last test starts with an empty reserve. Advancing still completes a tick, while reserve remains zero. That follows from two separate choices in advance: saturating_sub floors reserve at zero, and checked_add advances the counter or fails if its next value cannot be represented. A floor makes sense for this reserve model; silently freezing or wrapping the completed-tick counter would hide how much work occurred.

An empty reserve also doesn't remove a creature in this example. The current Moss maintenance rule has the same floor, with death still outside that live checkpoint. Arithmetic can tell us that an account is empty; deciding what happens to its owner requires a lifecycle rule. We'll keep those questions separate as the terrarium grows.

Check the rule where it is installed

The two read frequencies tested the separation between observation and advancement in our small program. They don't tell us whether Moss actually installs and runs its maintenance rule. To follow the same claim into the real world, run the existing focused maintenance test from the repository root:

scripts/with-toolchain.sh cargo test -p moss-sim --locked --test maintenance maintenance_spends_energy_and_stops_at_zero -- --exact

Look for one passed test with that exact name. A report of zero tests means the filter selected nothing, while a compilation error means execution never reached the assertion. If you run a broader suite and encounter the unfinished movement exercise, treat that failure as its own result; it doesn't replace this maintenance check.

A tick explains the change; a reading records it

Fern's stationary square now has an explanation: three maintenance ticks changed her reserve, and observing her added no further charge. The small program made that separation easy to trace. The installed test checks Moss's scheduled work, while the browser observation checks what its controls and inspector show. In each case, reading tick and reserve together lets you connect a measurement to completed work instead of guessing from the picture.

There is another kind of observation we haven't built yet. Suppose the inspector saves a reading at tick 0 and keeps it while Fern advances to tick 3. Should the saved reserve become 57 too, or should it remember 60? The answer depends on what we kept: access to the original value, or an independent value of our own.

Recall the access distinction

A shared borrow lets a function read the original state under Rust's borrowing rules. A copied measurement can remain unchanged after the original changes. Both are useful, but a saved historical reading needs to retain what was true when it was captured.

In ownership at the inspector boundary, we'll build that saved reading and use it to work out when to borrow, copy, and take ownership.
