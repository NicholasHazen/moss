A selective Rust survey · 40 minutes

Let a view borrow exactly what it needs

The inspector wants to show a sentence from Fern's journal: “ate 1 unit.” An export wants to keep the same sentence after the journal has been cleared. The text is identical, but its destinations ask different things of our code.

Let a borrowed view depend on the right owner

You'll complete latest_with_kind, a search whose returned view borrows from the journal independently of the temporary search string. We'll compare that view with an owned snapshot, then use small compiler experiments to test what happens when text belongs to a local variable, a journal is cleared, or a borrow reaches its last use.

The aim is to read a lifetime annotation as a relationship between a result and its actual source. By the end, you should be able to choose borrowing for a temporary inspection, copying for a retained export, and an appropriate correction when a reference would outlast the data it needs.

This optional Rust supplement revisits ownership, owned reports and retained history. It uses a small journal fixture with Rust 1.93.1, edition 2024, and changes no ecological rule or active Moss assignment. The fixture gives us a manageable place to explore references before carrying the reasoning into a larger report API.

One observation, two destinations

Our journal contains four records in append order. Actor 7 has meals at ticks two and five, with an observation between them; actor 8 has a meal at tick six. To find actor 7's latest meal, we need to match both actor and kind, returning tick five. Taking the first meal would give an old result, while taking the newest record without checking its actor would describe somebody else. This gives the search a clear job before lifetimes enter the picture.

Each Record owns its kind and note as strings, and the journal owns the vector containing those records. For a temporary inspector, a View can copy the small actor, tick and optional reserve fields while borrowing the note as &str. That avoids allocating the same sentence again, but it also connects the view to its source: every use of the borrowed text must occur while that text remains available.

The export has a different need, so Snapshot gives its note an owned String. Calling snapshot() explicitly copies the text, paying for the independence we asked for. The export can then survive an amendment, eviction or the loss of the original journal altogether. It keeps the sentence as it was copied, rather than following later changes to the source.

The choice therefore starts with the result's intended use. A brief inspection can borrow, while a retained report needs to cross an ownership boundary. Neither design is universally cheaper or better: borrowing couples use to the source, and copying creates storage the result must own. Lifetimes let the borrowed design state that coupling precisely.

Name the relationship the caller needs

Our search borrows two inputs: the journal and a kind string such as “meal.” Only one of them supplies text to the result. The kind is a search condition that we can forget once comparison finishes; the returned note comes from the journal. Look for that distinction in the signature below, which is also used in the complete file.

fn latest_with_kind<'a>(
    journal: &'a Journal,
    actor: u64,
    kind: &str,
) -> Option<View<'a>>

The name 'a connects the journal borrow to the reference stored inside the returned view. It describes a relationship that Rust must check, rather than choosing how many seconds or simulation ticks an allocation will live. The caller must keep the source valid for the uses of the view that the signature permits, and the function body must actually return references consistent with that promise.

Giving kind the same named lifetime would unnecessarily tie the result to the search string as well. The example in main makes the difference visible: it creates an owned search string inside a short inner block, performs the search and uses the resulting view after that block ends. This works because the view borrows no part of the query. A dedicated test keeps that freedom in the API as the implementation changes.

With only one borrowed input, Rust can often express the relationship without a name. The smaller helper writes fn last_note(journal: &Journal) -> Option<&str>, and lifetime elision connects its output to that sole input. A method's &self or &mut self receiver supplies the usual relationship for a returned reference. These are defined signature rules, explained in the Rust Reference; the compiler isn't guessing which input you intended by reading the function body.

The View<'a> type still needs a lifetime parameter because its fields retain a reference. Its implementation can use impl View<'_>, since snapshot doesn't need to name a relationship between that borrow and its owned output. Snapshot needs no lifetime parameter at all. This is another way the ownership decision shows up in the API: the borrowed type describes its connection to a source, while the owned result carries its own data.

Complete the borrowed search

Put the lifetime relationship to work by returning a view of the latest matching journal record. Prepare the practice file from the repository root and run its initial check. Only latest_with_kind is unfinished, so the starter should compile and then fail when the relevant tests reach its todo!. Keep the surrounding functions and tests while filling in that search body.

python3 learning/scripts/labs.py prepare lifetimes --dest work/lifetimes-practice
python3 learning/scripts/labs.py check lifetimes --file work/lifetimes-practice/lifetimes.rs

Here “latest” means the last matching record in append order. The fixture appends chronologically, but the helper itself doesn't sort records or search for the greatest tick. Its None also has a precise meaning: no matching record is retained in the supplied journal. That answer doesn't tell us whether an event once happened and was evicted, or whether the actor is currently present in the world.

Hint 1: search backward with both conditions

Borrow the record collection with iter(), reverse the iterator and use find to require both the actor and kind. Searching from the end makes the first match the latest retained one without rearranging the journal or moving its strings.

Hint 2: borrow the note and copy the small fields

Map the optional matching record into a View. Borrow its note with &record.note, which Rust can coerce to &str, and copy the actor, tick and Option<u32>. In particular, copying the option preserves the difference between an absent measurement and a measured zero.

#[derive(Clone, Debug, PartialEq, Eq)]
struct Record {
    tick: u64,
    actor: u64,
    kind: String,
    note: String,
    reserve_units: Option<u32>,
}

#[derive(Debug, Default)]
struct Journal {
    records: Vec<Record>,
}

#[derive(Debug, PartialEq, Eq)]
struct View<'a> {
    tick: u64,
    actor: u64,
    note: &'a str,
    reserve_units: Option<u32>,
}

#[derive(Debug, PartialEq, Eq)]
struct Snapshot {
    tick: u64,
    actor: u64,
    note: String,
    reserve_units: Option<u32>,
}

impl View<'_> {
    fn snapshot(&self) -> Snapshot {
        Snapshot {
            tick: self.tick,
            actor: self.actor,
            note: self.note.to_owned(),
            reserve_units: self.reserve_units,
        }
    }
}

fn last_note(journal: &Journal) -> Option<&str> {
    journal.records.last().map(|record| record.note.as_str())
}

fn fixture() -> Journal {
    Journal {
        records: vec![
            Record {
                tick: 2,
                actor: 7,
                kind: "meal".into(),
                note: "ate 2 units".into(),
                reserve_units: Some(9),
            },
            Record {
                tick: 4,
                actor: 7,
                kind: "observation".into(),
                note: "reserve uncollected".into(),
                reserve_units: None,
            },
            Record {
                tick: 5,
                actor: 7,
                kind: "meal".into(),
                note: "ate 1 unit".into(),
                reserve_units: Some(10),
            },
            Record {
                tick: 6,
                actor: 8,
                kind: "meal".into(),
                note: "ate 3 units".into(),
                reserve_units: Some(12),
            },
        ],
    }
}

fn main() {
    let mut journal = fixture();
    let view = {
        let search = String::from("meal");
        latest_with_kind(&journal, 7, &search).unwrap()
    };
    println!(
        "view: actor={} tick={} note={}",
        view.actor, view.tick, view.note
    );
    let snapshot = view.snapshot();
    journal.records.clear();
    println!("retained rows: {}", journal.records.len());
    println!(
        "export: actor={} tick={} note={} reserve={:?}",
        snapshot.actor, snapshot.tick, snapshot.note, snapshot.reserve_units
    );
    assert_eq!(last_note(&journal), None);
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn finds_latest_matching_actor_and_kind_in_append_order() {
        let journal = fixture();
        let view = latest_with_kind(&journal, 7, "meal").unwrap();
        assert_eq!((view.tick, view.actor, view.note), (5, 7, "ate 1 unit"));
        assert_eq!(view.reserve_units, Some(10));
    }

    #[test]
    fn append_order_is_not_replaced_by_a_greatest_tick_search() {
        let mut journal = fixture();
        journal.records.push(Record {
            tick: 1,
            actor: 7,
            kind: "meal".into(),
            note: "late archival copy".into(),
            reserve_units: None,
        });
        let view = latest_with_kind(&journal, 7, "meal").unwrap();
        assert_eq!((view.tick, view.note), (1, "late archival copy"));
    }

    #[test]
    fn empty_or_absent_match_is_none() {
        assert_eq!(latest_with_kind(&Journal::default(), 7, "meal"), None);
        let journal = fixture();
        assert_eq!(latest_with_kind(&journal, 99, "meal"), None);
        assert_eq!(latest_with_kind(&journal, 7, "birth"), None);
    }

    #[test]
    fn view_borrows_the_original_note_allocation() {
        let journal = fixture();
        let view = latest_with_kind(&journal, 7, "meal").unwrap();
        assert!(std::ptr::eq(view.note, journal.records[2].note.as_str()));
    }

    #[test]
    fn query_need_not_live_as_long_as_the_returned_view() {
        let journal = fixture();
        let view = {
            let query = String::from("meal");
            latest_with_kind(&journal, 7, &query).unwrap()
        };
        assert_eq!(view.note, "ate 1 unit");
    }

    #[test]
    fn snapshot_survives_mutation_eviction_and_owner_drop() {
        let snapshot = {
            let mut journal = fixture();
            let snapshot = latest_with_kind(&journal, 7, "meal").unwrap().snapshot();
            journal.records[2].note.push_str("; amended");
            journal.records.clear();
            snapshot
        };
        assert_eq!(snapshot.note, "ate 1 unit");
        assert_eq!((snapshot.tick, snapshot.actor), (5, 7));
    }

    #[test]
    fn uncollected_reserve_and_measured_zero_stay_distinct() {
        let mut journal = fixture();
        let unknown = latest_with_kind(&journal, 7, "observation")
            .unwrap()
            .snapshot();
        journal.records[1].reserve_units = Some(0);
        let zero = latest_with_kind(&journal, 7, "observation")
            .unwrap()
            .snapshot();
        assert_eq!(unknown.reserve_units, None);
        assert_eq!(zero.reserve_units, Some(0));
        assert_ne!(unknown, zero);
    }

    #[test]
    fn unicode_note_is_borrowed_whole_and_single_input_elision_works() {
        let mut journal = Journal::default();
        journal.records.push(Record {
            tick: 1,
            actor: 7,
            kind: "observation".into(),
            note: "Fern — 水".into(),
            reserve_units: None,
        });
        assert_eq!(last_note(&journal), Some("Fern — 水"));
        assert_eq!(
            latest_with_kind(&journal, 7, "observation").unwrap().note,
            "Fern — 水"
        );
    }
}

        Snapshot {
            tick: self.tick,
            actor: self.actor,
            note: self.note.to_owned(),
            reserve_units: self.reserve_units,
        }

fn latest_with_kind<'a>(journal: &'a Journal, actor: u64, kind: &str) -> Option<View<'a>> {
    journal
        .records
        .iter()
        .rev()
        .find(|record| record.actor == actor && record.kind == kind)
        .map(|record| View {
            tick: record.tick,
            actor: record.actor,
            note: &record.note,
            reserve_units: record.reserve_units,
        })
}

fn last_note(journal: &Journal) -> Option<&str> {
    journal.records.last().map(|record| record.note.as_str())
}

Make the compiler experiment small

Now try a smaller function that can't keep its promise. It creates text locally and attempts to return a reference to that text. Save the complete probe as work/lifetimes-practice/dangling.rs, separately from the working lab, so its expected compilation failure is easy to inspect on its own.

fn summary<'a>() -> &'a str {
    let text = String::from("actor=7 tick=5");
    &text
}
fn main() {
    println!("{}", summary());
}
rustc +1.93.1 --edition=2024 work/lifetimes-practice/dangling.rs -o work/lifetimes-practice/dangling

Rust 1.93.1 rejects the probe with E0515, reporting that the reference points to a local variable. The string belongs to summary and will be dropped when that function returns, so the caller would have no valid storage left to read. Writing a longer lifetime—or 'static—can't make the local owner survive. The annotation must describe a valid ownership relationship; it can't create one.

Immediate correction: return the newly created value

Replace the probe with this version, which returns the newly created string itself, and rerun the same compilation command. Running work/lifetimes-practice/dangling then prints actor=7 tick=5. Ownership moves to the caller, which can keep the result. If the text already belonged to the caller, returning a borrow of that caller-owned text could have been a different valid design.

fn summary() -> String {
    String::from("actor=7 tick=5")
}
fn main() {
    println!("{}", summary());
}

The Rust Book's lifetime chapter develops this distinction between describing a reference's relationship and controlling storage duration. Our probe removes the journal, iterator and optional result so the compiler's objection has one clear cause: the returned reference outlives the local data it would refer to.

End a view before changing its owner

The local-string probe showed an owner disappearing at return. A journal can also invalidate borrowed text through mutation, so the order of uses now matters. Back in the working program, we read the view and make a snapshot before calling journal.records.clear(). Nothing uses the view afterward, so Rust can finish this ordinary borrow after its last use even though the enclosing block continues. Move a later println!("{}", view.note) below the clear and the situation changes: the program now asks to read text after an operation that may destroy it, producing E0502.

You can resolve that conflict by printing the view before clearing, or by printing snapshot.note afterward. The right correction depends on whether you need current borrowed text or a retained copy. Clearing the vector requires exclusive access, and the diagnostic is protecting the particular note that a later use of the view still needs. Adding lifetime names elsewhere won't change that sequence of events.

This also explains why an inspector usually shouldn't own a journal and keep an ordinary reference into that same journal as another field. Construct a view when a caller borrows the journal, or keep a stable actor ID and resolve it when needed. When the result must survive a reset, use an owned snapshot. Those designs meet our needs without introducing the extra constraints of a self-referential owning structure.

To check the boundary, consider three changes: dropping the temporary search string, clearing the journal, and replacing a measured zero with an absent measurement. Predict which affects the borrowed view's validity and which changes the meaning of the observation. They're easy to conflate if every problem is described loosely as missing data.

Recall answer

The query string can disappear because the view doesn't borrow it. Clearing the journal must wait until the view's last use, unless we first copy what needs to survive. Some(0) and None describe a measured zero and no measurement, respectively; that semantic distinction doesn't determine a reference's lifetime.

Let the destination decide whether the text is borrowed

The two destinations from the opening now have different, useful APIs. The inspector borrows its sentence from the journal, independently of the short-lived search string. The export owns a snapshot that survives clearing the journal. A lifetime annotation states the first relationship; copying creates the independence needed for the second. The native tests establish that small contract, leaving storage durability and wider retention policy to their own checks.
