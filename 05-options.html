Missing is a different state

The inspector says “no food,” but Fern's situation is still unclear. Perhaps she hasn't selected a patch. Perhaps her selected patch is empty. Or perhaps its reading is missing. Those situations need different explanations before anyone decides what Fern should do next.

You'll implement an isolated observer in options.rs, resolving a selected ID against supplied readings. The current Moss fixture authors its movement target; this exercise doesn't add target selection or feeding, and the live assignment remains in NOW.md.

Give each missing fact its own meaning

The observer we'll build must preserve three different answers: no target was selected, the selected patch has a reading, or that reading could not be found. We'll model those answers as enum variants, resolve an optional identity against borrowed readings, and return an owned description. By testing an empty patch alongside a missing one, you'll be able to explain why zero is sometimes the right result and sometimes an invented answer.

Ask what is absent

We've already encountered None in two places. In the forecast, it meant that the function couldn't represent the exact requested amount. In the audit query, it meant that a matched entity had no reserve component. The same Rust spelling answered different questions. To interpret an optional value, we need to know what was being requested.

For Fern's target, the first question is whether an identity has been selected at all. We'll express that with Option<SimId>. A value of Some(SimId(3)) carries the selected identity, while None says no identity was supplied. Having a selected ID still doesn't tell us what a patch contains, or even whether the supplied readings include that patch.

Resolving the identity therefore takes a second step: search the snapshot for a patch reading whose ID matches. If we find it, we can report its biomass, including a legitimate zero. If we don't, we can report that the selected ID is missing from this snapshot. Keeping the two steps separate lets an empty patch remain distinguishable from a missing reading.

We should be careful about what that failed search proves. A snapshot could be partial, stale, or from a different run; the lab doesn't supply enough information to distinguish those explanations. “Missing from this reading” is supported by the lookup. “Destroyed” would require evidence that we haven't collected.

Keep each answer with the data it needs

Our returned TargetView will have three alternatives. Unchosen needs no further data. Present needs both the selected ID and observed biomass. Missing needs the unresolved ID so the inspector can say which reference it couldn't find. A Rust enum lets each alternative carry exactly those fields.

Compare that with a struct containing separate has_target and found flags, plus an ID and biomass. Such a struct could say “no target” and “found” at the same time, leaving every consumer to work out which fields to trust. With the enum, a value is one variant at a time. Unchosen doesn't need a dummy ID, and Present can't omit its biomass field.

The following cases will become the core of our tests. Notice that the first two can both look like “no food” in a vague display, even though they describe different evidence:

Three facts the inspector should preserve
Input evidenceInspector result
No selected ID, even if patches are availableUnchosen: there is no selected identity to resolve.
Selected ID 3; its reading has biomass zeroPresent { id: SimId(3), biomass_units: 0 }: the reading exists and reports an empty amount.
Selected ID 99; no matching readingMissing { id: SimId(99) }: the selected identity remains unresolved.

The type removes contradictory combinations of these fields, but it can't establish the quality of the input snapshot by itself. Duplicate IDs, for example, would still make a lookup ambiguous. For this lab, we assume unique IDs in one coherent snapshot. Later history work will make run identity and coverage explicit.

The Rust Book's enum chapter develops data-bearing variants and introduces Option. Our design gives you a concrete reason to use them: facts that belong together in one situation can stay together without forcing unrelated situations to carry unused fields.

Resolve one alternative at a time

We'll implement view_target with two matches, following the two questions above. The first examines the optional selected ID. In the Some(id) branch, the pattern binds the contained identity to id. In the None branch, there is no identity to look up, so the helper can return TargetView::Unchosen immediately.

After that early return, the function has a definite ID and can search for its reading. Matching this search result gives a borrowed patch in Some(patch), or no matching row in None. The successful branch copies the ID and biomass into Present. The unsuccessful branch keeps the selected ID in Missing.

Neither match needs a default biomass. That's how the implementation preserves the difference we wanted at the beginning. Searching for a matching ID with positive biomass would lose it: an empty patch would disappear from the result even though its reading was present. The lookup asks about identity; a future feeding rule will ask whether the patch can supply a meal.

Exhaustiveness makes match useful as this design grows. If we later add an alternative for an unavailable snapshot, a consumer that explicitly covers every existing variant must account for the new one. A catch-all can be appropriate when remaining cases truly share behavior, but using it merely to silence the compiler could hide a decision the new state needs. The official match chapter explains these rules.

You may also recognize if let, which is convenient when only one alternative matters, such as displaying a badge for Present. Here the helper owes a status for every case. Keeping both matches visible makes it easier to check that each path preserves the evidence it received.

Build the observer

Before editing, try two calls on paper. First, supply no selected ID and a snapshot containing a patch with 80 units. Then select a patch whose recorded biomass is zero. The observer should describe each input as it stands. Choosing a rich patch in the first case or hiding the empty patch in the second would introduce behavior that the caller didn't request.

Hint 1: begin with the selected identity

For None, return TargetView::Unchosen. For Some(id), keep that exact identity for the lookup instead of selecting the first available row.

Hint 2: search by ID alone

Compare each reading's ID with the selected ID. Zero biomass doesn't disqualify a reading from describing the selected patch.

Prediction answer

The rich patch doesn't change an unchosen target, so the first call returns Unchosen. The second returns Present with biomass zero. We have described the evidence without selecting food or claiming that a meal can succeed.

Complete worked answer: options.rs
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct SimId(u64);

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct PatchReading {
    id: SimId,
    biomass_units: u32,
}

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum TargetView {
    Unchosen,
    Present { id: SimId, biomass_units: u32 },
    Missing { id: SimId },
}

fn view_target(target: Option<SimId>, patches: &[PatchReading]) -> TargetView {
    let id = match target {
        Some(id) => id,
        None => return TargetView::Unchosen,
    };
    match patches.iter().find(|patch| patch.id == id) {
        Some(patch) => TargetView::Present {
            id,
            biomass_units: patch.biomass_units,
        },
        None => TargetView::Missing { id },
    }
}

fn main() {
    let patches = [
        PatchReading { id: SimId(1), biomass_units: 80 },
        PatchReading { id: SimId(3), biomass_units: 0 },
    ];
    println!("{:?}", view_target(Some(SimId(3)), &patches));
    println!("{:?}", view_target(Some(SimId(99)), &patches));
}

Keep the result after the search finishes

Our status preserves the distinction between a missing reading and an observed empty patch. To keep that status after the input snapshot changes, we also need to follow what it owns. The helper borrows its readings through &[PatchReading], a slice. A caller can lend a sequence without handing over its array or vector. Calling iter() visits shared references, and find stops at the first one whose ID satisfies the comparison in the closure.

Finding a borrowed reading doesn't require us to return that borrow. The status needs only its ID and numeric biomass, both of which we copy. After view_target returns, the caller can replace or discard the input snapshot while keeping the status. This is the same ownership pattern as our saved reserve: borrow while observing, then own the values needed for the record.

The first-match behavior explains our uniqueness assumption. With two readings for the same ID, whichever appeared first would determine the result. One test puts a nonmatching row first to catch a helper that skips the ID comparison, but none of these tests validates all IDs for uniqueness. Construction of a real snapshot needs to preserve that separate invariant.

Let the inspector say what it knows

A shortcut such as unwrap_or(0) is useful when zero is the specified fallback. It would be misleading here because an observed zero and a failed lookup mean different things to the reader. The Option reference offers many ways to transform or default an optional value; the operation we choose should follow the question we're answering.

Compare this helper's Option<SimId> with the audit query's Option<&Reserve>. One carries a selected identity; the other carries borrowed access to a component on a matched entity. Seeing Some in either case tells us what is present at that boundary. It doesn't establish that some other entity is still eligible for an action.

Recall the two lookups

The optional component answers whether reserve exists on a matched entity. The optional ID answers whether a target identity was supplied. Resolving that identity requires another lookup, which this lab performs only within its supplied snapshot. Live action-time validity, complete history, and successful feeding require further evidence.

Our inspector can now replace “no food” with an explanation: no target was selected, the selected patch was observed empty, or its reading couldn't be found. In recoverable errors and validated configuration, we'll give an unsuccessful operation a reason too, so its caller can decide how to respond.
